# Bidirectional File Sync — v0 Specification

Working name: `dsync` (placeholder, rename freely).

## 1. Goals and non-goals

**Goals**
- Bidirectional synchronization of regular files between two replicas.
- No data loss: nothing is overwritten or deleted unless the reconciliation rules say it is safe or the user explicitly confirmed it.
- Minimal resource use: skip work whenever the stored state allows it.
- Same core engine drives a CLI and, later, a Flutter app.

**Non-goals for v0**
- Continuous / watch mode.
- Delta (partial-file) transfer.
- Ownership, ACLs, extended attributes.
- More than two replicas per run.
- A transport this project does not own the read loop of. In-process, ssh, and dsync's own socket transport in its two forms — unix-domain (§4.2) and paired TLS over the network (§4.4) — are what v0 speaks.

## 2. Concepts

- **Replica** — a directory tree at a location. A location is a local path, `user@host:path`, `ssh://[user@]destination:path`, `unix://<socket-path>:<replica-path>`, or `peer://<device-name>:<replica-path>`.
  - The first two are told apart by ssh's and rsync's own rule: a colon separates a host from a path only when it comes before the first `/`. That keeps `./log:old` a local path, and it is why `notes` is a relative path rather than a host.
  - That rule can only describe a destination shaped like a hostname, and `ssh` reaches plenty that are not: a `~/.ssh/config` `Host` alias, a `.host` name, `unix/run/ssh-unix-local/socket` for a socket-activated sshd. `ssh://` means "this one is for ssh, hands off": everything between the scheme and the first `:` is handed to `ssh` as its destination, verbatim, slashes included — which is why the colon separates it from the path and a `/` cannot.
  - `unix://` is the same shape for the transport that needs no `ssh` at all: everything between the scheme and the first `:` is the filesystem path of a socket a `dsync agent --listen` is already bound to (§4.2). Both halves are full of slashes, so only a colon could separate them. No `user@` is split off — there is no user to name, because what decides whether the connection is made is whether the process can open the socket, which is the filesystem's answer. A socket path containing a `:` is not addressable, the same limit an `ssh://` destination has.
  - `peer://` is the same shape once more, for a device reached over dsync's own authenticated network transport (§4.4) rather than ssh or a local socket. `peer://`, not `dsync://`: what follows the scheme here is not a transport, it is the name of a peer — the thing being addressed, not the means of addressing it. Everything between the scheme and the first `:` is the name this host gave that device when it was paired, not a host and not an address; it resolves through the paired-device store (§4.4), never through DNS or the network. No `user@` is split off, for the same reason `unix://` splits none: there is no user to name, because what decides whether the connection is made is whether the store still trusts the certificate that name currently resolves to, which is the store's answer and not a credential anyone types. A device name containing a `:` is not addressable, the same limit `ssh://` and `unix://` already carry.


- **Root** — the top directory of a replica, or, for a single-file entry, the one file itself (§6.2). All paths inside a folder root are relative to it.
- **Entry** — one pair of replicas a profile syncs: a folder on each side, or one file on each side (§12). Its own archive, locks, run marker and delete guard, and its own id (`EntryId`, §12).
- **Profile** — a named, ordered list of entries plus options shared across them (ignore rules, thresholds). Lives in a TOML file.
- **Agent** — the component that has direct filesystem access to one replica. Every replica is accessed through an agent, whether local or remote.
- **Archive** — per-replica record of the state of every synced file as of the last successful propagation for that path.
- **Run** — one invocation over one entry: connect to both agents, scan, reconcile, present, apply, exit. A profile with several entries runs one after another, in order (§12's `ProfileRun`).

## 3. Platforms and heads

- Targets: Linux, macOS, Windows, Android, iOS. All five are v1 (task a1d635) — not aspirational, and not free: each bullet below names the cost and whether it is paid now or named as a deferral, so nothing here becomes true by omission.
- Heads: `cli` (Linux, macOS, Windows; Android via Termux) and `app` (Flutter; Android, iOS, and — as a manager, see below — Linux, macOS and Windows). Both are built on the Rust workspace under `native/` (`native/Cargo.toml`): `dsync-domain` (pure rules and values), `dsync-core` (I/O: stores, replicas, the protocol, transports, pairing, `Run`), `dsync-cli` (the `dsync` binary), and `hub` (the rinf bridge the `app` head alone links). The Flutter head (`lib/app/`) never imports `dsync-core` or `dsync-domain` directly; it talks to the core only through `lib/app/core_link/` (§13). iOS has no `cli` head and cannot get one: the platform grants no arbitrary process execution outside an app bundle, so `app` is the only way onto it.
- **The `app` head on desktop manages the device; it does not become a second one.** On Linux, macOS and Windows the Flutter head resolves the *same* state and config directories the CLI head does (§8.3, §12): the core resolves them (`dsync_domain::app_dirs`, below) and hands them back to whichever head asked — the CLI at startup, the app head on its `Init` command's reply — so one machine has one device identity, one paired-device store and one set of archives, whichever head is looking at them. A second, app-private directory was rejected for the same reason it always was: it would give a desktop two device ids, two pairing sets and two grant sets, each invisible to the other, and "manage this device" would mean managing whichever half the user happened to open. What the desktop head does *not* do is serve *in the background*: it runs no always-on agent, and the grants it edits are enforced by `dsync agent` on the same machine, reading the same file. It can answer paired devices, on every platform, for as long as a user has its Serve page open — an explicit, foreground act with the same shape §4.4 gives the enrolment endpoint (`ServeController`, `lib/app/features/serve/`, still Dart: the head's pages, controllers and view state are unchanged by the Rust port, only their seam to the core moved). A per-OS branch hiding that on desktop was rejected: it would be untestable on four of the five targets, and the collision it guards against is already legible rather than damaging — a port `dsync agent --serve` already holds is a rendered refusal naming it, a replica both reach at once meets the replica lock's in-process registry and its file lock and is reported as busy on both heads, and two genuinely independent installs on one machine are expressible with `--state-dir` (§11.2).
- Pinned Dart SDK version in `pubspec.yaml`, for the `app` head — the only Dart left. The Rust workspace pins its toolchain the ordinary cargo way (`dtolnay/rust-toolchain@stable` in CI); there is no `dart compile exe`/SDK-pin story left to state, because the CLI is a plain cargo binary now (§13, §14).
- **Linux, macOS and Windows run the whole test suite in CI** (`.github/workflows/test.yml`, two jobs on all three OSes: `flutter-test` — `dart analyze` and `flutter test` for the `app` head — and `cargo` — `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo build --workspace --all-targets` and `cargo test --workspace` for `native/`, plus a `cargo tree -p dsync-domain -e normal` check that `dsync-domain` never depends on tokio). There is no `dart test` job any more: the Dart core and CLI that job ran are deleted (§13). A Rust test that needs a unix socket, a POSIX signal, a `/bin/sh` stand-in for `ssh` or a POSIX far end is `#[cfg(unix)]`; the real-ssh test additionally skips, naming the reason, on a runner with no sshd. Everything else — including case folding, which the domain and core crates test as a property of the filesystem actually mounted (§16), asserted on all three OSes rather than assumed from the OS — runs in the one `cargo` matrix, so what the bullets below say about a macOS or Windows replica is exercised there, not only reasoned about.
- **The crypto §4.4 is built on is a small, widely-used dependency slice, not code this project owns**: `rustls`, `ring` and `rcgen` (workspace-pinned in `native/Cargo.toml`), which the same `cargo` CI matrix builds and tests on Linux, macOS and Windows, and Cargokit cross-compiles for Android and iOS (below) the same way it cross-compiles the rest of `native/`. What follows in §4.4 is this project's own choices on top of that dependency graph — pinning, grants, framing — not the graph itself.
- **State directory is not XDG-only.** `dsync_domain::app_dirs` (pure; no dependency on `native/core`) resolves it from a `DirRule` and a `HostFacts` value: `$XDG_STATE_HOME`, else `$HOME/.local/state`, on Linux; `~/Library/Application Support` on macOS; `%LOCALAPPDATA%` on Windows; and `DirRule::HostSupplied` for a base directory the Flutter heads resolve through the platform's own API and hand down at `Init` (§8.3). `StateDirChoice` sits one level up, over `DirRule`: `Rule(DirRule)` or `Explicit(DirPath)` for `--state-dir` (§8.3, §11.2) verbatim — a sum type rather than a nullable override, because "derive it from the environment" and "here is the path" cannot both be asked for at once. Every fact the rule needs is passed in on `HostFacts`, never read from the environment inside `app_dirs` itself, so every branch is a unit test with a hand-built value; a variable a branch needs that is absent or empty is an error naming it, never a path silently built from nothing. This is v1 and non-negotiable: §4.4's device identity, the paired-device store, the archive and its lock all live under it (§8.3), so nothing else works on a platform whose branch is wrong. The directory leaf is `dsync` (it was `dsync-rs` during the port, alongside a Dart install's `dsync`; the switch flipped it once there were no more Dart-era stores to keep separate from).
- **Root-relative paths stay `/`-normalized on the wire and in the archive, on every platform** — git does the same, and it is what keeps one archive portable between a Windows and a Linux replica. `RelPath` (`dsync-domain`) is the type that enforces this: it parses and stores a path as `/`-separated segments and refuses one that is not root-relative (an absolute path, `..`, a backslash, a drive-shaped segment), so an invalid path cannot reach the scanner, the wire or the archive at all — there is no separate conversion step to get wrong. The read side is the scanner (`native/core/src/scanner.rs`): a platform-native directory listing is turned into `RelPath`s as it is walked, so a Windows host's `\`-spelled entries become `/`-joined root-relative paths before anything else sees them. The write side is `RelPath::join_under(root)`, which joins the segments onto the replica root through `std::path::PathBuf` — the standard library's own path type already spells the native separator for the host it is compiled for, so there is no `package:path`-style `Style`/`Context` object to inject and no `Platform.isWindows` read inside the core: a Windows host emits `\`-joined native paths because `PathBuf::push` does, not because anything here branches on the OS. `dsync_domain::Platform` (`Unix` | `Windows`, plus `Platform::HOST`) exists only where a location or a rule is *parsed* from host-typed text (§4.1) — a drive-letter check, a `unix://` refusal on Windows — and is passed in there the same way `HostFacts` is above, so a test can hand either platform to the parser without a Windows host.
- **Mode bits (§7.4) do not exist on Windows.** The write path's mode step (`native/core/src/file_write.rs`) is `#[cfg(unix)]`: on Windows there is no `chmod` to call and no attempt to translate ACLs into POSIX bits, so the step compiles to nothing there rather than discovering the platform empirically. On every unix host it first asks its own replica once whether a `chmod` sticks at all — a scratch file, a flipped bit, a `stat` to check it moved — and skips the per-file call for the rest of the session where it does not (Android's external storage, below); a `chmod` that runs and is refused for one path is not an error either. The archive records whatever the post-write `stat` actually reports, which is §7.4's general rule ("record the actual post-write state … rather than the intended one") on Windows as much as anywhere else. That write runs on a real Windows host in CI (above), so the call is exercised; what the value it records *means* there is the Windows claim no test asserts.
- **Case-insensitive filesystems are a correctness issue, not cosmetic, once macOS and Windows are targets.** APFS and NTFS are case-insensitive by default, as Android's external storage already is (below). §16 states the v1 policy and what it does not catch.
- **Symlinks cost nothing here.** A `follow` rule (§5.1, §9) resolves an existing link and syncs its target's *content* as a plain file at the link's path; dsync does not create a symlink at the destination, on any platform — there is no symlink-creation call anywhere in `lib/`, only `Link(...).resolveSymbolicLinks()`, and only to read. Windows' privilege requirement for creating a symbolic link (Developer Mode or `SeCreateSymbolicLinkPrivilege`) gates an operation this project never performs, so it is not a v1 cost and not a deferral either — there is nothing here to defer.
- **iOS is a target within its sandbox, not a general-purpose one.** A replica root is confined to the app's own container (`Documents/`, `Library/`, the rest of what the sandbox grants by default) plus whatever directories the user has separately granted through `UIDocumentPickerViewController` and kept reachable via a security-scoped bookmark. It cannot sync another app's data or an arbitrary path the way the other four targets can; that is a stated platform limitation, not a defect. The `app` head's location picker is built against that constraint: it offers folders under the app's own documents directory, and folders the user chooses through the platform's own chooser — never a free-text path it cannot actually resolve. A chosen folder is proved usable by a `dart:io` probe (list, write one entry, remove it) before it is offered as a replica root, because only the filesystem can answer that question: on iOS the picker's grant lasts the session but not a relaunch until a security-scoped bookmark is persisted (task c3f70e), and on Android the grant that makes a chosen *path* openable is All-files access, not the picker's own tree-URI grant (§16).
- Android note: Android's shared ("external") storage does not preserve POSIX permission bits and is case-insensitive. The engine must not fail when a metadata write is rejected (see §7.4), and must record the *actual* post-write state in the archive rather than the intended one. Whether mtime can be set on a given Android path is verified on the device early in development; the archive rule above keeps the engine correct either way.

## 4. Replica access

### 4.1 Location resolution
A location `user@host:path` is resolved before the run. If `host` is `localhost`, an address of this machine, or absent, the agent runs **in-process**. Otherwise the agent runs as a **remote process**. Both cases use the same `Agent` interface; the caller does not know which one it got.

A location written with a scheme — `ssh://`, `unix://`, or `peer://` (§2) — is **remote by declaration**, and no address is consulted for it. Inference is what the form opts out of: a config alias can point anywhere, including back at this machine, and a unix socket, a `.host` name, or a device name has no address to compare at all — there is nothing honest to guess with. Asking `ssh -G <destination>` what ssh itself resolved was the alternative considered; it was rejected as a process spawn and a second parser per remote side that still could not answer for the shapes that motivated the form. It also follows that reaching *this* machine through its own `ssh` is a thing a user can ask for, rather than something quietly turned back into an in-process run.

### 4.2 Remote agent
The channel is a bidirectional byte stream — a `Transport`, any `AsyncRead + AsyncWrite` pair (`native/core/src/transport.rs`) — and the same protocol runs over every one. Two exist here; a third, authenticated one is §4.4's.

**Over ssh.**
- The same binary is installed on the remote host and started as `dsync agent --stdio` over `ssh`, by spawning the system `ssh` executable. That session serves exactly one replica and ends when its input closes.
- The destination is handed to `ssh` exactly as the location gave it and is never resolved, rewritten, or probed here. Whatever `ssh` accepts as its destination argument, dsync addresses.

**Over a socket.** `dsync agent --listen <socket path>` binds a unix socket and serves it, reached by a `unix://` location (§2). It is dsync's own transport: no system binary, which is what a head that cannot rely on one needs (§3, §16), and the read loop and buffering are this project's to tune rather than a borrowed library's.
- A listener outlives a session. It stays up, accepting until the process is signalled, and serves connections concurrently — one `ReplicaServer` per connection, which holds no state between them. Two sessions against the *same* replica are already handled by §4.3's lock; two against different replicas have nothing to contend over. A session that fails is reported and closed; it does not take the listener down, unlike `--stdio`, where the process *is* the session.
- The socket file is unlinked when the listener closes. One left behind by an agent that was killed outright is cleared on the next start, after connecting to it proves nothing is listening there.
- **It authenticates nobody, and neither does ssh, and neither needs to (task 83800f).** `hello` names the root path and the agent is rooted wherever it says. Over ssh that is harmless because the connection was already authenticated as that user before this protocol ever saw a byte. Over this socket it is harmless because the only gate is the filesystem: on Linux, a connect is refused if the process cannot open the socket, which is why this transport is unix-domain and local by construction. Neither transport requires the pairing §4.4 defines, and that is a decision, not an accident of which code path got touched first: ssh already vouches for the peer, so a second authentication step under `hello` would be authenticating a connection that is already authenticated; and this socket is local by construction, where the filesystem is a real gate, so requiring pairing on top of it would be friction against no threat and would make `dsync agent --listen` useless for a same-machine sync — the plain case the pairing umbrella (589b90) leaves alone. Pairing is what stands in for both of those once a socket leaves the machine, where the connection is no longer already-authenticated the way ssh's is and there is no filesystem to gate it the way this one's is. §4.4 now gives that replacement — authentication and the encryption TLS carries with it — a full design: a self-signed certificate pinned per device, checked at the transport handshake, plus what a paired device may reach once it is on the wire. That transport is `dsync agent --serve` (§11.1), reached by a `peer://` location (§2).
- Two things about a remote replica are configurable **per replica**, since SPEC §4.1 allows a pair of two remotes and two hosts need not agree on either: the **options** passed to `ssh` before the destination (`-p`, `-i`, `-o …`), and the **command** that starts the agent on the far side, which defaults to the bare word `dsync` resolved on the remote *non-interactive* PATH. Both come from the profile (§12) and the command line (§11.2). `~/.ssh/config` already answers port, identity, user and proxy command per destination and remains the better place for them; the options exist for what it cannot say, and for a one-off.
- **Protocol 3.0 (Rust; `native/core/src/wire.rs`, `version_handshake.rs`, `frame.rs`).** One multiplexed connection per replica session, over any `AsyncRead + AsyncWrite` transport (a `Transport`): stdio (an ssh child), a unix stream, or the `peer://` TLS stream (§4.4). Frame = a 9-byte header (1 byte kind + 4 byte big-endian request id + 4 byte big-endian length) + payload. Kind is one of `Version`, `Request`, `Reply`, `Chunk`, `End`, `Fail`, `Heartbeat`, `Credit`, `Cancel`. **Each kind has its own payload cap, checked from the header before a byte of the payload is read** (`Kind::max_payload_bytes`, task 197bdf): `Heartbeat` and `Cancel` 0, `Credit` 4, `Version` 1 KiB, `End` 4 KiB, `Fail` 64 KiB, `Chunk` 256 KiB (the body credit below: no chunk can be past it), `Request` 512 MiB, `Reply` 1 GiB. A length past its kind's cap is undecodable and ends the connection, and a writer refuses to encode such a frame rather than send it, so what a peer can make this end hold is one frame of its kind's cap per connection, and nothing is allocated up front at the announced length. `Reply` and `Request` stay large because a scan's listings are each one frame, not paged: a reply carries `Scan`, `Digests` or `Buckets` (a million-file tree's is a few tens of MiB), and `ScanDigests` carries the other side's changed paths — every path of a tree on its first sync, about half its scan reply. Before this, every kind shared one 512 MiB cap. `Request` and `Reply` payloads are **postcard**, not JSON — both ends are Rust, so there is no text format to keep human-readable on the wire, and postcard is smaller and cheaper to decode than JSON or the Dart protocol's hand-rolled binary scan encoding without a second format to maintain for it; `Chunk`/`End`/`Fail` carry a streamed body's raw bytes or its in-band failure (below). The kind byte is checked the instant it arrives, so a wire that is not speaking the protocol at all — a shell banner over an ssh connection whose remote command failed — is caught at once rather than by a decode failure deep in a payload, and is quoted back (up to 256 bytes) in the error rather than swallowed, because a banner is exactly what a human needs to see to fix the command. First exchange is a version handshake: each side sends an 8-byte magic (`dsync-rp`) plus its protocol version as two big-endian `u32`s, major then minor, and reads the other's. **The protocol version is 3.0**, versioned by §8.4's rule: a different major aborts the run with an error naming both versions (§11.5 exit 3), and the same major goes ahead, the session speaking the lower of the two minors wherever behaviour depends on it — nothing in 3.0 does yet. 3.0's `Write` request carries the source's whole scanned state, its hash included, which the far writer checks the landed bytes against (§7.2); 2.0's carried only its size, mtime and mode, and postcard would read a 2.0 request's later fields as the hash. 2.0 dropped the write-in-place marks (§7.6: the `Intent` and `Withdraw` commits, the untrusted statuses and their tally count, the `open` write stage) and took in 1.1's `Cancel` frame, which every session since 2.0 sends. That frame's layout is the one thing no major may change, since it is how two majors tell each other apart; a later minor may append to it, and a reader ignores what follows the minor. There is no compatibility story with the deleted Dart protocol to carry. Every request's paths and every domain value on the wire are typed newtypes that validate on decode (`RelPath` refuses `../x`, a glob that fails to parse refuses the request), so a malformed payload is refused before it reaches a replica rather than trusted as data.
- **A bounded request window, per-path order, and barriers (`request_window.rs`).** At most **48** operations are outstanding on one connection at once (`Tuning::request_window`): the apply's 40 read-ahead streams (§7.2), each of which holds a slot for its whole body on a remote source, plus a lead of eight so commits are never starved by them (task 447876) — pure scheduling, no I/O, tested with plain futures. Two operations on the same path never overlap and run in the order they were issued, which is what the write-then-commit ordering §7.3 rests on; a commit batch touches many paths, so it enters behind the last operation issued on *every* path in it. Operations on different paths overlap freely. `hello`, `lock`, `unlock`, `createRoot` (§4.5), all three phases of `scan`, `compact` and `removeEmptyDirs` are barriers: a barrier waits for every operation issued before it, then runs alone, and — unlike a plain per-path wait — holds every operation issued *after* it too, until it finishes. The first six are barriers because each changes what the whole replica means to the session; `removeEmptyDirs` earns it on its own, because it reaches ancestors of the path it is given (§7.5) and could remove a directory a concurrent write is about to write into (§7.5 keeps it out of the apply loop entirely, so in practice that barrier finds an empty window). A failed operation's reply comes back under its own id and fails only that caller; a connection failure — closed, or bytes that do not decode — fails every outstanding and every later operation, because nothing can be matched to anything any more (fatal, §11.5 exit 3). The far end dispatches requests concurrently as they arrive, but **at most its own `Tuning::request_window` of them are served at once per session** (task 890267): a served read holds a blocking thread until its body is over, so an unbounded server would let a peer that opens reads and never grants credit park every blocking thread the process has. A request past the bound is not refused but waits for a place, and the reader queues up to a window's more behind it before it stops reading — backpressure that stalls only the overrunning session. Refusing it as a protocol error would wrongly end honest sessions: the window is not negotiated (each side reads its own `Tuning`), and even with equal windows the server gives a place back only after it has queued the request's last frame, so a client that sees that frame can send its next request a moment before the place is free. The bound is per session; a process serving many sessions at once still holds up to the window's blocking threads for each.
- **A reader routes every frame the instant it is decoded and never stops reading on a body's account; each body is bounded by its sender's credit (`inbound.rs`, `credit.rs`, task ad44db).** A frame goes to its request's route at once; a route whose consumer is not yet taking frames — a served write queued for a writer, a read admitted ahead of a worker slot (§7.2) — keeps them queued in arrival order while every other route, every new request and every heartbeat carries on past it. What bounds that queue is the body's sender: every body may put **256 KiB** on the wire before any grant, and past that waits for `Credit` frames (id = the exchange, payload = a big-endian `u32` of bytes), which the receiver sends as its consumer takes the bytes, once half the allowance has been taken — so a body that fits in 128 KiB, most files, never costs one. The sender splits a chunk to fit its credit; a chunk past the credit is a protocol error that ends the connection; a receiver whose consumer dropped a body keeps granting while it drains the rest, and a write answered early stops sending even while it waits for credit. A **read** body its consumer drops also sends one `Cancel` (id = the exchange, empty payload), so the far end stops reading the file: it sees it at its next credit take, before its next chunk — even one waiting for credit — drops the body and ends the exchange with a `Fail` (`Interrupted`, "the reader cancelled this read"), always, since the receiver holds the read's window slot until that terminating frame: the far end has the file open until then, and per-path order should not let a write on that path start under it. A `Cancel` for a read no longer being sent — ended, never opened — is ignored; one from the server is a protocol error. `Cancel` is a frame, not a request: a request would take a window slot and an id of its own. Withholding credit instead would leave the far end holding the file open forever. The allowance is a protocol constant, not a tuning, because both ends must agree on it. What this end holds of bodies nobody is taking is therefore at most 256 KiB each, times the bodies open — which the initiator's window bounds (48). This replaced a connection-wide byte budget (1 MiB) the reader paused over: a budget shared by every route deadlocks as soon as the bodies filling it wait for a consumer that is itself waiting on frames behind them — the apply's read-ahead past its worker slots on a remote source, and its writes past the far side's writers on a remote destination (task ed9018, reproduced in `native/core/tests/it/run/flow.rs`). A per-route cap at the reader could not fix it, since a reader cannot know whose frame is next until it has read it; a cap the sender keeps can. The cost is one round trip's worth of stall for a single large body when 256 KiB is less than the link's bandwidth times its round trip (~50 MiB/s at 5 ms); the apply's many bodies in flight hide it.
- **Streamed bodies, for `Read` and `Write`.** A body is chunks of at least **64 KiB** (`Tuning::read_ahead_chunk_bytes`), ending in an explicit `End` frame; a body that fails part-way sends `Fail` in its place, with the `io::Error`'s kind and message, and the session keeps going — the failed operation's route drains and the rest of the connection is unaffected (SPEC §7.6 already asks a run to keep going past one failed action). A body's sender is a single type that both a local read and a connection can feed (`body.rs`): a body whose sender is dropped without finishing — a task that panicked, a connection that dropped mid-write — is a distinct `CutShort` error, never silently read as a complete-but-short file, so a torn transfer can never be committed as whole. **There is no write-cancel frame.** `Run::stop()` (§9's grace) lets an in-flight write finish and commit rather than aborting it mid-body; dropping a write's future early leaves the far side's write waiting for a body that stops arriving until the connection itself ends, so nothing here cancels a write mid-body — a run either lets it finish or ends the connection; either way the target holds the old file or the new one (§7.2).
- **Nagle is off on every peer:// socket** (`set_nodelay(true)`, both the dialer and the listener, and the enrolment channel of §4.4): the protocol is request-then-wait-for-reply with nothing queued behind an idle sender's flush, exactly the shape Nagle plus a peer's delayed ACK punishes. A unix socket is left alone, since `TCP_NODELAY` is a TCP option with nothing to set it on.
- **A bounded silence, on the transport that needs one.** `with_liveness` wraps a `Transport` with a heartbeat (`Tuning::heartbeat`, 5 s) sent by either end once it has sent nothing for that long, and a `SilenceLimit` (`Tuning::silence_limit`, 30 s) that fails the connection `PeerSilent` if nothing at all arrives for that long while this side is waiting to read. It is attached to the transports that cross a network — `peer://` (§4.4) and `ssh://`, on both ends: the initiator over the spawned `ssh`'s pipes and `dsync agent --stdio` over its own stdin and stdout (task 045cd1) — and not to `unix://`, whose peer is a process on this machine, so a dead one closes its socket and the reader gets EOF. Over a network nobody else is watching the link: the OS default keepalive is two hours, and a slept laptop, a dropped Wi-Fi or an expired NAT mapping would otherwise leave a run waiting forever with both replica locks held. `ssh`'s own `ServerAliveInterval` was considered for `ssh://` and rejected as the answer: it is off unless the user turns it on, and it only ever ends the client — the far agent sits under an `sshd` that keeps the session, and its lock, until its own TCP gives up. dsync's heartbeat ends both. On the initiator the silence limit is armed only once the version handshake is done: over ssh that handshake waits on ssh's own login, a password or a host key a person may take longer than the limit to answer; `peer://` bounds its handshake with `Tuning::handshake` instead.
- **A served session that loses its connection releases its replica in one order, and never wedges on the link it lost.** A session ends on a dead link the same way whatever noticed it — the reader failing (`PeerSilent`, an I/O error) or the server's owner cutting it (`ReplicaServer::serve_until`): first the reader returns, which stops every read body still being sent and ends every write body still arriving short, so its writer fails the write and removes its temp; then the writer task is aborted, dropping whatever frames were still queued for a link nothing will read again; then every request in flight is joined; and only then are the replica and its lock (§4.3) dropped. The writer is aborted because the outbox in front of it is bounded (16 frames) and a write to a black-holed TCP connection blocks once the kernel's send buffer fills, for as long as retransmission takes — many minutes — so a request sending a read's body would wait on that send, the session could not finish joining it, and the far side would hold both replica locks long past its own silence limit. The requests are joined, never aborted: a write's request waits for its writer to finish with the file before it returns, so joining them is what keeps the lock held until nothing of this session's is still touching the root. A client that closes its end cleanly still gets the orderly close: every reply flushed, then the write half shut down.
- **A `peer://` connection opens with a preamble, before the version frame, and its session can be reclaimed by the device that held it (`peer_preamble.rs`, `live_sessions.rs`, `peer_sessions.rs`, task 98e1a9).** Right after TLS, each end writes one frame and then reads the other's — the dialer a `Claim` (the session token it was issued on its last connection for the same device, entry and side, or none), the listener an `Issued` (this connection's token, 16 random bytes compared in constant time). A frame is the 8-byte magic `dsync-ps`, the preamble's own version as two big-endian `u32`s (**1.0**, versioned like the protocol: a different major is refused naming both, a later minor may append to a payload), a kind byte, a big-endian `u16` payload length and the payload. Both ends read it with exact reads on the raw TLS stream, never through a buffer, so the version frame that follows is left whole for the protocol's own reader. A listener's answer may also be preceded by any number of `Draining { queued }` frames (reserved; nothing sends one yet), each of which restarts the dialer's handshake bound — but the dialer waits for `Issued` at most `DRAINING_LIMIT`, 60 s from when it sent its claim, however many arrive, and past that fails the dial as `LinkError::StillDraining` (not a drop, so not re-dialled), so a paired listener cannot hold a dialer by draining forever; the version exchange that follows still gets the bound from the last `Draining`. The preamble is `peer://`'s alone: stdio and unix connections do not carry it, `ReplicaServer` never sees the token, and **the protocol does not move for it** — a `peer://` peer from before the preamble reads `dsync-ps` where it expects `dsync-rp` and is refused as not speaking the protocol, and this side refuses its version frame as no preamble. `PeerDialer::probe` speaks the preamble too, claiming nothing. The listener keeps `LiveSessions`, one registry per listener: each served session's token, the device it serves, and how to end it. A claim that names a live session **of the same device** ends that session (`ReplicaServer::serve_until`, in the order above) and waits for it to let go of its replica — at most `Tuning::reclaim_wait`, 5 s, which stays below `Tuning::handshake` because the listener sends its version frame only after the wait — before this connection is served. An unknown token, one whose session has ended, or another device's is ignored, with no reply that tells them apart. A token lives exactly as long as its session: the entry goes when the session ends, for any reason, so nothing outlives a restart on either end. The dialer keeps its tokens in `PeerSessions`, shared across attempts — one per CLI process, one per hub run session — and replaces a token only once a dial succeeds. This is what lets a re-dial after a dropped link, or the hub's fresh attempt when the app returns to the foreground, take over at once instead of meeting the dead session's lock until the far side's silence limit.
- **The initiator stops writing to a link whose reader failed (`remote_replica.rs`).** When the reader of a `RemoteReplica` ends on anything but a clean end of stream — `PeerSilent`, an I/O error, bytes that do not decode — its writer task is aborted, so a write whose body is stuck behind a full outbox on a dead path fails at the silence limit with the link's error instead of waiting out TCP's retransmission.
- Replica operations, as `Request` variants: `Hello`, `Lock`, `Unlock`, `CreateRoot`, `OpenScan`, `ScanDigests`, `ScanBuckets`, `Read` (streamed), `Write` (streamed, staged and renamed onto its target, sets mtime/mode), `Delete`, `RemoveEmptyDirs`, `Commit`, `Compact`. `Write` and `Delete` each carry what the initiator's scan saw at their path — a size and mtime, or nothing (`Precondition`, `dsync-domain`) — which the far side checks just before acting, refusing with `WireError::Changed` when it no longer holds; a `Read` body's `End` frame is not empty but carries what the far side's file was once its last byte was read (`OnDisk`), for the initiator to check against its scan before it ends the body it is writing (§7.6). Both are §7.6's check that a path has not changed since the scan, and the far side decides only the first: it acts, so it must check right before acting; the second is the initiator's to decide. The three scan requests are §6.1's phases and must reach one session in order, exactly as before: `OpenScan` walks the tree and the far side holds the paths it reports unchanged, which the other two ask about; a `ScanDigests` or `ScanBuckets` arriving first is a protocol-level refusal, not a fresh scan. A `Heartbeat` is not among them: it carries no id that means a request (`NO_REQUEST`, the same id the version frame uses) and has no reply.
- `Hello` carries the replica this connection should serve — `ReplicaSpec { root, kind, as_path, entry, side, jobs }`, its root **unexpanded** exactly as the location gave it, expanded once inside the handler that serves it — and replies with whether that replica's root exists and where its archive lives (§4.5's `RootFacts`), since the initiator cannot `stat` a remote host's filesystem. It reports nothing the archive holds: the archive is read only under the lock. `Lock` replies with that — the archive's last-commit time and the files it holds (`ArchiveFacts`) — from the one replay of the log a session makes, as it takes the lock; until then, and after `Unlock`, a scan, commit or compaction is refused (`ReplicaError::NotLocked`). `entry` is the pair's id (`EntryId`, §12; the field the wire already carried before entries existed, renamed along with the type). `kind` says whether this entry's root is a folder or one file (§6.2), and `as_path` is `Some` only for a file root — the one `RelPath` it syncs, side A's file name — `None` for a folder. A `hello` naming a root outside a `peer://` caller's granted set gets one generic refusal (`ReplicaError::Refused`, wire text `NOT_GRANTED`) before the filesystem is touched at all — missing, unreadable and simply-not-granted roots are not told apart on the wire, for the same reason §4.4 gives below.

**A file root accepts exactly its own `as_path`, whoever is asking.** `Root::locate` (`native/core/src/local_root.rs`) is where every `Read`, `Write`, `Delete`, `RemoveEmptyDirs` and `Commit` request resolves the `RelPath` it names to a filesystem path, and for a file root it refuses every path but `as_path` itself — a sibling, a path above or below it, anything with more than the one component the entry declared. This is independent of, and in addition to, §4.4's grant check: a device served only `/x/notes.md` cannot reach `/x/anything-else` merely by naming it in a request, whether or not that path would otherwise be granted, because the replica this session opened has no path but the one it was told to be.

### 4.3 Locking
Each agent takes a lock file in its state directory for the replica before scanning and releases it at exit. A held lock aborts the run with a fatal error. This is what makes a listener (§4.2) safe to serve concurrently: two sessions reaching for the same replica meet the same lock a second `dsync` process would.

**A reclaim happens before the new session's lock.** A `peer://` dialer that presents the token of its own live session (§4.2's preamble) has that session ended, and its locks dropped, before its connection is served — so its `Lock` finds the replica free instead of held by the session its dropped link left behind. The claim is honoured only from the device that session serves and only with its exact token: a claim from another device, or an unknown token, is ignored and that run meets the lock as before; a second run from the same device that was never issued the token — the CLI beside the app — still meets **lock held**.

**Two locks per replica: the entry's and the folder's (task 145a0f).** `<entryId>-<side>.lock` guards the archive, but an entry id hashes the pair as its initiator sees it (§12), so two runs over the same folder under different entries never met on it: two devices each starting a run at the other at once, or one folder synced through two entries, a cron job and the app running together. Each would see the other's writes as "changed during sync" (§7.6) and leave the result to the next run. So a run also takes `folder-<hash>.lock`, the first 16 bytes of the SHA-256 of the replica root's canonical path, in hex, in the state directory of the host the folder is on — taken on the initiating side for a local replica and on the serving side (`agent --serve`, `--listen`, `--stdio`, the app's Serve page) for a remote one, since every one of them locks through the same `LocalReplica::lock`. A second run on that folder is refused as **folder in use**, exit 3 like any held lock (§11.5), whatever its entry, with the folder named and the advice to run again when the other run finishes. `RunLocks` (`replica_lock.rs`) is the one place the order lives: the entry's lock first, so a repeat of the same run is still refused as that, then the folder's; they are released in reverse as it drops. Both use the mechanism below.

A root that does not exist yet (§4.5 creates it after the lock is taken) is keyed by its nearest existing ancestor, canonicalized, with the missing rest joined on lexically — which is the canonical path the folder has once the run creates it, since nothing below that ancestor existed to be a symlink. So a run holding a root it is about to create and a run arriving after it was created meet on the same lock. A single-file root's own file is keyed the same way — `canonical_root` works on a file path exactly as it does on a folder's.

**Two runs of the same profile started at once are not excluded either, and do not need to be.** Each entry's own locks are what one run's second attempt on an entry meets — refused as entry/folder in use — while the rest of that run's entries, the ones the other run is not also touching, still sync: safe, because each entry's own archive, locks and delete guard are its and its alone (§12).

**Nested roots do not exclude each other, across profiles.** A run on `~/Docs` and one on `~/Docs/Photos` from two different profiles (or two ad-hoc invocations) take different folder locks and proceed together. Excluding them would take a shared lock on every ancestor of every root, up to the filesystem root, on every run, in both the OS lock and the in-process registry, to catch a configuration someone set up on purpose, whose worst outcome is the one above: skips reported as changed during sync, settled by the next run. It is a documented limit instead — but only across profiles now: **within one profile, the same nesting is refused outright**, before any entry runs (`Profile::options`'s overlap check, §12), so `~/Docs` and `~/Docs/Photos` as two entries of one profile, or as one entry's own two sides, never reach this lock at all. The folder lock is also only as wide as the state directory: two agents given different `--state-dir`s (§11.2) do not see each other's folder locks, as they do not see each other's entry locks.

**Mechanism (`native/core/src/replica_lock.rs`).** An OS advisory lock — `flock(LOCK_EX | LOCK_NB)` on every unix target, including Android, where `std::fs::File::try_lock` itself is unsupported and returns `Unsupported` rather than taking the lock (fixed in task 538b18: a phone replica could not be locked at all until the switch to `libc::flock` directly); `LockFileEx` on Windows, through `std`. Nothing is written into the lock file, so a killed holder leaves no obstacle — the kernel releases the lock when the process's file descriptors close, whatever killed it. Alongside the OS lock, a process-local registry keyed by the replica's canonical path answers `ReplicaLockHeldException`-equivalents for a second holder *within* this process (the Flutter head, which runs its own sync in the same process as its UI, and `dsync archive clear`, §11.1): the OS lock alone is owned by the process, not the caller, so it would grant a second in-process holder the same lock its first holder still needs. The guard is RAII: dropping it releases the OS lock and then clears the registry entry, in that order, so an unlock that silently failed would never let the next in-process holder in while the file was still actually held.

### 4.4 Pairing and the authenticated transport
Extends §4.2's socket transport past the local machine (task 4ec17f, under the pairing umbrella 589b90). §4.2's unix socket gets its access control from the filesystem for free; a socket that leaves the machine has to build its own, and the requirement is the same one stated there — an unpaired peer must not reach the version handshake, `hello`, or any frame parser, not be turned away by one.

**Mutual TLS 1.3 with a self-signed certificate, via rustls, not Noise.** `native/core/src/peer_pin.rs`: rustls 0.23 on `ring`, TLS 1.3 only, client authentication required. Pinning is a custom verifier, `PeerPin`, implementing both rustls's `ServerCertVerifier` and `ClientCertVerifier` — one type serving both directions, since the check is the same either way: admit the certificate whose device id (SPKI hash, below) the pin names, one id or `ANY`, then check the handshake signature against it through `verify_tls13_signature` with `ring`'s algorithms. Pinning replaces chain building; it does not replace proof of the key. `PeerPin` is built fresh per connection — the listener's over the paired set it loads at that accept, the dialer's over the one device it dials — so a revocation or a new pairing applies on the very next connection, with nothing cached and no restart (§4.4's own point, now literally how the code is shaped). The alternative was still Noise (XX or KK) — a genuine second option, since `ring` already carries X25519, not a hand-written curve to avoid — and was not taken for the reason unchanged from the Dart design: the two failure modes are not symmetric. A broken certificate encoder is loud — a TLS library either completes a mutually-authenticated handshake with the bytes this project generated or refuses to load them, so a wrong certificate assembly cannot connect to anything, including a second copy of itself. A subtly wrong Noise handshake state machine has no equivalent gate: two copies of the same bug still complete a handshake with each other, and the failure is silent and security-relevant rather than a loud rejection. Put the security protocol in a TLS stack the world already attacks; keep a data-format problem — the certificate encoder — for this project to own. Custom verifiers bypass the library's own chain and date checks, so `PeerPin` checks `notBefore`/`notAfter` itself, in both directions, before it checks the key — a stranger is reported as a stranger, not as expired.

**The identity certificate.** `native/core/src/certificate.rs` / `device_identity.rs`: every peer generates one, once, and keeps it — an EC P-256 keypair through `rcgen`, assembled into a self-signed, **end-entity** certificate (`basicConstraints` with `cA: FALSE`; `keyUsage: digitalSignature`; extended key usage `serverAuth` + `clientAuth`). The Dart design's `cA: TRUE` and its subject `serialNumber` distinguisher existed for one reason that does not exist here: BoringSSL's trust store looked an issuer up by subject name and needed a CA-flagged, subject-unique anchor to pin a peer at all. rustls's custom `PeerPin` verifier (above) is not a trust-anchor store — it inspects the presented certificate directly, and `webpki` itself refuses to accept a CA-flagged certificate as a peer's leaf — so pinning an end-entity certificate is not merely permitted here, it is the only shape that verifies. The subject is the common name alone, with nothing appended to disambiguate it, because nothing needs to: pairing has never pinned the subject, only the public key (device id, below), and no lookup-by-subject collision is possible without a subject-keyed store to collide in. Validity is 3650 days, backdated one hour from the moment of generation, unchanged from the Dart design's numbers, for the same reason — two clocks that disagree by a few minutes should not read a brand-new certificate as not-yet-valid. The serial is 126 random bits from `ring`, fresh per issue (`rcgen`'s own default derives a serial from the key, which would make a renewal indistinguishable from the original at the one field meant to vary). The private key is written to `identity.key` at file mode 0600 — the temp file is opened at 0600 before any byte is written, rather than created loosely and chmod'd after, so there is no window where a partially-written key is world-readable — and the certificate to `identity.crt`, both PEM, both through the atomic-write helper (§8.2). It is renewed, never automatically, by `dsync pair renew`: the same private key, the same common name, a fresh random serial and validity window with the same backdating, so the device id below is unchanged and no peer has to pair again. `dsync pair list` and the run header warn on a certificate expiring inside a thirty-day window, for this host's own certificate and each paired peer's, the same as the Dart design; a handshake refused because a certificate has expired is reported as that, distinct from "no pairing" and "unreachable" below.

**Device id: SHA-256 of the certificate's `SubjectPublicKeyInfo`, hex, grouped.** `native/core/src/device_identity.rs` (`DeviceId::from_spki_der` in `dsync-domain`). Syncthing's shape is a hash of the device certificate, rendered for humans; the deliberate choice here is *what* gets hashed. Hashing the whole certificate DER ties the id to the serial number and the validity window, both freshly generated if a certificate is ever renewed under the same key — which would silently change a device's id out from under an otherwise-unchanged pairing. Hashing only the `SubjectPublicKeyInfo` ties the id to the one thing that cannot change without it actually being a different device. It is rendered as lowercase hex in 4-character groups (`a1b2:c3d4:…`, sixteen groups from the 32-byte hash) — long enough to print in a paired-device list and in `dsync pair`'s output, and grouped for the reason a hardware key fingerprint is: a human reading two of them side by side, or aloud, gets fixed points to check against instead of one 64-character run.

**The enrolment token, and what photographing the QR gets an attacker.** The QR carries three things: the desktop's certificate (or its DER — the trust anchor itself, and public by nature; there is nothing to protect by keeping it secret), two address hints — the enrolment endpoint this one pairing is redeemed against, and the serving address (`dsync agent --serve`) every connection after it dials — and a single-use, time-bounded enrolment token. On the wire (`dsync_domain::pairing_payload`) that is the text `dsync-pair:1.0:` followed by the base64 of `[u16 len][cert DER][u8 len][host][u16 port][u16 service port][u8 len][token]`; the token must be exactly 16 bytes, and the version is §8.4's: a payload of an older major is refused as "from an older dsync", a newer major as from a newer build — there is no attempt to read a foreign layout leniently — while a later minor of this one is read, what follows the token being its additions (in a payload of this build's own minor or older, nothing may follow it). The enrolment exchange the payload opens has no version of its own: the payload's major covers it. The phone scans it, connects once, presents the token as proof it saw the QR, and registers its own certificate as a paired device; the token is burned on that first successful use, regardless of whose connection redeemed it. An attacker who photographs the QR — over a shoulder, from a recording — gets exactly the three things a legitimate phone would, and *can* complete enrolment in the phone's place, provided they get there first and inside the token's window. What bounds that: the window is short, the token is single-use (so the real phone and an attacker cannot both succeed — whichever arrives second fails, which is at least a visible signal rather than a silent compromise), and the desktop's enrolment endpoint is off by default and open only for the duration of one pairing operation — a photograph used outside that window, or reused after the token inside it is burned, gets nothing. This is a real cost against two-scan pairing, where the phone's identity also travels out of band and there is no token to steal at all; it is accepted because the same mechanism is what lets `dsync pair` (task bc68c7) work by exchanging text between two machines that both lack a camera, which two-scan pairing cannot do.

**The head reads that QR, and the declarations stop where the scan does (task 57da0f).** The `app` head takes the payload either way: pasted in as the `dsync-pair:1.0:` line, or scanned off the symbol `dsync pair show` renders on stderr. Both end in one place — `PairController.codeEntered`, which decodes the payload and checks the version — and neither sends anything. **A scan is an input, not a confirmation.** The camera lives on a route of its own that closes on the first code it reads and hands the text back; the Pair page then shows what that code *says* — which device it names, and the address it will be reached at — above the one editable name (what *this* device will call it; what it calls this device is its own choice, made where it showed the payload), and `PairController.submitPayload` runs only when the user presses the button. The base64 line itself is never displayed: it cannot be checked by reading it, and the card says the two things about it a person can actually check. This is what makes the single-use token safe to point a camera at without a guard on the page: `MobileScanner` reports every frame the code stays in view, but reading a frame does no I/O, and the route is gone after the first one — where a page that redeemed on sight would burn the token on frame one and then show "the desktop refused this pairing", the far end's answer to frame two, over a pairing that had in fact just succeeded. Every failure of the exchange is still mapped to its own rendered line by `submitPayload`, and a text that is not a payload at all is answered before any of that, where the code is read. The reader is `mobile_scanner` — the *decoder*, against the `qr` pin that *encodes* the symbol the CLI prints; neither replaces the other, and the CLI links neither. The permissions declared are exactly what that scan uses and nothing more: `CAMERA` in `android/app/src/main/AndroidManifest.xml` and `NSCameraUsageDescription` in `ios/Runner/Info.plist`. A scan of an address the user showed the camera is an outbound TCP connection to a literal host and port, so neither `NSLocalNetworkUsageDescription` nor a `_dsync._tcp` Bonjour entry is declared: iOS asks for local-network access to *discover* and *advertise* peers, not to connect to one it was told about, and a speculative entry is a prompt the user is asked for nothing. The Android release manifest also declares `INTERNET`: Flutter gives it only to the `debug` and `profile` source sets, so until the main manifest had it, every network connect the head made worked in development and failed in a release build. It also declares `MANAGE_EXTERNAL_STORAGE`, for a replica root the user picks outside the app's own container: the directory picker's grant covers the `content://` tree URI it hands back, not the path that URI converts to, and the scanner and `LocalReplica` are plain `std::fs` — they open paths — so on targetSdk 30+ All-files access is what makes such a folder readable and writable at all. It is the one permission here granted on a Settings screen rather than a dialog, so it is asked for explicitly and a refusal is not fatal: the app-private documents directory remains a replica root that needs no grant.

**Confirming a pairing out of band is the user's tool, not the protocol's.** Pinning answers "is this the same key as last time" on every connection, and answers it without anyone's help. The one question it cannot answer is whether the key pinned at pairing time is the key the *intended* device holds: a payload carried by QR was read off the peer's own screen and there is nothing to doubt, but the text form of the same payload (above) exists precisely so it can be relayed to a headless server through some channel dsync knows nothing about, and a middle that sees it can redeem the token first and be pinned in the intended device's place. The enrolment token being single-use makes that visible — the legitimate enrolment then fails — but visible is not the same as ruled out. So the store carries one optional field per device: the device id the user says they compared, out of band, against the id that device shows on its own screen, and when they compared it. Nothing in the protocol reads it. No connection is gated on it, no run consults it, and a device that carries it is not trusted one degree more than one that does not — it is metadata about a human act, kept because that act is the only thing that can establish what pinning cannot. It is stored as the id that was compared rather than as a flag, so that it stops applying by itself when the key moves: a certificate renewal keeps the key and keeps the confirmation, while a pairing thrown away and redone against a different device produces a different id and inherits nothing. It does not expire — nothing about a pinned key changes on its own over time, so a confirmation that lapsed into "check me again" would be asking for a ritual with no question behind it, and would train the user to click through the one prompt that matters. Un-confirmed is the ordinary state and is shown as nothing at all: no warning, no badge, no empty slot where a mark would go. A user who never uses this is not doing anything wrong, and a pairing that nagged about it would be reporting a choice as a defect.

**Revocation is local, not a network operation.** `dsync pair revoke` removes a device's certificate from the paired-device store (§8.3's state directory) on whichever side it is run on; that side stops pinning the removed certificate's key, so the next connection attempt from it fails the same TLS verification a stranger's would. No message is sent to the revoked device — sending one would mean trusting a channel to a peer this side has just decided not to trust, the same contradiction §4.2 and the pairing umbrella rule out for an unpaired peer generally. A device unpaired while it was offline therefore learns nothing at the moment of revocation; it finds out the next time it tries to connect, when the handshake fails exactly as it would for a device that was never paired — no distinct "you have been removed" error, because producing one needs the trust the revocation just withdrew. Unpairing is consequently one-sided by construction: running it on the desktop stops the desktop from trusting the phone, but the phone's own store still trusts the desktop until the phone — or someone with access to it — removes that entry too. A user who wants both directions severed runs it on both ends; nothing here does it for them.

**A pairing binds to agreed replicas, not the account (task 83800f).** Trusting a device's certificate, above, answers *who*; it says nothing about *what*. Over §4.2's unix socket, `hello` naming any root is contained by filesystem permissions — the agent can only ever be rooted somewhere its own user could already reach, so there is nothing further to decide. That containment is gone once a peer is reached over the network transport this section extends to: "paired" taken literally would mean a paired phone can read, write and delete anywhere the agent's user can reach, not the one folder anyone meant to sync. So pairing a device's identity and authorizing it for a replica are two different acts, not one. The agreed set — the resolved, expanded root paths (the same expansion `ReplicaSpec::expanded_root` and `Location::expanded_path` apply at every other edge that must agree with it) a given device id may serve — is recorded per device in the paired-device store, alongside the certificate pin this section already keeps there (§8.3's state directory). Granting it is a local operation on this host, by the same hand and for the same reason `dsync pair revoke` is one: nothing a peer sends over the wire can add to its own entry, because a device that could grant itself access to a new path by merely asking for it would make the allowlist decorative. Pairing a device and authorizing it for a path are consequently always two steps, two commands: `dsync pair accept` (or `show`) records the identity, `dsync pair grant` adds a root to that device's agreed set (stored as `Location::parse(..).expanded_path(home)`, the same expansion the listener compares a peer's requested root against byte for byte), and both write the same paired-device store (`native/core/src/paired_device_store.rs`).

**A grant can name a single file as well as a folder, and a device's own grants may never nest (task ceba30).** `serves_root`'s exact-string membership does not care which kind of root a grant names, so granting a file needs no change there; what changes is `PairedDevice::grant`, which now refuses a new grant that would, once resolved on this host, lie inside an existing one, contain it, or turn out to name the very place an existing grant already names under a different spelling (`GrantNests`, naming both) — a device already granted `/sdcard/Docs` cannot also be granted `/sdcard` or `/sdcard/Docs/Notes`, since either would let it reach through one grant what the other was meant to bound. Re-granting the identical stored string is a no-op, not a refusal. The comparison resolves both paths (`dsync pair grant` and the hub's own grant flow both resolve *inside* the store's `update` closure, so a concurrent grant cannot race past the check) precisely so that two different spellings of one place — `/sdcard/Docs` and a symlinked `/mnt/sdcard/Docs`, say — are caught as the same grant; what is actually stored, and what `serves_root` still matches byte for byte, is the typed string, unresolved.

**Paths can move after granting, so `hello` checks the device's whole granted set again, once its named root has already passed the check above.** A folder renamed into another folder already granted to the same device would otherwise nest silently between the moment it was granted and the next sync it is part of. So a `hello` for a root that *is* granted gets a second, distinct refusal — `ReplicaError::Refused`, wire text `GRANTS_NEST` — if resolving that device's grants now finds any two of them nesting; a root that failed the first check (`NOT_GRANTED`) never reaches this one, so `GRANTS_NEST` says nothing about a path that was never granted at all. This is decision 2's "re-check at run start" for the far side of a `peer://` entry — the near side gets its own resolved re-check from `ProfileRun` before any entry starts (§12) — and it is what stands in for that check on a device whose filesystem this host does not control.

The app head has both steps, and the second one only ever writes this host's own store: its Pair page is `dsync pair accept` with the payload pasted or scanned, and its Device page is `dsync pair grant` and its withdrawal against the store *this* installation keeps. That is not a weakening of the rule above, because the rule is about *whose* store a grant lands in, not which head writes it: nothing a peer sends can still reach its own entry, and a phone granting a path grants it in the phone's store, which is the store that phone's own Serve page enforces when a paired device dials it (§16). The case that makes it worth having is the desktop head, which shares the CLI's state directory (§3): there the grant lands in exactly the file `dsync agent` enforces, and the user who paired a device in the app can authorize it there too instead of switching to a terminal to run `dsync pair grant`. The earlier version of this paragraph ruled the second step out of the head entirely, on the reasoning that the head was a phone; that reasoning does not survive the head running on the machine that serves.

**The refusal does not confirm what it refused.** A `hello` naming a root outside the calling device's agreed set gets `ReplicaError::Refused` (wire text `NOT_GRANTED`), the same reply shape every other rejected operation already gets. Its wording has to do one thing carefully: not let the caller distinguish "that path does not exist," "this agent could not read it," and "it exists and is readable but is simply not on your list" — three different facts that, told apart, would let a paired-but-curious device map the host's filesystem one refusal at a time. All three collapse to the one answer a peer with no business asking gets.

**`hello` stays client-named; the allowlist is a property of the session, not the protocol.** The alternative — a pairing names the replica, and `hello` selects it by id instead of by path — was considered and rejected. It removes this class of question by construction, but ssh and the unix socket have no pairing at all (§4.2), so there would be no id for either of them to select by: `hello` would need two modes, or the core would need a replica registry that exists independently of pairing, either of which is a much larger change than the wire already affords (§4.2's protocol version exists exactly to cover a change like this, cheaply, whenever it is needed). `hello` keeps naming a root path, exactly as it does today, on every transport.

What changes is where the check happens. `ReplicaServer::new` takes `open` as `impl Fn(ReplicaSpec) -> impl Future<Output = Result<R: Replica, ReplicaError>>`, and that signature does not change across transports — `Transport`, `ReplicaSpec`, `ReplicaServer` and everything else under `native/core/src/replica_server.rs` stay exactly as they are, because none of them is where a peer's identity is known. The transport is. Giving `open` itself a `peer` parameter was the other shape considered, and rejected for teaching that concept to code that should not need it: `ReplicaServer`, and the plain `open` that `--stdio` and `--listen` already supply, would all have to carry a parameter that means nothing on those two transports, for the sake of the one transport where it does. Instead, the `peer://` listener (`peer_listener.rs`) performs the TLS accept and reads the peer's certificate before `ReplicaServer::serve` is ever called for that connection — `--stdio` and `--listen` keep calling the head's `open` unwrapped, since there is nothing to check where §4.2 already decided there is nothing paired to check against. It performs that accept itself, per connection, rather than trusting a certificate loaded once at bind time: for each connection accepted it re-reads the paired-device store as it is at that moment and builds `PeerPin` from it, then upgrades under the handshake deadline (below). The trust anchors are therefore never older than the connection they gate — a device paired, granted or revoked while the agent is serving is honoured on its next attempt, with no restart and no rebinding; a session already in flight holds its own upgraded socket and is untouched — for the price of one store read per accept, which at this transport's connection rate is negligible. A handshake that fails is that one connection dropped and reported, never the listener. The listener then wraps `open`: it resolves the pinned certificate to a device id, looks up that device's agreed roots in the paired-device store, and hands `ReplicaServer` a connection-scoped closure that checks a `ReplicaSpec`'s expanded root against that set — refusing before the filesystem is touched, `NOT_GRANTED`, above — before delegating to the head's own `open` for the roots it permits.

**The grants are the bound on the links a served replica goes through (task 278aae).** The initiator sends its whole `RuleSet` in `OpenScan`, and a served replica used to scan by it, then write through whatever links it named (§5.1) — so a device granted `~/Sync` could send `follow **` and read or overwrite anything a link under `~/Sync` points to, which made a grant a starting point rather than a bound. On a replica served to a paired peer (`dsync agent --serve`, the head's Serve page) a link is therefore gone through only when both hold: the peer's `follow` rules ask for it, and its fully resolved real target — links in the folders above it resolved too — lies inside one of the folders granted to that peer (`PairedDevice::granted_roots`), compared by path components, so a grant of `/a/b` does not reach `/a/bc`. The grants are resolved too, so a grant reached through a link of the owner's own (`/sdcard` on Android) compares with the resolved targets. To sync a folder reached through a link, the owner grants the target folder as well; granting it means it is reachable, so that peer may also sync it directly. There is no other configuration — no follow list on a grant, no serve flag. The listener is where the peer is known, so it hands its factory the bound beside the spec: the factory `PeerListener` takes is `Fn(ReplicaSpec, Symlinks)`, and each connection's closure passes `Symlinks::WithinGrants` of that device's grants as read at accept; `ReplicaServer`'s own `open` is unchanged. `LocalReplica::open` takes the `Symlinks` (`native/core/src/symlinks.rs`, the containment itself in `native/core/src/granted_roots.rs`); local, ssh and `unix://` replicas pass `AsRuled`, where whoever runs dsync owns both ends and the run's own rules decide, as before. A followed link out of every grant is skipped by the scan and reported like any skipped link (§5.1). Because a peer can send `Read`, `Write`, `Delete` or `RemoveEmptyDirs` for any path without scanning first, each of those checks the path too (`native/core/src/confinement.rs`: an `lstat` per path component, each link on the way resolved and held to the grants, remembered per folder for the session so a folder is looked at once, not once per file); a link out of the grants, or one that does not resolve, at the path or in a folder above it, refuses that one path — a `Write` failure at the probe stage, or a `File` failure for the other three — never the run, and nothing outside is read or written. The folder lock (§4.3) covers the run's root, not a granted folder reached through a link from it: a run on that folder directly and one through the link proceed together, with the nested-roots outcome — skips reported as changed during sync, settled by the next run.

**What bounds an unauthenticated connection.** Until a peer has authenticated it can cost this host a descriptor and a TLS session, so the pre-authentication phase is bounded at both listeners (`peer_listener.rs`, `enrolment_listener.rs`) by two deadlines and two caps, one implementation of the caps shared by both (`unauthenticated_slots.rs`). A slot is taken in the accept loop, in accept order — so the connection *over* a cap is the one dropped, before any task or TLS work runs for it, and without taking a slot itself — and held until the session begins or the connection is turned away. At most `Tuning::unauthenticated_connections` (**16**) connections hold one at once, and at most `Tuning::unauthenticated_per_address` (**4**) of those from one address (an IPv4 peer over a dual-stack socket counted as its IPv4 address). The connection must deliver its whole TLS ClientHello within `Tuning::client_hello` (**3 s**) of the handshake starting — a dialer sends it the moment it connects, so a socket silent that long is idle and gives its slot back early — and finish the handshake (and, on the enrolment listener, the request read) within `Tuning::handshake` (**10 s**), the hello's deadline running inside it. In `tokio` both are plain `tokio::time::timeout`s, the hello's around rustls's `LazyConfigAcceptor` — there is no SDK gap here to build a bounded-handshake wrapper against, unlike the Dart design's `dart:io`, whose `SecureSocket` API left the accepting listener no handle to end a stalled handshake with. One global cap, not one per phase: a connection is counted from accept and covers the upgrade and the request read together, so one legitimate peer is one slot whichever side of the handshake it is in. The per-address cap was first rejected — a rate limiter needs a key, per-IP is wrong behind NAT and for an IPv6 /64, and its table is a memory-growth vector — and then taken (task 1fc302), because without it a single host on the LAN holding 16 idle connections, renewed every 10 s, blocked every paired device and every enrolment without authenticating. It is a cap on concurrent slots, not a rate limiter, so the objections mostly fall away: its table holds only addresses with a slot taken, never more entries than the global cap, and remembers no past peer. The accepted costs: peers behind one NAT share 4 slots between them (a legitimate dial over the cap is refused at once, not queued); an attacker with many addresses — an IPv6 host can take a /64 of them — is held back only by the global cap; and one that sends a hello and then stalls still holds a slot for the full 10 s, so the pairing window stays blockable by such a host at roughly 1.6 connects/second sustained. Genuine per-source rate limiting still belongs in an L4 passthrough proxy, which knows the address and whose policy it is.

**No HTTP reverse proxy can front this listener.** This follows from pinning rather than from any deployment choice, which is why it is here and not only in the README. The authenticated fact is "the peer on *this socket* presented key X", read off the peer's certificate at accept; terminating TLS destroys it, and nothing restores it downstream — the proxy holds no private key to present onward, and a header asserting the device id is only the proxy's word for it. The one front that works is L4 passthrough — nginx `stream`, haproxy `mode tcp` — which forwards TCP bytes and terminates nothing, so the mutual handshake still runs end to end between the two paired devices. That is the same layer the paragraph above puts genuine per-source rate limiting in, and for the same reason: it is where the address is known and whose policy it is.

**Addressing a paired peer: a name, not a host (task b1ab09).** A `peer://` location (§2) names a device, not an address — resolved through the paired-device store (§8.3), the same store that already holds the certificate pin and the agreed roots, above. The alternative was a location self-contained the way `ssh://` and `unix://` are — `peer://host:port/replica-path` or similar — and it was rejected because the thing it would bake into a profile is exactly the thing pairing already has to track and that changes on its own: a phone's address differs between one sync and the next far more often than its identity does, so writing it into a profile (§12) means writing down something that rots before the profile is read a second time, while a device's *name* is stable for as long as the pairing is. The cost is real and is not hidden by the convenience: a `peer://` location is no longer self-contained the way the other three forms are. The same profile, unchanged, does not work on a machine that has not paired with the named device — and unlike `ssh://`, where `~/.ssh/config` is at least a separate, portable, human-editable file that can be copied alongside the profile to make it work, there is no file to copy here; the paired-device store is this host's own record of a mutual trust exchange, and trust is not something a `cp` can extend to a machine that was never party to it. A run that meets a `peer://` name with no entry in the store fails before it opens a socket, with an error that names the device and points at `dsync pair` (`bc68c7`) — the same "caught while still harmless" property §11.4 already gives a mistyped location, not a hang or a generic connection failure.

**Where the name comes from, and what constrains it.** The name is local: this host's own label for that peer, chosen at pairing time, the way a `~/.ssh/config` `Host` alias is chosen by whoever writes the file rather than agreed with the far end. The two sides of a pairing need not call each other the same thing, and nothing here makes them try. It must be unique within this host's paired set — the store enforces it, the same way it already has to enforce that one device id maps to one entry — and a pairing that would collide with an existing name is rejected at pairing time, not silently disambiguated with a suffix: the operator picks a different name and pairs again. A device name is a handle for humans and for locations; the device id (above) is the cryptographic truth and what actually gets pinned.

**Each side names its peer, and the enrolment request carries no name at all (task 736fdb).** The paragraph above says the name is local — this host's own label, chosen the way a `~/.ssh/config` `Host` alias is. An earlier shape contradicted that outright: the enrolment request carried a name the device being enrolled proposed for itself, and the listener stored it verbatim. So the name is now chosen by the side that *shows* the payload — `dsync pair show --name <name>`, and the head's own code page asks for it before it binds anything — and the request carries a token, a certificate and the port the enrolling device serves on, and nothing else. It is required on both sides and defaulted on neither. Making the code match this section's own model is the first reason; the second is that the name is not a display label but the handle a human types to authorize data access (`dsync pair grant <name> <root>`, `peer://<name>`), and the collision rule above rejects a duplicate outright, so a peer that can choose it can squat on or collide with a name this host meant for something else — a hazard that has nothing to do with a race, and that a peer which paired legitimately and was later compromised would still have. The third is narrower and still worth having: one less attacker-controlled string is parsed and stored before the peer has authenticated anything.

**This does not close the leaked-payload race, and no naming rule can — the showing side confirms the device instead (task 23344d).** An attacker who redeems a leaked payload first is recorded under the name the operator typed for that session — which is the name the operator meant for their *own* device, so a later `dsync pair grant <that name> <root>` would grant the attacker. The name cannot catch this, because at the moment it is chosen nobody has connected yet and there is nothing to tell apart. What catches it is a confirmation on the side that showed the payload, before anything is stored: the enrolment listener redeems the token, validates the certificate, derives the device id from it, and then puts that id in front of whoever is standing there — against the id the intended device shows on its own screen — and writes the paired-device store only if they say yes. That is the same grouped-hex comparison the out-of-band confirmation field above describes ("Confirming a pairing out of band is the user's tool, not the protocol's"), moved to the one moment where it can still prevent rather than merely detect: a won race becomes a declined prompt and a fresh payload, not a trusted stranger in the store waiting to be noticed and revoked. It matters that this is before the store write rather than gating `dsync pair grant`: a stored-but-ungranted device is trusted enough to pass the handshake, resolve as a peer, and exercise `hello` and the frame parsers with every request refused — surface a stranger does not otherwise reach — and gating the grant would also reverse this section's position that nothing in the protocol is gated on the confirmation *field*, which stays true: the field is still metadata about a human act that no connection consults. Nothing on the wire changes; the enrolment request already gets exactly one reply, and the socket simply stays open across the wait, which is bounded by the token's own expiry — a window that closes with nobody answering refuses, the same as a decline. The token stays burned through either outcome, so a decline means the operator shows a fresh payload rather than getting another attempt at the old one. The cost, stated: pairing is two-sided. `dsync pair show` now prompts on stdin and refuses to start without a terminal behind it, and a pairing window left open on a device nobody is at no longer completes on its own. The camera-less desktop-to-server case this section calls primary still works — two terminals, four groups of hex compared by eye. The single-use token remains what makes the race *visible*; this confirmation is what settles which of the two devices is trusted, and settles it before either is.

A location resolves a name to whatever certificate the store currently holds for it, which is the entire point of the indirection: a device re-paired under a new certificate — a phone wiped and set up again, say — keeps the same name, and the same locations keep working once the operator has re-paired it, without editing a single profile.

**Discovery: a last-known-address cache, refreshed on every connection.** The QR (above) carries the serving address, so the first connection needs no discovery at all. The other direction is the enrolment request's: the enrolling device sends the port it serves `peer://` on (`dsync pair accept --serve-port`, the head's Peer port setting; the port it *would* serve on if it does not serve yet), and the listener records it at the address the request connected from, on that port, rather than assuming 28771 for a device that may serve elsewhere. A port of 0 does not decode, so such a request is refused as malformed before the token is spent. That address is carried in its own right rather than reused from the enrolment endpoint the payload was redeemed against: the enrolment listener is one-shot and bound on an ephemeral port, so seeding the cache from it would store an address guaranteed not to answer, and the user would have to re-enter the port by hand before the first sync could run. The second is answered by a field in the paired-device store: the address a connection to that device last succeeded at, overwritten on every successful connection and read back as the address to try next time. mDNS was considered and set aside (§16) rather than taken: it is not a small addition to reach for — a dependency, a multicast socket, an Android multicast lock, an iOS entitlement — and it does not cross subnets, which is precisely the desktop-to-server shape this product's other pairing case needs. The cache costs one field and a write on every successful connect, and it covers the case that actually dominates: a desktop's address is close to static, and even a phone's is often stable for the length of a sync session on one wifi network. When the cached address is wrong, the escape hatch is manual re-entry — the operator supplies an address the same way the QR supplied one the first time — not a background scan for the device. A connection attempt against a stale cached address does not hang waiting for a socket that will never answer: it is bounded, fails, and reports failure against the address it actually tried and the device name it was trying to reach — distinct in the error text from the "no such pairing" case above. "No pairing for `<device name>`" means dsync never had a certificate to trust in the first place; "could not reach `<device name>` at its last known address `<address>`" means the store trusts it and the address it holds did not work this time, which is the signal that a manual re-entry is what is needed next.

**The port: 28771, fixed, configurable on the listener.** A `peer://` location carries no port of its own — the store's cached address does, alongside the host, since a client never assumes one. The listener's own port defaults to a single fixed value, configurable the way `--listen <socket path>` already takes its socket path as an argument, so the common case of one dsync agent per host needs no configuration at all, and two agents sharing a host stay expressible by giving the second a different port. Negotiation was not considered seriously: there is nothing to negotiate a port over before a connection exists to negotiate on. 28771 is unprivileged — Linux's privileged range ends at 1024, and a listener should not need root — and sits in the registered/user range rather than the ephemeral one (49152–65535) the OS hands out to outgoing connections, which a fixed listening default has no business colliding with. It is also not a port dsync is likely to share with anything else already running on the same host: not ssh's 22, not a dev server's 8080/3000/8000, not Syncthing's 22000/21027/8384 — prior art this design already leans on (above) and that may well be installed alongside it.

### 4.5 A root that is not there
An entry's root can be missing when a run starts — a folder, or, for a file entry (§6.2), the file itself. A grant (§4.4) authorizes a path, not a folder that exists, and the phone's Shared folders dialog deliberately accepts one that has not been created yet — a release build has no other way to make a folder in app-private storage. Missing can also mean an SD card or drive that is not mounted, or a folder the user deleted.

**`hello`'s reply names which of five things is true of the root** (`ReplicaRoot`, `dsync-domain`): `Present`; `Missing` — a folder root's own folder is not there; `ParentMissing { folder }` — a file root's folder is not there; `WrongKind { expected }` — something other than the entry's declared kind sits at the root, a folder where the entry syncs one file or anything but a folder where it syncs a folder; or `Unreadable { reason }` — looking at the root failed, so whether it is there is unknown. A file root whose folder exists is `Present` whether or not the file itself is there: an absent file answers no question a folder-shaped root asks, and §6 already knows what an entry reporting nothing at a path means.

**Only "not found" is missing (task 29f697).** `Missing`, `ParentMissing` and a file root's absent file are each read from an `ENOENT` (`io::ErrorKind::NotFound`) and nothing else. Any other failure to `stat` the root, a file root's folder or its file — a permission denied on a folder above it, an I/O error from a failing or half-unmounted drive — is `Unreadable`, carrying the OS's own error text as `reason`. Read as missing, it would get the wrong message with an archive and, without one, a `CreateRoot` aimed at a path dsync cannot even look at.

**The rule for a folder root: created on that replica's first sync, and refused once it has an archive.** Scanning an absent folder against an empty archive finds nothing and asks for nothing to be deleted, so an empty folder is exactly what a first sync expects, and the run creates it and goes on. Scanning it against an archive reports every archived file as deleted, and the run would propagate those deletions to the other replica — the wrong answer for an unmounted drive, and one that cannot be undone. So a folder replica whose archive exists and whose root is missing ends the run before anything is scanned, on either side, with a named failure rather than an exception string: *"The folder <path> on <device> is missing. If it is on a drive that is not mounted, reconnect it; the last sync saw N files there."* N is the number of files in that replica's archive.

"First sync" is judged per replica, by that replica's own archive: a replica with no archive has nothing to propagate as deleted, whatever the other side holds, so a phone reinstalled with its app data wiped gets its folder back and a fresh copy rather than a refusal it has no way to clear.

**The rule for a file root: `ParentMissing` is always refused, and its folder is never created, first sync or not.** dsync never creates the folder above a single file: a file entry names one path, not the folders above it, and a missing folder reads as an unmounted drive or a deleted folder far more often than as a folder nobody has made yet. The refusal names the folder rather than a file count, since a file entry only ever has the one file to have lost — *"The folder <folder>, which holds <path>, is missing. If it is on a drive that is not mounted, reconnect it; dsync does not create it."* A **relative** file path's folder is taken from the working-directory-resolved path, so a bare `notes.md` in the profile has folder `.`, checked the same way as any other.

**`WrongKind` is judged before either root is even locked.** `Run` (`native/core/src/run.rs`) checks both sides for it on the `hello` replies, before taking either lock — ahead of `must_create_root`'s judgement below, which runs only once both locks are held — so an entry whose kind does not match what is on disk is never locked, let alone written to. The message names what the entry expected: *"<path> is not a folder, but the entry syncs a folder there. Move what is there aside, or change the entry."*, or, the other way, *"<path> is a folder, but the entry syncs a single file there. Move the folder aside, or change the entry."*

**`Unreadable` is refused the same way, first sync or not, and never created.** `Run` checks it alongside `WrongKind` (`RootFacts::refused_before_lock`), before either lock, so a root nobody can look at is never locked, scanned or created whatever its archive holds. The message carries the OS error: *"dsync cannot tell whether <path> on <device> is there: <reason>. Check that it is mounted and readable; dsync does not create it."*

The same missing/parent-missing rule holds for every replica on every transport. `hello`'s reply (§4.2) tells the initiator the root's state and `lock`'s tells it the archive's, since it cannot `stat` a remote host's filesystem; `Run` judges both sides from those facts (`ReplicaInfo::must_create_root`, `dsync-domain`) once both locks are taken — each archive as its lock read it, so a run that committed between `hello` and `lock` is not missed — before creating either, so a refusal of one side leaves the other untouched too; and it then asks the replica to create the root with `CreateRoot` — never for a file root, which `must_create_root` always refuses instead. The replica reports and creates, and decides nothing. The failure is raised on the initiator, so it is the same typed `MissingReplicaRoot`, `MissingParentFolder`, `WrongRootKind` or `UnreadableReplicaRoot` error for a remote replica as for a local one; a profile's `ProfileRun` (§12) turns each into that entry's own `Skipped` outcome and moves on to the next entry rather than ending the profile.

**§4.4's refusal comes first.** A `hello` naming a root outside the calling device's agreed set is refused before an agent is built, so it never learns whether that root exists and nothing is created; existence is reported only for an authorized root.

**The app never creates a root itself.** Run setup used to create the local folder before every run; that would recreate an archived-but-missing folder empty — exactly the outcome the folder rule above refuses to allow — and would make a directory at a file entry's path. Whether and how to create a root is the core's decision alone (above); the head only ever picks the path.

## 5. Scan and change detection

Each agent scans its own replica and compares against **its own archive**. It returns a list of entries with a status relative to the archive, so the initiator never needs the full archive of the other side.

A path the scan cannot read — permission denied, or the entry vanished between the directory listing and the read — is **recorded and skipped, and the scan continues with the rest of the tree**, mirroring the per-path tolerance §7.6 gives the apply phase. One locked file does not cost the run. Such a path produces no status entry, for the same reason a skipped symlink does not (§5.1): a path the scan could not read has no state relative to the archive, so there is no cell of §6's table it belongs in. It is reported alongside skipped symlinks and contributes to the exit code (§11.5).

Archive entries beneath a directory whose listing failed are **not** reported `deleted`. The scan never got to look, so their absence from the walk is not evidence they are gone; reporting them would propagate a deletion the user never made to the other replica.

Silence is not enough on its own, though. An unreadable path is reported to reconciliation as well, and excluded there (§6) — because §6 reads a side's silence about a path as "this side has never seen it", which means *mirror it from the other side*. That is the right reading for a path that is genuinely absent and the wrong one for a path that is present and merely unread: it would overwrite a locally-edited file the scan could not look at, on a run that just said the path was not synced. An unreadable directory covers every path beneath it for this purpose, since the directory is what the scan reports but the files are what it hid.

The replica **root** is the exception: if the root itself cannot be listed, that is fatal (§11.5 exit 3), not a per-path skip. There is no tree left to sync, and reporting an empty one would invite mirroring the entire other replica into a directory this host cannot read.

### 5.1 What is scanned
- Regular files only. Directories are traversed but not tracked as entries.
- Symlinks: skipped and reported, unless the path matches a `follow` rule (§9), in which case the link is resolved and the target is treated as if it were at the link's path. A `follow` link that is broken, whose target is neither a regular file nor a directory, or that points back into a directory the walk is already inside, is also reported as skipped. Reported paths travel alongside the status list and surface as `symlink` lines (§11.4); they are not status entries, since a skipped link has no state relative to the archive to reconcile.
- **A skipped link's path is kept out of the plan, on both sides** (task 47cec1). A regular file on the other side at that path is not copied, and an archived file the user replaced with a link is not reported `deleted`; for a link to a directory, the same holds for every path beneath it. Planning around the link anyway wrote onto it: when copies wrote in place (task 58d609, since reverted), a copy onto an unfollowed link went *through* it, into a target the user never asked to sync, and a rename onto the link's path would replace the user's link with a file. It is the answer Unison gives for a link it does not sync — report the pair, propagate neither — and, like the link itself, not a failure (§11.5). Syncing a link *as* a link, its target string as its content, is not done: Android's shared storage cannot hold one, and Windows needs a privilege to create one (§9).
- **On a replica served to a paired peer, a followed link is gone through only when its resolved target lies inside a folder granted to that peer** (§4.4, task 278aae). One whose target is outside every grant is skipped and reported with the detail "target outside the folders granted to <peer>", and kept out of the plan on both sides like any skipped link: never deleted on the other side, never a failure. Local, ssh and `unix://` runs follow as their rules say.
- **A copy onto a followed link writes through it** (task 47cec1): the target's bytes change and the link stays a link, even when the target is outside the replica. That is what a `follow` rule says — the target stands at the link's path in both directions — and it is what Unison does. Replacing the link with a regular file, which a rename onto the link's own path would do, silently undoes the user's rule on the first copy from the other side; so the temp is renamed onto the link's resolved target instead (§7.2).
- Every reported path says *which* of those cases it was, not just that it was skipped. All four are one outcome to the tool — report it, plan nothing, leave the exit code alone — but not to the reader: a broken link and a link pointing back up its own tree need different fixes, and the walk is the only thing that ever knew which it saw.
- **Special files — a fifo, a socket, a block or character device — are skipped and reported, and their path kept out of the plan on both sides, exactly as a skipped link's is** (task 7b667b). They surface as `specialFile` lines (§11.4) whose detail names the kind. The walk used to drop them without a word, and the scan's silence then read an archived file the user replaced with a fifo as `deleted`, so the delete propagated to the other side; and a copy onto a fifo at the destination had nothing to stop it opening the fifo to write, which blocks until a reader turns up. There is no content to sync — a fifo's bytes are whatever its writer sends next, a device's are the device — so, like an unfollowed link, it is the tool obeying its rules and not a failure (§11.5).
- Unreadable paths: reported the same way, as `unreadable` lines (§11.4), carrying the OS's own reason — "permission denied" and "no such file or directory" are what tell a locked file apart from one that vanished mid-scan, and the latter is not there to inspect afterwards. Unlike a skipped symlink, which is the tool obeying §9's rules and happens identically on every run, an unreadable path is a failure and counts toward exit 1.
- Case-folding collisions (§16): on a replica whose filesystem folds case, two live paths — or a live path and an archived one — that fold to the same key are reported and excluded the same way an unreadable path is, rather than one silently overwriting the other, and count toward exit 1 (§11.5) for the same reason.
- Hardlinks: treated as independent regular files. A copy renames a new file onto this name rather than writing the shared bytes (§7.2), so the other names — inside the replica or out of it — keep what they had (task 6ac6ad). Nothing records which paths share an inode, so the other side receives them as separate files, as Unison does.
- Paths matching an `ignore` rule are not scanned.

### 5.2 Fast path
For each file, with archive entry `E`:
1. If `size` and `mtime` equal `E.size` and `E.mtime` → **unchanged**, no hash computed.
2. Otherwise compute the content hash.
   - Hash equals `E.hash` → **unchanged**; the archive entry's `size`/`mtime` are refreshed at commit.
   - Hash differs → **modified**, new hash reported.
3. File present, no archive entry → **created**, hash computed and reported.
4. Archive entry present, file absent → **deleted**.

Hash: SHA-256, via `ring`. Stat and hash both run on a pool of scoped OS threads sized to `jobs` (`native/core/src/scan_pool.rs`); parallelism is configurable, per §11.2's `--jobs`.

**A shared work queue, not a pre-split shard per worker.** The walk itself runs single-threaded, in walk order, building the candidate set §5.2's fast path could not settle by size and mtime alone; those candidates are then queued largest-first (a stable sort, so ties keep walk order) and each pool worker pulls the next one off a shared atomic counter as soon as it finishes the last, rather than being handed a pre-balanced share up front — a heavy file never leaves one worker still grinding through its shard while a lighter one sits idle. Each worker reads with its own reused 256 KiB buffer (the same size the writer side streams with, §7.2), so peak memory is one block per worker rather than per file or per shard. Results are slotted back into the walk's own order by index once every worker is done, whatever order the pool actually finished them in, so what §11.4 and the archive see never depends on scheduling. This is a materially different shape from an earlier isolate-per-shard design that does not apply here: OS threads share memory and a queue for free, where the Dart core's isolates could not, and there is no separate "run inline below a size threshold" case to reason about — a pool of `jobs` threads costs the same whether the tree is one file or a million.

`mtime` is stored as microseconds since epoch as returned by `FileStat`. Comparison is exact equality.

### 5.3 What a scan costs

**Historical note.** Before the Rust port, this section carried a long device-measurement ladder (Pixel 9a, Android, `dart:io`) pinning the walk and the per-file hash read as the two dominant costs of a scan on Android's emulated storage, plus a Dart-VM garbage-collector analysis of what a scan allocates and how capping the young-generation semispace moved it. None of that instrumentation exists in the Rust core — there is no VM, no semispace, no per-object allocation to profile the same way — so the numbers are cut rather than carried forward. The one behavioural rule they left behind, still true and still worth stating: **a file's type comes from the directory listing itself, never from a second lookup.** `native/core/src/scanner.rs` reads it off the walk's own directory entries; nothing re-`stat`s a path purely to ask what kind of entry it is. Phase 16's phone acceptance numbers (task 538b18) and their latest re-run (§17.1) are the Rust core's device measurements; nothing in this section reproduces the Dart ladder against the new implementation, because the two are not the same shape of cost to compare rung for rung.

The Rust scanner reads directory entries and stats with blocking `std::fs` calls on the walk thread and the scan-pool threads (§5.2) — there is no asynchronous I/O layer above the syscalls to account for, so the async-machinery-versus-syscall breakdown this section used to carry (what a Dart `Future` and an `await` cost over a blocking call, `dart:io`'s per-call overhead against raw `getdents64`/`fstatat` through FFI) has no analogue here and is cut along with the runtime it measured.

**Measuring it: a developer tool, not a page.** `dsync-scan-probe` (`native/scan_probe/`, a workspace member outside `default-members`, never shipped) walks one tree once per rung of core's `ScanProbe` — list, list+stat, the §5.1 rules, a scan against a warm archive, a scan against an empty one — and prints what each step on top of the platform's floor costs, with the tree's case folding (§16) beside it. It runs on a desktop and, cross-compiled, over `adb shell` (§14.1; its README has both). It replaced the app's Diagnostics page, which measured one folder where a profile now syncs several entries: the tool is run over each entry's local root in turn.

## 6. Reconciliation

Done on the initiating side from the two status lists. Per path, with statuses on replicas A and B:

| A \ B | unchanged | created | modified | deleted |
|---|---|---|---|---|
| **unchanged** | nothing | copy B→A | copy B→A | delete on A |
| **created** | copy A→B | same hash: commit only; else **conflict** | same hash: commit only; else **conflict** | **conflict** |
| **modified** | copy A→B | same hash: commit only; else **conflict** | same hash: commit only; else **conflict** | **conflict** |
| **deleted** | delete on B | **conflict** | **conflict** | commit only |

Additional rules:
- **Same content, no transfer.** Whenever both sides currently hold the same hash, no bytes move; both archives are committed with the current state.
- **A status from both sides is not a status *sent* by both sides.** The table is read per path from two statuses, and §6.1's exchange no longer puts every path's status on the wire: a path both replicas report `unchanged`, with the same hash, is proven so by a bucket digest and never sent at all. That is the `unchanged × unchanged` cell, which is "nothing", so an unsent path and a visited one produce the same plan. What §6.1 guarantees, and what this table depends on, is narrower and stronger than "both sides send everything": **a path is either absent from both sides' lists or present in the list of every side that has a status for it.** A path one side holds `unchanged` and the other has just reported changed is therefore still reconciled through the cell it belongs in, not through the "never seen" rule below — see §6.1's subtraction.
- **`unchanged` on both sides with *different* hashes is a conflict.** Two archives that have silently diverged: each replica is in sync with its own, so neither reports anything changed and neither has any claim on being the newer. There is no direction a rule could pick, which is what makes it a conflict rather than a copy — the same answer `modified × modified` with unequal hashes already gives. **This is new, and it is a behaviour change, not a consequence of the wire format.** Before §6.1 the disagreement was in hand on every single run and discarded, because this cell was "nothing" whatever the content; the two replicas stayed diverged forever, and nothing ever reported it. §6.1's digests are taken over `(path, hash)` pairs rather than paths alone precisely so that the disagreement dirties a bucket and the entries are fetched.
- **A path one side has never seen.** A replica with neither the file nor an archive entry for it reports nothing at all — the normal state of a fresh replica being set up against an established one, and of any path that is new to this pair. Such a path is mirrored from whichever side has it, whatever status that side gives it — or, when that side reports `deleted`, tombstoned on the side that still records it, so the two archives converge instead of drifting apart forever. Silence is what makes that safe: a replica that still had the file on disk would report `created` even against a wiped archive, so silence from one side plus a `deleted` report from the other means the path is gone everywhere. It is not a conflict: treating it as one would make the first run against an empty directory conflict on every file, and treating a still-pending deletion as one would ask the user to resolve a deletion that has already finished everywhere.
- **A path a scan could not read.** Excluded entirely: no action, no conflict. The table needs a status from both sides, and the unreadable side has none to give — its silence would otherwise be read as the "never seen" rule above and mirror the other side's copy over a file the tool was never able to look at. Not a conflict either: asking the user to choose between one side's content and something that was never read is not a choice they can make. The path is reported (§5.1) and counts toward exit 1 (§11.5); the next run reconciles it normally once it can be read.
- **Type mismatch.** A file at `P` on one side and a directory containing files at `P` on the other is a conflict on `P`.
- **Conflicts are never auto-resolved.** They are presented to the user, who picks a direction or skips — or, when both sides hold a file, keeps both (§7.2's copy aside), which settles nothing: the conflict is asked again next run.
- **Deletions are actions.** A propagated deletion appears in the plan like any other action and can be vetoed per item in interactive mode.

The output of reconciliation is a **plan**: an ordered list of actions (`copy A→B`, `copy B→A`, `delete on A`, `delete on B`, `commit-only`) plus a list of conflicts. The plan holds at most one action per path.

**A proposal may carry a reversal.** Each action is proposed with what the reconciler would have planned had the user said "the other side is right": the conflict resolution (§11.3) that keeps the side the action would overwrite or delete on. It is offered **only when that resolution is a copy** — the other side holds a file — so an offered reversal is always a copy of the same path from the other side, carrying that side's size:

| Proposed | Reversal | Offered |
|---|---|---|
| copy A→B, B holds a file (any status with one) | copy B→A | yes |
| copy A→B, B silent (a mirror) | delete on A | **no** |
| delete on B (A deleted, B unchanged) | copy B→A (restore) | yes |
| delete on A | copy A→B (restore) | yes |
| commit-only | — | no |

(and symmetrically for B→A.) The case it serves is "another app made a wrong change; put the stale version back", which is always a copy. Reversing a copy from a `modified` side **overwrites that side's edit** with the other side's version: that destruction is the point of the choice. An offered reversal therefore always leaves a file at the path on both sides. A reversal that would delete a new file is not offered, because skipping the action already covers "don't send this".

### 6.1 Exchanging the two status lists

**The wire cost is O(changes), not O(tree).** A run used to ship the whole replica listing whatever had changed, spent even on a run that concludes there is nothing to do. A scan is therefore three exchanges per side rather than one.

1. **The changed entries.** Each side sends only the paths it reports `created`, `modified` or `deleted`, plus the skipped and unreadable paths of §5.1 and the tally of §11.4. Empty in steady state. **Skipped and unreadable paths are always sent in full and are never in a digest**: a path the scan skipped or could not read has no status relative to the archive, so it is in no cell of §6's table and has no `(path, hash)` pair to digest — and it has to reach the report and the exit code (§5.1, §11.5), which only sending it can do.
2. **A digest per bucket** over the paths that side reports `unchanged`, **minus the paths the other side just reported changed in phase 1**, together with that side's own entries for exactly those subtracted paths. Bucketing is by a hash of the path, so both sides bucket a path identically whatever order they walked in. The digest is over the `(path, hash)` pairs in the bucket, in path order.
3. **The buckets the two digests disagree on**, requested in full from both sides and reconciled by §6 exactly as before. Buckets that agree are proven to hold the same `(path, hash)` pairs on both replicas — §6's `unchanged × unchanged` cell — so nothing more is fetched for them. When every bucket agrees, this phase is skipped outright.

**The subtraction in phase 2 is what makes a dirty bucket rare.** Without it, a path `created` on A and `unchanged` on B dirties B's bucket and drags the whole bucket's worth of entries across, so the cost is one dirty bucket per changed path. With it, a bucket differs only on genuine disagreement. It also cannot lose anything: the paths a side subtracts are exactly the paths the peer named, so that side returns its own entries for them in the same reply, and the cell resolved is the real `unchanged × created` — not the mirror that side's silence would otherwise have been read as, which would turn a same-hash commit-only into a copy and an `unchanged × deleted` into a tombstone that never deletes.

**K is scaled to the entry count, one level, no tree.** A target of a few hundred entries a bucket; a fixed K wastes digests on a small tree and makes a dirty bucket expensive on a large one. Both sides are given the same count, derived from the larger side's entry total, since only the initiator has seen both phase 1 replies. A Merkle tree refining only down the branches that differ is the general answer and is deliberately **not** built: phase 2's subtraction is what refinement would be for. Build it when a measurement says one level is not enough.

**Historical note.** Before the Rust port this section carried a measured traffic table (Dart's hand-rolled binary encoding, benchmark/scan_exchange_traffic.dart, since deleted with the rest of the Dart-core benchmarks, plan D11) showing the shape this design buys: a steady-state exchange in the low kilobytes against roughly a megabyte for shipping the whole listing, a dirty bucket costing tens of kilobytes rather than the whole tree, and a fresh replica against an established one degrading to close to the full-listing cost because every path on the established side lands in a bucket the empty side cannot match. Postcard's encoding is different from the Dart binary format (smaller per entry, no wire compatibility intended, plan D5), so the old byte counts do not carry over; the algorithm and its complexity class do, unchanged. The plan produced is identical to the one a full exchange produces in every case, with the single exception the `unchanged × unchanged` rule above states.

**A run against a replica whose archive was wiped** is the one degradation worth naming: every path is `created` there, so phase 2's request to the other side carries all of them — a list of paths rather than a list of full entries, so still cheaper than shipping every entry, but the one term in this exchange that grows with the tree rather than with the changes.

### 6.2 A single-file entry

A file entry (§12) reconciles exactly like a folder entry over the one path it names, `as_path` — the same table above, the same fast path (§5.2), the same staged write (§7.2) — with two differences, both because the entry named this path itself rather than a rule or a walk finding it:

- **The profile's `ignore` rules, and the scanner's own scratch-name and staging-folder skips (`is_temp_file_name`, `STAGING_DIR`, §7.2's write path), do not apply to a file entry's own path.** An `ignore = ["*.tmp"]` rule does not stop `notes.tmp` from syncing when the entry says that is the file to sync, and a scratch-file name dsync itself might otherwise mistake for one is not a concern here either, since there is only ever the one path to consider and it was never written under that scheme. Both rules still apply as normal to everything else — which, under a file root, is nothing, since there is nothing beneath it to apply them to.
- **Keep-both is never offered.** `Conflict::offers` omits `Resolution::KeepBoth` whenever the conflict belongs to a file entry, even when both sides hold a file: the copy aside (§7.2) would be a second file at a sibling path, which the entry does not name, and a served file replica refuses to write anywhere but its one declared path (§4.2). The user picks a side instead; skipping leaves the conflict open, exactly as it would for a folder entry with only one side's version to keep.

A single file's scan reports it in exactly the same shape a folder entry's scan reports one path in (§5): `symlink`/`specialFile` for a link or special file sitting where the entry expects a plain file, `unreadable` for a stat or read failure that is not simply the file being gone, and **only `NotFound` reads as absent** — everything else is reported unreadable and excluded, never mistaken for a deletion the user made (§6). Probes the write path runs to learn a filesystem's own behaviour (case folding, whether `chmod` sticks, §3, §7.4) still run inside the file's folder, and remove what they create there, exactly as they do for a folder root; the staging folder (§7.2) sits in that folder too.

## 7. Applying the plan

### 7.1 Order
Actions are *started* in plan order spread across folders (§7.2, task 5d8c28), and up to **32** of them run at once (`Tuning::apply_in_flight`; task 0f7dfc set 16, task 447876 raised it). Copies before deletions is not required; the archive rule in §7.3 makes order irrelevant for correctness, and it is per path, so two actions on two paths have nothing to order between them — the actions applied write at most one per *written* path (a copy aside writes its own new path, not the conflict's), so no two in flight can share one. Overlapping actions is what fills the idle gap §4.2's window exists to close: a serial applier keeps one operation outstanding however wide that window is.

**The number is the bandwidth-delay product.** Every replica operation costs one round trip, and an action was two of them — a `Write` and an archive commit — so one worker moved one file per two round trips however fat the link is. Throughput is `concurrency × file size ÷ (trips × RTT)` until it meets the link, and nothing in between contends: measured over a unix socket with 10 ms of added latency, apply time halved for every doubling from 4 to 64 concurrent actions with every per-operation mean pinned at one round trip. Sixteen is where that meets a phone on Wi-Fi for a tree of ~12.7 KB files. It costs a same-machine sync nothing — the same sweep at zero latency had 16 marginally ahead of 4.

Since task 9d2158 `trips` is one: §7.3's commit is batched and no longer sits in a worker's path.

**Actions in flight are not the destination's writers (task 447876).** The Rust port sized the apply's worker slots from `Tuning::writers` — the destination's writer threads, 16 — on the reasoning that a worker beyond them would only queue in the destination's pool. That holds for a local destination and not for a remote one: a slot is held from a write's request to its answer, so it covers the round trip and the body on the air as well as the far writer's work. Re-measured on the phone (1,500-file overwrite over `peer://`, 13.5 KB mean, instrumented on both ends; sessions `pairs/2026-09-25T01-*`):

| | 16 in flight | 32 in flight |
|---|---|---|
| laptop: write request → answer | 13.6 ms | 18.8 ms |
| phone: request arrives → answer queued | 6.4 ms | 8.5 ms |
| left on the link, both ways | 7.2 ms | 10.3 ms |
| phone writers busy (of 16) | 6.2 | 9.5–10.2 |
| phone's own writer queue | ~0.5 ms | ~0.5 ms |
| apply per file | 0.89–0.94 ms | 0.64–0.75 ms |

At 16 the phone's writers were starved, not queued: 16 × 6.4 / 13.6 ≈ 7.5 busy at most. At 32 the apply is 0.75–0.80× (every pair agreeing) and moves ~18.6 MiB/s against the 19.0 MiB/s this pair's link carries under raw `nc` (task 9d2158; the desktop is on Wi-Fi too, so every byte crosses the air twice): the time left on the link grows with what is in flight, which is the link queueing, and nothing of ours is near a bound — the phone's reader loop worked 0.06 s of a 1.4 s apply, bodies finished arriving 1.3–2.5 ms after their request, answers queued in 0.01 ms. More in flight past 32 buys queue, not throughput, on this pair. Two things were ruled out on the way: batching every record of the apply into one exchange (no change; the marks of the time, since removed, cost 0.35 s of a run, overlapped), and the phone's storage (its per-file stages slow ~20% at 10 busy writers against 6, and still net ahead). A local destination is unaffected: a local 1,500-file overwrite is ~41 ms at 16 and ~43 ms at 32, inside run-to-run noise, so one number serves both.

Confirmed on the shipped build (976275d, trunk CLI and APK, `--apply-concurrency 16` against the default 32, interleaved; sessions `pairs/2026-09-25T10-*`). Nine pairs over two sessions put the apply at 0.52–0.93× with every pair on the same side, median 0.82–0.83 in each session, and phone writers 5.9–6.2 busy against 9.5–10.1. Over the six-pair session the whole run is **0.88×** at the median (0.59–1.06, five pairs of six agreeing). The apply is about three quarters of a run, so 0.82 of it is ~0.87 of the total. The one pair that disagrees lost its difference to the scan, which swings 0.82–1.60× between runs of the same build (median 1.02) and is untouched by this change.

**The apply is three stages, not one loop** (task 9d2158). A read-ahead stage reads each copy's source ahead of the writers (§7.2); a worker does an action's file work and hands the records the two archives are owed to the commit stage, which batches them (§7.3) and reports each action once its batch has landed. The three are different work against different resources — the source's storage or the inbound link, the destination's storage, and a round trip carrying one line of JSON — and a worker that did all three in turn spent a third of the apply on the commit and 53–62% of the serialized budget waiting on the read. Each stage is bounded by the thing that constrains it rather than by one count of actions in flight: bytes buffered on the source, **32** actions in flight to the destination (§7.1), 64 records per exchange. What it costs is that the run reports later than it acts: an outcome is delivered when its batch lands, so the run may be up to `concurrency` actions in flight plus twice the batch size applied-but-unreported ahead of the last outcome a consumer saw. Every outcome delivered is still durable on both sides when it is delivered.

Outcomes are therefore reported in **completion order, not plan order**, and a consumer that stops mid-apply stops within the bound above rather than exactly one action later — each action past the last one reported is already finished and durable on disk, and nothing beyond them starts.

**The apply acts on the scan, and nothing scans twice** (task 2ad058). A path can change between its scan and its action — the plan may wait on a review for minutes, and a large tree takes a while to apply — so each action checks its own path right before it acts, against what the scan saw there, and one that no longer holds is skipped and left for the next run (§7.6). A second scan before the apply was the alternative; it would cost a whole scan to narrow the window rather than close it.

### 7.2 Copy
1. Source agent streams the file; destination agent writes it to a **temp in the replica's staging folder**, hashing each chunk (SHA-256) as it writes it, and, once it is whole — every byte, the source settled (step 4), and the bytes hashing to the source's scanned hash (step 5) — renames the temp onto the target. Parent directories are created as needed. Before anything is created, the destination stats the target and compares it with what the scan saw there; a target that changed is not written (§7.6).
2. Destination sets the temp's mtime to the source mtime and its mode bits to the source mode (§7.4), fsyncs it, renames it onto the target, and fsyncs the target's folder: the write answers only once the bytes and the rename are on disk (below).
3. Destination stats the final file and returns the resulting `size`, `mtime`, `mode`.
4. Source agent, once its last byte is read, stats the file it read — the open file, so a file renamed over the path after the open does not count. The initiator compares it with what the scan saw before the body's end reaches the destination: a source that still holds it ends the body, and one that does not fails the body in place of its end, so the destination drops the temp instead of renaming it (§7.6). The rename never waits on anything but its own target's re-check (step 1).
5. Destination, once the body has ended, compares the hash of the bytes it wrote with the source's scanned hash, which the write is handed with the source's metadata (over the protocol, in the `Write` request, §4.2). Bytes that hash otherwise — corrupted on the wire or in memory, routed to the wrong file — fail the write before the rename (a write failure at the `write` stage, `InvalidData`, `LandedMismatch` in `file_write.rs`): the temp is dropped and the target keeps its last good version. This is what makes the archive's reuse of the source's hash for the destination sound (§7.3): it is recorded only for bytes that hashed to it. The hash rides on the chunks already in hand, so it costs no second pass and no copy; it checks what the writer was given and wrote, not a read-back of the disk. Every copy's source has a hash — a scan entry for a file always carries one — so there is no unchecked write.

**Keep both: a copy aside.** For a conflict where **both** sides hold a file (`Conflict::keep_both`; modified × modified, created × created, diverged unchanged × unchanged), the user may keep both versions instead of picking one. `Action::CopyAside { path, from, to, bytes }` reads `path` on the peer (side B) and writes it, by the steps above, at a new sibling path `to` on this device (side A). Nothing at `path` is touched on either side, and **the conflict stays open**: the user merges the two files with whatever app they like, and the next run shows `path` again for them to settle. Its only write is a new file, so it cannot destroy anything. The sibling is named `<stem>.dsync-copy-from-<device>-<YYYY-MM-DD-HHMM>.<ext>` (`RelPath::conflict_copy`): `<device>` is side B's label, the time is the peer file's mtime in UTC, so the name identifies the version and a repeat keep-both of the same version writes the same name. A copy aside expects nothing at `to` — the scan exchange does not reliably report a path neither side changed — so a repeat keep-both whose sibling is already there, perhaps merged since, is skipped as changed during sync (§7.6) rather than written over; the file there is that version or the user's work on it. There is no other collision handling and no special case afterwards: only the destination's archive records `to` (§7.3), so the next run sees it unchanged on A and silent on B and mirrors it like any new file. A result is reported under `path`, the conflict's own, and the summary counts it applied while `path` still counts as a conflict (§11.4). Rejected: Syncthing's "keep this device's at the path and the peer's aside in one go", which overwrites the peer's file before the user has merged it.

**A temp in a staging folder, renamed onto the target (task 4e7fe7).** The target holds the old version or the new one, never a mix: a stream that fails, a process killed mid-write (routine on Android) or a far agent dying can only damage the temp, which is this write's own, and the next run copies the file again. The temp is created in `<root>/.dsync-staging/` (`STAGING_DIR`, `dsync-domain`; for a single-file entry, in `.dsync-staging.<file name>/` beside the file, `file_staging_dir_for`), named `<target name>.dsync-tmp.<pid>.<sequence>`, and the folder is created once a session by the first write. Each write: create the temp, write it while hashing it, check the hash, set mtime and mode, fsync, close, rename onto the target, fsync the target's folder, stat the target (`native/core/src/file_write.rs`).

- **Why a staging folder rather than a temp beside the target.** On Android's emulated storage a create costs ~15 ms plus ~17 µs per entry already in its folder, and a rename into a folder is cheaper than a create in it (the storage floor below). `write_ops_probe`'s `staged` pass, 8,000 files into one folder at four threads: 8.1 ms to create plus 48.5 ms to rename, 56.7 ms in all, against 84.7 ms to create in place. A temp beside the target would pay both the create in the full folder and the rename (est. ~85 + ~48 ms).
- **A rename that fails with `EXDEV`** — the target is behind a followed link onto another mount — falls back to a temp beside the target: the staged temp is copied there, its mtime set again, and that copy renamed onto the target. For a followed link the rename's destination is the link's resolved *target*, so the target is replaced and the link survives (§5.1).
- **A rename replaces only this name.** A hard-linked target keeps its other names' bytes (§5.1, task 6ac6ad), and a read-only target is replaced rather than refused: a rename needs the folder's permission, not the file's, and §7.4 sets the source's mode on the temp first (task 3a857c). The probe before the write reads only what §7.6's check compares (`on_disk_at`).
- **The scan skips the staging folder** at the root of a folder entry — its own and any single-file entry's beside a file there (`is_staging_dir_name`) — the way it skips a scratch name (`is_temp_file_name`) anywhere. **Leftovers are swept at lock:** taking a replica's lock (§4.3) removes the staging folder and whatever a crashed or stopped run left in it, and releasing the lock removes the folder again, so a user's folder carries it only while a run holds it.
- **Why a single-file entry's staging folder is named after its file.** A single-file entry locks its file, not its folder, so a folder entry over the same folder, or a single-file entry for another file in it, can hold its own lock at the same time; a shared staging folder would let one's sweep delete the other's in-flight temps. A per-file folder keeps every sweep to its own temps without making those entries wait on each other's lock. It adds no new name-length limit: the temp inside already carries the file's name plus a longer suffix.

**Why not in place (task 58d609, reverted by task 4e7fe7).** For a while every copy wrote in place over the target, behind a durable mark in the archive log: §7.2's rename was measured as the largest single term of a write on emulated storage, and the marks (an `intent` line per copy, withdrawn when a stopped run never started it) made a torn file detectable on the next run, as an untrusted path raised as a conflict labelled *interrupted*. Detection was all they bought. An in-place overwrite destroys the target's old bytes from the first one written, so the interrupted conflict offered a choice that did not exist: the old version was gone (on a pull, the last synced version; on a conflict resolved in the source's favour, the user's own edit), and "keep this side" picked the torn file, so the user's own answer spread the garbage. The speed in place bought came entirely from overwrites (~25× on the phone), which is exactly where there is data to destroy; a fresh file saved only ~25% (23.3 against 30.9 ms, `storage_probe.c`), so no hybrid keeps the speed without the danger. Rejected for now: backing up the old bytes to app-private storage and then writing in place (a rollback journal). It is fully safe and nearly as fast — task 6d7bfb measured read plus overwrite at 378 against 264 µs a file at 16 workers — but keeps all of the marks machinery and adds a recovery step; it is worth revisiting only if mass overwrites on the phone turn out to matter in real use.

**What it costs, the phone as destination (OnePlus 6).** Estimated from the probes below, not yet confirmed through the real write path:

| case | in place (before) | staged rename |
|---|---|---|
| fresh, 8,000 files in one folder | ~11 min (84.7 ms a file) | ~7.5 min (56.7 ms a file, probe) |
| fresh, 1,500 files spread across folders | 5.0 ms a file | ~8–17.5 ms a file (est.) |
| overwrite all, 1,500 files | 0.79 ms a file | ~20 ms a file (est.; renames run one at a time) |
| overwrite all, 8,000 in one folder | ~6 s | ~13 min (est.) |

On a desktop ext4 the whole temp-and-rename is ~11 µs a file, which is noise; the two fsyncs below are not.

**A write is durable before it answers, so an archive never records bytes a power cut can take back (task 945ea6).** The archive's own append is fsynced (§8.2), and a landed file used not to be: on a filesystem with delayed allocation (ext4, XFS, f2fs — the phone's app storage included) a power cut after the batch's commit could leave the archive saying "in sync" over a file that is missing — the next run reads it *deleted* against the other side's *unchanged* and deletes the good copy (§6) — or empty, which reads *modified* and is copied over the good copy. So the writer fsyncs the temp before its rename (`File::sync_all`) and fsyncs the target's folder after it (`atomic_write::sync_dir`; a no-op on Windows, as in §8.2), the copied-beside temp of the `EXDEV` fallback likewise, and only then answers. The applier hands a path's record to a commit batch only once its write answered (§7.3), and that holds for **both** archives — the source side's commit, made at the same time as the destination's, is just as wrong over a file that is not on disk — and for a `peer://` destination too, where the writer runs on the far host behind `replica_server` and its answer crosses the link after the syncs. A sync that fails fails the write (at the `close` stage for the file, `rename` for the folder; there is no `sync` stage, since a new stage changes the write stats a replica server sends and so the protocol): nothing records it, and the next run finds the path as the scan does. Deletes fsync their folder after the unlink the same way (§7.5).

- **Why per write, in the writer, rather than once per batch.** The writers already run sixteen at once on their own threads (`writer_pool.rs`), so each file's two fsyncs overlap the others' rather than queueing behind one another: the cost is the fsync latency divided by the writers, not the 6.2 ms a file the block-device ladder below shows for an fsync on one worker. Syncing at the commit instead — a folder sync per folder the batch touched, or one `syncfs` per batch on Linux and Android — would have to happen on *both* replicas before *either* commits (the two commits run at once, and each records the other side's file too), which is a new request on the protocol and a barrier in the commit pipeline; `syncfs` also flushes everything else dirty on that filesystem and has no portable equivalent on macOS or Windows.
- **What it costs, desktop ext4 on NVMe** (5,000 fresh files of 13,000 B, 30 a folder, local-to-local `dsync sync --batch --timings`, three runs each, interleaved): the apply went from 90–94 ms to 739–748 ms, ~18 to ~148 µs a file; per write the `close` stage went from 1 µs to ~1.05 ms (the file's fsync) and `rename` from ~0.14 to ~1.17 ms (the folder's). Not yet measured on the phone; there a write already costs ~5–32 ms on shared storage (above), against which the block-device ladder's fsync row adds about 4 ms to one worker's write.

**The source read starts before the write asks for it.** A read-ahead stage starts each copy's read while earlier writes are still going, and hands the writer a stream that already has bytes in it, rather than the write triggering the read on first demand. What a copy does and in what order is unchanged; only when the first byte is available is. This was the largest single term the Dart core's apply spent waiting on, measured phone-to-desktop; the Rust core has the read-ahead stage from the start rather than as a later fix.

**Bounded in bytes, not in files, and there is no size threshold.** The bound is on bytes *buffered per stream* — one chunk, `Tuning::read_ahead_chunk_bytes` (**64 KiB**) — with a total budget of `Tuning::read_ahead_budget_bytes` (**1 MiB**) across every read in flight, so a file larger than the whole budget holds one chunk and streams the rest under backpressure — on a remote source too, where it holds at most its credit on this side of the connection (§4.2) rather than whatever the far side sends it. There is no large-file bypass and so no threshold to choose. A second bound, `Tuning::read_ahead_streams` (**40**, the thirty-two actions in flight of §7.1 plus a lead of eight), caps how many source reads may be open at once: the byte budget alone would admit far more concurrent reads of a tree of small files than the writers could keep up with, and a remote source's read holds one of the connection's 48 window slots (§4.2) for its whole stream. A slot is held from the read starting until the writer has taken the last chunk, which is earlier than the write finishing.

**What one write costs, on the device.** The Dart core's apply carried an extensive allocation and garbage-collection ladder here (per-call and per-byte cost of `dart:io`'s asynchronous write path, a Dart VM concurrency sweep). None of that applies to the Rust write path, which is blocking `std::fs` calls on dedicated writer threads throughout (`native/core/src/file_write.rs`, `writer_pool.rs`) rather than an async runtime's I/O completion machinery — there is no per-call asynchronous overhead of the kind that ladder measured, because the calls are not asynchronous. Phase 16's phone-acceptance numbers (task 538b18) are this core's own device measurements; nothing here reproduces the Dart ladder against it, because the two write paths are not the same shape of cost to compare rung for rung.

**On the device, the write path is the storage and almost nothing else — a fact about the platform, not the language.** `benchmark/device/storage_probe.c` is a static aarch64 binary run over `adb shell` — no APK, no install, nothing this project's own runtime touches — that asks the kernel the same ladder of syscalls directly, and it is unaffected by the Dart→Rust switch: it never linked against either. A OnePlus 6 (SD845, UFS 2.1) on Android 14, where `/storage/emulated` is a `/dev/fuse` mount and `/data/local/tmp` is the block device, 850 files, mean 12,988 B, every size capped at one 64 KiB chunk, one worker:

- **A create costs more the larger its directory**, and nothing parallelises it: ~15 ms at 30 entries, ~34 ms averaged over filling 1,500, ~85 ms averaged over filling 8,000 — about 15 ms plus ~17 µs per entry already there, so filling one directory is quadratic. A first pull of an 8,000-file folder is ~11 minutes on this phone whatever dsync does. Why is not measured; a case-insensitivity check against the whole directory on a kernel (4.9) without ext4 casefold would fit.

That is the staging folder's case (above).

**So the room left is narrow and in the less common case.** Against that floor a fresh pull has further to go than an overwrite, but only for trees of many small directories; a large directory is at its own floor already, whatever the write path above it does. Closing that gap further would need an ordering that keeps concurrent creates in different directories, which is exactly what the folder-spread rule below already does; it does not need the async-vs-blocking design change the Dart analysis called for, since the Rust write path is blocking-on-threads throughout already.

**The apply spreads its actions across folders** (task 5d8c28; `spread_across_folders`, `dsync-domain`). Concurrent writes into the *same* directory serialise on this storage (the table above), so the pump walks the plan spread across folders rather than in plan order: one action from each parent directory in turn, the directories in the order the plan first reaches them, each directory's own actions in plan order. Every action, not only fresh copies, because the rule then needs only paths and costs the others nothing: an overwrite has no serial part whatever its directory, and a commit-only touches no file. Nothing else moves with it: that one order is the order source reads start in and the order workers take actions in; parent directories are still created by the write that first needs one and remembered per session; and the pruning §7.5 asks for is still swept once, after every action. A tree that is mostly one directory — a camera roll — gains nothing, because once the smaller directories run out what is left is that directory's creates, which serialise and grow with its size regardless. This was measured, on the Dart write path, as roughly a 3× win on a fresh pull and holding over a real `peer://` run once the far end's request window ran its writes concurrently (§4.2) — a device-and-storage effect, not a language one, so it is expected to hold for the Rust write path; phase 16 (task 538b18) is where that expectation was checked against this core.

### 7.3 Archive commit per path
After an action succeeds on both sides, **both** agents are owed the record for that path — except a copy aside (§7.2), which owes only its destination the record of `to`: the source side was not touched (`OwedCommits::One`). The record is handed over immediately; it *travels* in batches, and it is made *durable* in batches (§8.2), so a crash loses at most the last unflushed batch. That is the same shape of damage as the crash this section is already about, and the rules below close it the same way — it is simply a few hundred paths rather than one. A crash between the two commits leaves one side's archive stale.

**Records travel in batches of 64 (`Tuning::commit_batch`, task 9d2158).** One `Commit` request per replica carries the records of up to sixty-four finished actions. The Dart core's phone-to-desktop measurement that motivated this batch size — a single-path commit costing tens of milliseconds, almost all of it link round-trip rather than the replica's own work — is cut as a figure; the shape of the argument it made is not: the exchange itself is the cost on a chatty link (§17), so batching sixty-four actions behind one exchange amortizes it to a fraction of a millisecond each. The bound on going further is what a batch holds and how late the run reports, not the wire. A batch that fails fails every action in it, because nothing says which of its records landed — pessimistic on purpose, since an action reported failed whose record did land costs the next run nothing, and the reverse would archive a path nothing propagated. This batches the wire; §8.2 batches the fsync; the two are independent bounds on the same crash window.

For a copy, that self-heals: the stale side reports the path as modified with the same hash as the other side, which resolves as commit-only (§6). No work is redone beyond one hash.

For a delete, the same crash does not self-heal the same way — there is no shared hash for the two sides to agree on. The side whose commit landed has no file and no archive entry left, so it reports nothing; the side whose commit was lost still holds its stale pre-delete entry, so it reports `deleted`. §6's "a path one side has never seen" rule is what closes this gap: silence from the landed side plus `deleted` from the stale side tombstones the stale side's entry, so the next run converges on both archives agreeing the path is gone, rather than leaving one side reporting a deletion that already finished everywhere.

### 7.4 Metadata
- `mtime`: always propagated. If setting it fails, the write still succeeds; the actual mtime is what gets archived.
- Mode bits: propagated on a best-effort basis; failure is logged, not fatal. On a platform with no mode concept at all — Windows, per §3 — this degrades from "may fail" to "never attempted"; the archived value there is whatever `FileStat.mode` actually reports, the same "actual state, not the intended one" already true for Android's external storage.
- **Mode bits are not set on a filesystem that ignores them.** Before its first mode step, the write path asks its replica once whether modes stick (`ModeStep`, `native/core/src/file_write.rs`, §3): it creates a scratch file in the root (named like §7.2's scratch files, so a leftover is skipped by the scan), flips its owner-execute bit through `chmod`, and `stat`s whether the bit moved. If it did not, no file on that replica gets a `chmod` for the rest of the session. That is Android's shared storage (`/storage/emulated`, a FUSE mount): the storage layer fixes every file at 660 and `chmod` changes nothing, yet each call is a synchronous FUSE round trip — a real, if small, share of a serving replica's write time on a large pull. Skipping it changes nothing that is recorded, because the post-write `stat` archives the mode that landed either way. The answer is per filesystem, not per path, so it is asked once; a root the probe cannot create a file in keeps the per-file `chmod`. A `chmod` refused for one path on a replica where modes otherwise stick is still per-path and non-fatal, as above.
- Mode bits travel with content, never on their own. The fast path (§5.2) keys on size and mtime, so a file whose permissions changed and whose content did not scans as `unchanged` and gets no action. A mode-only difference between the replicas is therefore never detected and never repaired; it is corrected the next time that file's content changes. Detecting it would mean comparing the scanned mode against the archived one and adding a metadata-only action, which v0 does not have.
- Ownership, xattrs: not touched.

### 7.5 Delete
Target file is deleted — unless, stat'ed just before, it is no longer what the scan saw there, in which case it is left (§7.6) — and its folder fsynced, so the delete is on disk before its record commits, as a write's rename is (§7.2). Without it a power cut could bring the file back after the archives dropped it, which only costs a re-copy, but the same sync closes it at no new design. Every ancestor directory up to the root that the tool has just emptied is removed. Directories that were already empty before the run are left alone — the tool only removes emptiness it created.

**The pruning is swept once, after every action is applied**, not per delete (task 0f7dfc). `removeEmptyDirs` is the one agent operation that cannot share a connection with anything else, because it reaches ancestors of the path it is given rather than that path alone — it can remove a directory a concurrent `writeFile` on an unrelated path is about to write into — so §4.2 makes it a barrier. Run inside the apply loop it drained the connection's window once per delete, handing back most of what §7.1's overlap buys; run after the loop there is nothing left to drain.

Deferring it is not less correct. The rule above is unchanged and still holds: a directory emptied by a delete and then written into again by a later copy is now simply left alone, where before it would have been removed and recreated. What it gives up is that a failure to prune is no longer attributable to an action — that action has already been reported and recorded as applied — so it is swallowed, the same best-effort §7.4 gives mode bits. Pruning is tidying: §7.3's archive rule does not depend on it, so a directory left behind cannot stop the replicas converging.

### 7.6 Failures
A failed action is recorded, the path is left in whatever state it reached, and the run continues with the next action. Failed paths are reported at the end and contribute to the exit code.

**A copy that stops part-way leaves the target whole** (§7.2). A failed stream, a process killed mid-write or a far agent dying leaves at most a temp in the staging folder, which the write removes when it fails and the next lock sweeps when the process died; the target holds what it held before the copy, so the next run finds the path as it was and copies it again. No mark, archive line or conflict label is needed for it, and none exists: §7.2 has why the write-in-place marks of task 58d609 were removed.

A copy killed after its rename and before its commit holds the new content and no record of it; the next run finds it the same as the other side and commits it (§7.3). A write killed after its bytes and before its mtime never renamed, so it is a lost temp like any other.

**A stopped run** (the app's Stop, a backgrounding pause, leaving the page) lets the writes in flight finish and commit, starts nothing more, and ends like any other: summary, unlock, disconnect.

**A path that changed since the scan is left for the next run** (task 2ad058). Nothing re-scans before the apply (§7.1), so without a check an edit made on the destination while the run waited — during the review, say — was silently overwritten or deleted, and a same-size edit on the source between its scan and its read was archived under the old hash as though in sync. So each action carries what the scan saw at the path it acts on — a size and mtime, or nothing, the two facts §5.2's fast path compares (`Precondition`, `dsync-domain`):

- **A write or a delete** stats its path just before acting (§7.2's probe). A path that no longer holds what the scan saw — edited, created, removed, or turned into a folder — is not touched: the action is reported **changed during sync**, and neither archive records anything for it. The user's edit stays an edit to the next scan.
- **A copy's source** is stat'ed once its last byte is read (§7.2 step 4), and checked before the write's rename, not after it (task 91d20f). If it no longer holds what the scan saw, the body fails in place of its end: the destination drops its temp and keeps its last good version, the action is reported changed during sync on the source's side, and nothing is recorded. The next run finds the source changed and copies it again. The bytes read may be another version, or a torn mix of two — a file rewritten in place while it is read — and checking only after the rename let such a mix replace the destination's last good version, leaving the next run a conflict over garbage. The initiator decides, since it holds the scan: over the protocol a read's `End` frame carries the far file's settled stat to it (§4.2), and a write's body it fails is a `Fail` frame to the far writer, like any failed body; the failure is told apart from the write's own by the copy that handed the body on (`SourceMoved`, `body.rs`), not by anything on the wire.

A path left this way has no fresh archive entry, and the next run reconciles it like any other change: it propagates, or it is a conflict, and nothing is lost. It counts as a failed action (§11.4) — the run did not converge it. What stays uncovered is the time between the stat and the act, microseconds, and an edit the fast path would itself miss (same size, same mtime), which §5.2 already accepts.

**A run marker says whether an entry's last apply finished.** One empty file per entry, `<entryId>.run` in the initiating host's state directory (§8.3), is created and flushed before that entry's apply has anything to do and deleted when it returns, failed actions or not. A marker still there means the process died or that entry's run aborted mid-apply. It is a file of its own so a head asks "did the last run finish?" with one stat per entry, not a replay of every log. Both heads read the relevant marker before a run and warn when it is there (task 99f404): the CLI under each entry's own run header (and as `lastRunUnfinished` on that entry's `--json` `replicas` line, that entry's marker alone), the app on the profile's home-list row — true when *any* one entry's marker is there — with an offer to run it again, and in Run setup before that run starts. The run that follows is what sorts out what was left, entry by entry: files it never reached, or stopped mid-write, sync as usual.

Tested in `native/core/tests/it/replica/killed_write.rs` and `native/core/tests/it/run/changed.rs` (§14).

## 8. Archive

### 8.1 Content
One archive per replica, on the host of that replica, keyed by entry id + replica side — `<entryId>-<side>.jsonl` in the state directory (§4.3, §8.3). Header: format version (§8.4), entry id, root path. Entry: `path`, `size`, `mtime`, `mode`, `hash`.

### 8.2 Format (default chosen, see §15)
Append-only JSON Lines log (`native/core/src/archive_store.rs`, `archive_line.rs`). Each commit appends one line: an `upsert` or a `delete` (tombstone) for a path's entry. At the end of a run that reached the apply phase, the log is compacted into a fresh file and swapped in by rename. A run that committed nothing does not compact. On load, the log is replayed; last write per path wins.

**Format 2.0, and another major is refused, naming the file.** 2.0 dropped 1.0's `intent` and `withdraw` lines (§7.6); a 1.0 log is refused like any other major, and the way out is deleting it. The header's `version` is read first and checked by §8.4's rule: a log of another major is refused with an error naming the file, both versions and the way out (a dsync that reads that major, or deleting the log to start the replica's archive afresh), never silently replayed as damage or read as an empty log. A later minor is replayed with the fields it added ignored. A minor may add a field to a line, never a new `op`: a line this build cannot place might be a delete it would miss, so a new kind of line is a major bump. A first line that is not a header at all is corruption at line 1. Opening a log always replays it in full; there is no unloaded, lazy state to get out of sync with the file.

**Repaired by compaction, not by guessing, before the next write.** A crash can leave a log's last line torn (cut mid-write) or whole but missing its trailing newline (what an append after a crash-truncated file would otherwise splice onto); both are detected on open and repaired by running compaction before anything else is written, so a tolerated tear at the tail never becomes corruption mid-file from a later append landing on top of it. A first write cut short inside the header itself leaves a log nothing in which was ever durable, so it reads as empty and is rewritten; a header that is whole but not one is refused as corrupt.

**A directory fsync follows the compaction rename.** The rename itself is atomic, but on most filesystems the directory entry it changes is not guaranteed durable until the directory's own fsync; the Dart core skipped this (a known gap), and the Rust store closes it (`atomic_write::sync_dir`) — a no-op on Windows, where `std` cannot open a directory handle to flush and NTFS journals the rename instead, so there is nothing to add there.

**Commits are batched behind one fsync (task 0f7dfc).** Lines are buffered and written together — `Tuning::archive_buffer_lines` (**256**) of them, or `Tuning::archive_buffer_interval` (**1 s**) of age, whichever comes first, checked as each commit arrives rather than by a timer — and the whole batch is fsynced as a single append. This is the largest serial cost left in an apply once the requests themselves are pipelined (§4.2), because every commit on one replica queues behind every other commit on it; the Dart core's phone-to-desktop measurement that motivated the batch size is cut as a historical figure, kept as the shape of the argument only.

What batching gives up is bounded: a crash loses at most the last unflushed batch, which is the state §7.3 already converges on without intervention — the stale side rehashes those paths on the next run and they resolve as commit-only. The cost of being wrong is a rehash, never a wrong answer, and it is capped at a couple of hundred paths.

**A failed append is rewritten, not resumed, so a commit can never be silently dropped (task 42e1c4).** An append that fails partway — open, write or the fsync itself — could otherwise leave the in-memory buffer already cleared and the file not actually holding what that buffer described, so the *next* flush, taking the append path again, would write nothing further and report success. The store instead marks itself for repair on any append failure; the next flush rebuilds the whole log from the in-memory archive state (which already holds every commit, pending ones included) through the same atomic-write helper compaction uses, so nothing committed is ever lost to a failed append and no half-written fragment survives to be replayed later.

**Buffered commits are flushed before the replica is given up**, which is the part that is not optional: a clean exit must not lose work. `Unlock` is where that happens, since it is the one operation both a local replica and a served one run on every exit path, and the lock is what says the replica is this session's.

Rationale: per-path commits (§7.3) without rewriting the whole file, no native dependency, trivially inspectable. Unlike the Dart core, the archive store is **not** behind an interface here: it is a concrete `&mut self` type over `std::fs` (plan D3), because CLAUDE.md's abstraction test is failed rather than passed — the real implementation runs fine in a test (a temp directory), and only one implementation ships. An interface built in anticipation of a SQLite swap that has not happened is a rename, not a boundary; one is added if and when a second implementation is actually written.

### 8.3 Location
- Linux: `$XDG_STATE_HOME/dsync/` (default `~/.local/state/dsync/`).
- macOS: `~/Library/Application Support/dsync/` — the platform convention; macOS has no XDG variables to defer to.
- Windows: `%LOCALAPPDATA%\dsync\`.
- Android: the app's private files directory (Flutter head) or Termux's home (CLI head).
- iOS: the app's own `Application Support` directory inside its sandbox (§3) — there is no CLI head to have a second answer.

The three desktop rows are the answer for *both* heads on those platforms: the Flutter head running on Linux, macOS or Windows resolves them through the same `core` rules from the same environment rather than asking `path_provider` for an app-private directory (§3), so a desktop machine has one state directory and one device identity no matter which head opened it.

`dsync_domain::app_dirs` (§3) is a pure function of a `HostFacts` value and a `DirRule`: `DirRule::Xdg`, `DirRule::MacOs` and `DirRule::Windows` derive the first three rows from the facts named there, and `DirRule::HostSupplied` carries the last two — a base directory the Flutter head has already resolved through the platform's own API, which `dsync-domain` (no Flutter dependency, §3) could not call itself. The platform's facts are passed in from the one edge that reads them (the CLI's `Host::read`, the head's `Init` command), the same way `--state-dir` (`StateDirChoice::Explicit`) is, so every branch is exercised from a unit test on any host. A variable a branch needs that is absent or empty is an error naming it, never a path silently built from nothing. Every one of §4.4's device identity, the paired-device store, the per-replica archive and its lock lives under this directory.

**`--state-dir <path>` overrides all of it (§11.2, task af1128).** Given, that directory *is* the state directory — used verbatim, with no `dsync` joined onto it, so the path in a service unit's `ExecStart` is the path that appears on disk. It is a fifth `StateDirPlatform` case (`ExplicitStateDir`) rather than a nullable override beside the other four, for the reason that sum type exists at all: "derive it from the environment" and "here is the path" cannot both be asked for at once. It is what makes instance-scoped state possible — two `dsync agent --serve` processes on one host, each with its own paired-device store, archive logs and locks, rather than two processes quietly sharing one. The flag is registered on exactly the commands that address this host's state directory (`agent`, and every `pair` and `archive` subcommand); `sync`/`status` do not take it, because a run has two sides that each resolve their own state directory on their own host, and a remote side's belongs on its own `dsync agent` invocation.

**There is deliberately no `DSYNC_STATE_DIR`, and no flag spelling of the XDG variables.** `XDG_STATE_HOME`, `HOME` and `LOCALAPPDATA` are platform conventions shared with everything else on the box: a service that sets `XDG_STATE_HOME` for a whole slice should get exactly the CLI's own behaviour out of dsync, and a dsync-specific variable beside them would be a second, invisible answer to the same question. One explicit override, and the rules above underneath it.

### 8.4 Format versions
Every format that outlives one process or crosses to another build carries a version `major.minor` (`dsync_domain::FormatVersion`), and all of them started at **1.0**: the archive log's header (§8.2), `paired-devices.json` (§4.4), the profile TOML (§12), the pairing payload (§4.4) and the replica protocol's handshake (§4.2). The archive log and the protocol are at 2.0 since the write-in-place marks were removed (§7.6), and the protocol at 3.0 since a write carries the source's hash (§7.2). There is no Dart-era format to read: nothing written before 1.0 is recognized, and none of it is migrated.

- **A minor bump is additive and backward compatible.** It only adds — a field, a key, bytes after the last ones — so a reader of the same major reads data of a later minor, ignoring what it does not know, and a later build reads older data. The profile and the pairing payload are strict about what they do not know only when it cannot be an addition: an unknown key in a profile of this build's own minor or older is a typo and refused (§12), one in a profile of a later minor is ignored; bytes past a payload's token are refused unless the payload is of a later minor. A store rewritten by an older minor drops what that minor did not know and writes its own version, which the later build then reads as older data.
- **A major bump is breaking.** A reader refuses a different major, older or newer, with an error naming both versions and what to do — use a dsync that reads that major, or, for a store, delete the file and start again — and never reads it as damage, as empty, or at all. The version is read before anything else, so a later major may reshape everything but where its version sits.
- **Over the wire** both sides send `major.minor` (§4.2). Different majors are refused (exit 3, the message naming both); the same major works, and a session uses the lower minor wherever behaviour depends on it.

The compatibility decision — given ours and theirs, the version both can use or the mismatch — is `FormatVersion::agree`, one pure rule every store and the handshake call. Two things on disk carry no version of their own: the device identity (`identity.crt`/`identity.key`) is PEM X.509 and PKCS#8, whose format is not dsync's to version, and a run marker (§7.6) is an empty file whose presence is its whole content. The `app` head's own settings file (`lib/app/app_settings_store.dart`) is the head's, versioned by the head.

## 9. Ignore and follow rules

- Syntax: glob, matched against the root-relative path. Supported: `*`, `?`, `**`, character classes. No negation in v0.
- `ignore` rules: matching paths are neither scanned nor deleted.
- `follow` rules: matching symlinks are resolved (§5.1) and their target's content is synced as a plain file at the link's path, and a copy onto the link writes its target (§5.1); dsync never creates a symlink at the destination, on any platform, so Windows' privilege requirement for creating one (`SeCreateSymbolicLinkPrivilege`) never applies to v0's write path (§3).
- Rules come from the profile file; `--ignore` may be repeated on the command line and is additive.
- **Over `peer://`, the serving side's grants bound the `follow` rules** (§4.4, task 278aae). The rules are the run's, and on local, ssh and `unix://` runs the user owns both ends; a replica served to a paired peer follows the links the peer's rules name only where the resolved target lies inside a folder granted to that peer, and refuses a read, write or delete through any other link.
- **The Flutter head writes `ignore` rules from a Filters page, not from a file.** A head profile (§12's note on `SyncProfile`) saves its patterns beside its two roots, and the run compiles them into the one `RuleSet` it hands both replicas — the same path a `--ignore` flag takes, so a rule set chosen on a phone reaches the desktop replica exactly as a profile file's would. The page is a file browser over the local root rather than a pattern editor: a row is tapped and the glob is derived from it (`**/<name>` or the exact root-relative path), because the user knows the folder they do not want and should not have to learn the grammar above to say so. Its counted preview (`preview_filters`, `dsync-domain`; `native/core/src/filter_listing.rs` walks the tree it runs over) answers "what would sync" with a listing and a stat per file and no hashes, and — unlike a scan — descends into an excluded folder instead of pruning it, because the number the user is deciding on is precisely how much that rule removes. `follow` rules are not offered: the head follows no symlinks, so a rule for it would be one nothing reads.

## 10. Size warning and delete guard
Optional `warn_size_bytes` in the profile (`--warn-size` flag). If the total bytes to transfer in the plan exceed it, the plan display shows a warning. Nothing is blocked.

**A run that would delete most of a side stops and asks before applying.** A folder emptied or moved by accident, the wrong root picked, a drive unmounted in a way §4.5 cannot see — each of these looks, to the scan, like the user deleting everything, and the run would faithfully delete it all on the other side. So once the decider has answered (§11.3), the actions it approved are judged by `MassDeletePolicy` (`dsync-domain`): a side trips the guard when the run deletes **at least 10 files there and more than 50% of the files that side's archive holds** (`ScanTally::archived` — unchanged, modified and deleted entries; marked paths are left out, which only makes it trip sooner). Both halves are needed: the count alone would stop every tidy-up of a big folder, the share alone every delete of two files out of three. Unison's `confirmbigdeletes` is the precedent. The rule is judged on what was *approved* rather than on the plan, so deletions the user already skipped one by one do not ask twice.

**Judged per entry.** Each entry of a profile is its own `Run`, with its own archive and its own scan tally (§12), so the guard is judged independently for each: one entry's approved deletions tripping it, and being declined, ends only that entry — `RunError::DeletesNotConfirmed` below, which a profile's `ProfileRun` reports as that entry `Failed` and moves past to the next one — while a sibling entry's own deletions are unaffected either way.

When it trips, the run reports the verdict — per side, the count, the archive's size and the first 5 paths — and asks the decider once more, still before the run marker and the apply. A yes applies the approved actions as they stand; a no, or no one to ask, ends the run with nothing applied, both sides as they were, and the typed `RunError::DeletesNotConfirmed` (§11.5's exit 3). The refusal is not remembered: the next run asks again. The interactive CLI asks with a `[y/N]` prompt whose default — an empty line, a closed input — is no; `--batch` has no one to ask and refuses, naming `--allow-mass-delete`, which applies them without asking (the verdict is still reported); a dry run approves nothing, so it never trips. The `app` head asks on the run page (§11.4).

The thresholds are named constants (`MassDeletePolicy::DEFAULT`), not profile keys (§12): the per-run flag is the override, and a key that switched the guard off for good would switch it off for exactly the run it exists for. The size warning and the guard stay two verdicts: the warning is about bytes and blocks nothing, the guard about files lost and blocks until answered, and they are judged at different points — the warning on the plan as reconciled, the guard on what was approved.

## 11. CLI

### 11.1 Commands
```
dsync sync <profile> [flags]      # the main one-shot run
dsync sync <locA> <locB> [flags]  # ad-hoc, no profile
dsync agent --stdio               # started by ssh on the remote host
dsync agent --listen <socket>     # bind a unix socket and serve it (§4.2)
dsync agent --serve [--bind A] [--port N] [--state-dir D]  # serve paired devices over the network (§4.4)
dsync status <profile>            # scan + reconcile + print plan, apply nothing
dsync pair show --name <name> [--bind A] [--advertise A]  # print this device's pairing payload (QR + text), wait for one redeem, record it as <name> (§4.4)
dsync pair accept --name <name> <payload>  # redeem another device's payload; record it as <name>
dsync pair list [--json]          # this host's paired devices
dsync pair revoke <name>          # forget a device, locally (§4.4)
dsync pair grant <name> <root>    # authorize a paired device for a replica root here (§4.4)
dsync pair renew                  # re-issue this host's certificate under its existing key (§4.4)
dsync archive list [--json]       # the archive logs this host keeps, and what they cost on disk (§8)
dsync archive clear <profile>     # delete a profile's archive logs; --all for every one of them (§8)
```
`status` is `sync --dry-run` under a friendlier name. `pair` and `archive` alone, with no subcommand, are usage errors.

`archive` is the maintenance surface over §8.3's state directory, and `clear` is the only destructive thing in it: an archive is per-replica sync history (§2), so deleting one touches no file in either replica and costs the next run over that entry a full rescan and rehash — the work its first run did. `clear <profile>` resolves the name to *every one of the profile's current entries* (`Profile::options`, §12) and clears each of their archives, both sides together — because an archive kept for side `b` after side `a` is gone records a propagation the other side no longer remembers making, and leaving one entry's history behind while its siblings are cleared would leave the profile's own archives disagreeing about what has and has not been reset. `<profile>` may also name one entry id directly, exactly as `archive list` prints it, to clear a single entry without the rest. A log in use by a run is refused rather than pulled out from under it: `clear` takes §4.3's replica lock for each log it deletes, and that lock now holds against every holder on the host rather than only against another process. The OS file lock alone could not do it — POSIX advisory locks are owned by the process, so the Flutter head (§13), which runs its sync in the same process as its UI, would have been granted a delete out from under its own run, and the run would have rebuilt a log the next run then refuses as a mismatched header (§8.1). `ReplicaLock` therefore keeps a process-local registry of the paths it holds alongside the file lock, and answers `LockError::Held` from whichever side the second holder comes. The lock file itself is left where it is: it is empty by construction, so it is not archive state, and removing it would only race the next acquirer.

`agent` needs exactly one transport, and none is a default: they are not spellings of the same thing — `--stdio` serves one session and ends with its input, `--listen` and `--serve` outlive any number of sessions, and only `--serve` authenticates who connects — so a bare `dsync agent` is a usage error rather than a guess, and naming two is a usage error rather than a silent precedence rule. `--serve` binds every IPv4 interface on 28771 unless `--bind` and `--port` say otherwise (§4.4); `--port` or `--bind` without `--serve` is a usage error. `--listen` and `--serve` end on SIGINT or SIGTERM (§11.5's 130 / 143), which is what lets `--listen` unlink its socket on the way out.

`--bind <address>` is where a listener answers, on `agent --serve` and on `pair show` alike. It defaults to `0.0.0.0` — every IPv4 interface — which is what both did before it existed. `--bind ::` gives a dual-stack socket that also accepts IPv4-mapped connections (`v6Only` is false), and is how a peer reaches this host over IPv6, which is worth having because IPv6 needs no NAT traversal and therefore no third party. It is opt-in rather than the default because it fails outright on a host with IPv6 disabled. A `--bind` that cannot be bound is fatal (§11.5) and says which address was asked for; there is deliberately no fallback to another address, since a listener answering somewhere other than where the operator said is worse than one that did not start. The value is an address literal, never a hostname: a name may resolve to several addresses, or to a different one later, and "which one did it bind" is the question `--bind` exists to stop asking.

`pair show` decides what the payload advertises rather than taking the first non-loopback interface it finds: `--advertise <address>` wins if given, otherwise a non-wildcard `--bind` is advertised (the listener answers at exactly one address, so there is nothing to guess), and only a wildcard bind falls back to probing this machine's interfaces. That is also the whole of dsync's VPN story — bind to the tunnel's address and it is advertised too, so a VPN is a pointer to a proper address rather than anything dsync has code for.

A peer that arrives over IPv4 on a dual-stack listener reports as `::ffff:a.b.c.d`; what is recorded as its last-known address is the plain IPv4 form, so `pair list` shows, and the next run dials, the address the user would type. Anywhere a host and port are shown or read as one string, an IPv6 literal is bracketed (`[fe80::1]:28771`), and an unbracketed literal is read as a host with no port.

### 11.2 Flags
```
--dry-run             show plan, apply nothing
--batch               apply non-conflicting actions without asking;
                      conflicts are listed, not resolved
--allow-mass-delete   apply deletions §10's delete guard would stop for,
                      without asking
--json                machine-readable output (JSON Lines) on stdout
--ignore <glob>       additive to profile
--warn-size <bytes>
--jobs <n>            hash parallelism
--ssh-option <arg>    one argv word for ssh itself, before the destination;
                      repeatable, additive to the profile
--remote-dsync <cmd>  the command that starts the agent on the far side
--verbose / --quiet
--state-dir <path>    where this invocation keeps its state (§8.3);
                      `agent`, `pair *` and `archive *` only
```
`sync` and `status` also take a hidden `--apply-concurrency <n>`: how many apply actions are in flight at once (§7.1, `Tuning::apply_in_flight`), default 32; the destination's writer threads are not changed by it. It exists for benchmarks (task 7080d6) and is not in `--help`.
`--state-dir` overrides §8.3's platform rules for one invocation, verbatim. It is what lets two agents run on one host without sharing a paired-device store or contending for the same replica locks (§4.3), and what makes a service unit self-describing — a packager reads `ExecStart` and knows where state lives without knowing what XDG is. See §8.3 for why it is a flag and not an environment variable, and why `sync`/`status` do not take it.
`--ssh-option` and `--remote-dsync` apply to every remote replica of the run *that is reached over ssh*. The value that reaches a replica is per replica (§4.2); a run whose two remotes need *different* values is what a profile's `[ssh.a]`/`[ssh.b]` is for. Neither has anything to say to a `unix://` or `peer://` replica — there is no argv to pass options to, and nothing to start on the far side, because the listener is already running in both cases — so a run that names either is not an error; they simply do not apply there.

### 11.3 Interactivity
Default is interactive: the plan is shown, conflicts first, then each proposed action; the user accepts, skips, or picks a direction per item, or accepts all remaining. `--batch` skips the prompts for non-conflicts. With `--batch`, conflicts are never resolved automatically.

**A multi-entry profile is reviewed one entry at a time, in run order (Resolved R2).** Interactive mode shows entry 1's plan, waits for it to be answered, then — once that entry's `Run` has reached its own review — shows entry 2's, never both at once and never entry 2's before entry 1's has been asked, so an answer always belongs to the plan just shown. A tripped delete guard (§10) is asked the same way, entry by entry, after that entry's own review. This costs no more than reviewing one plan in the common case: the head's own review already answers an empty plan — nothing proposed — at once, so an extra entry costs a screen only where it actually has something to show.

The `app` head offers two more answers. Per proposed action, **reverse** — when the plan carries one, i.e. the side the action overrides (a copy's destination, a delete's side) holds a file, it copies that side's version back over the other instead; the plan sends the reversal's byte count beside each action, and a reverse asked of an action without one is a stale answer and applies nothing. Per conflict where both sides hold a file, **keep both** — side B's version is saved beside side A's as `RelPath::conflict_copy`, named from side B's location label and side B's file's own mtime (UTC, to the minute), and the conflict itself stays open and counts as one. The head answers each index once; only the first answer per action or conflict counts. The CLI does not offer either yet (deferred).

While the review is open, the `app` head can **compare** one conflict or planned copy: it asks the core for both sides' *current* files, on demand and for that row alone, over the run's own connections and under the run's own locks, so nothing is read unless the user asks and nothing is read once the review has closed. The view is read-only — it chooses nothing; the row's choice stays on the review. The core refuses to read media (by extension) and any file over 4 MiB on either side, and a file with a NUL byte or invalid UTF-8 is shown as binary, so only UTF-8 text is compared, as a line diff with the changed words emphasised; it is unified on a phone and side by side on a wide window. Leaving the view cancels the read, and a remote far end is told to stop (§4.2's `Cancel`). The CLI does not offer it.

Whatever the review approved, §10's delete guard may then ask one more question before anything is applied: the CLI prints each tripped side's count and first paths and asks `Apply these deletions? [y/N]`; the head's run page asks in its own bar. It is asked after the review rather than folded into it, because it is about the approved set as a whole — no single row's answer would have raised it.

### 11.4 Output
- Human mode: for each entry in turn, a `[i/total] a ↔ b` heading naming both replicas and when the pair last synced, then a plan table, then progress lines during apply, then that entry's own summary (applied / skipped / conflicts / failed / unreadable); one entry's ad-hoc run, or a profile with exactly one entry, prints the heading without the `[i/total]` prefix. Each heading prints before that entry's plan moves, so a mistyped location is caught while it is still harmless; when either side has no archive it says so, because that entry's run mirrors rather than propagating deletions (§6). A closing outcome list names every entry once the profile ends, in run order — only shown for a profile of more than one entry, so a one-entry run's output gains nothing here. `skipped` counts proposed actions the user declined; `unreadable` counts paths §5 could not read, which were never proposed at all — two different questions, so two different numbers.
- `--json`: for a profile, a leading `entries` line lists every entry before the first connects — `{"type": "entries", "entries": [{index, entryId, kind, a, b}, ...]}`, in run order, `kind` being `"folder"` or `"file"` (§12) — and from that point on **every event line carries `"entry": i`**, the 0-based index into that list, so a consumer can group a multi-entry run's output without re-deriving order from arrival time. An entry that never connects gets a bare `{"type": "error", "entry": i, "message": …}` line, since its `Run` never started and has nothing else to report. An entry whose `peer://` link dropped and is being dialled again (§11.3) gets `{"type": "reconnecting", "entry": i, "attempt": n, "afterMs": …, "message": …}` — the re-dial's number from 1, the wait before it, and what ended the attempt. It comes right after that attempt's own `error` line and supersedes it: an `error` followed by `reconnecting` is not the entry's end, and the entry's later lines are the next attempt's, from its `replicas` on. Human mode prints one line on stderr per re-dial, under the attempt's error — `connection to <device> lost; reconnecting (n)` — and `--timings` adds `reconnects: n` under an entry that re-dialled. Every other line has a `type` field (`replicas`, `plan`, `massDelete`, `action`, `conflict`, `symlink`, `specialFile`, `unreadable`, `caseFoldCollision`, `scanTally`, `progress`, `result`, `summary`, `error`, `reconnecting`). `symlink` reports a link the scan skipped (§5.1); `specialFile` a fifo, socket or device file it skipped (§5.1); `unreadable` reports a path it could not read (§5); `caseFoldCollision` reports a path excluded because another folds to the same key on a case-insensitive replica (§16). All four carry a `detail`: which of §5.1's cases the link was, the special file's kind, the OS's own reason for the failed read, or the path it collided with. They are separate types rather than one type with a `reason` field, so a consumer already filtering for `symlink` — a thing that is normal on every run — does not silently start matching failures too. `scanTally` reports, per side, how many scanned paths resolved through each of §5.2's branches — most usefully `metadataMatched` against `hashMatched`, the fast path against the rehash it took to prove an unchanged file's drifted size or mtime meant nothing. `massDelete` is §10's verdict, before any `action`: `allowed` (whether `--allow-mass-delete` applied it without asking), then `a` and `b`, each `null` when that side did not trip it or `{deletes, archived, paths}` — the first 5 paths; a refusal follows it as an `error`. `replicas` is that entry's header data — each side's location, locality, archive path and last-commit time, plus the **entry id** (`entryId`), `firstSync` and `lastRunUnfinished` (§7.6's run marker was there when this entry's run started) — as facts only; the human warnings are renderings of those, not strings on the wire. Human text goes to stderr in this mode so stdout stays parseable.

**A locked screen on the `app` head is a pause, not a failure.** The mobile head is the peer that gets backgrounded mid-run, and the platform freezes a backgrounded app: the socket then goes silent and the far end fails the session on its heartbeat deadline (§4.2), mid-copy, holding both replica locks until its own deadline fires. So the head takes both halves of the problem. It holds the screen on for as long as a run is live (`wakelock_plus`), which removes the case nobody asked for — the idle timeout — and costs a plugin and no permission. And it treats a real backgrounding as a *pause*: on `AppLifecycleState.paused` it stops the run exactly as a user's Stop does: the writes in flight finish, nothing further starts, and the run ends by unlocking both sides and disconnecting, and the phase the page shows says paused rather than stopped or failed. Coming back to the foreground continues it automatically; a run that ended in failure instead waits behind a Resume button, because a stale address or a revoked grant (§4.4) is not something to re-dial every time the user glances at the screen.

**On Android a live run is not paused by backgrounding: it is kept alive (`RunKeepAlive`, `lib/app/run_keep_alive.dart`; `SyncService.kt`).** For as long as a run is live, whatever the keep-awake setting says, the head runs a `dataSync` foreground service holding a partial wake lock — the CPU otherwise sleeps with the screen off, foreground service or not — and a Wi-Fi lock, so power save does not throttle the link; the service is what keeps that wake lock and the network honoured under Doze and keeps the process from being frozen. Its notification ("Sync running") opens the app, and is shown once `POST_NOTIFICATIONS` is granted (asked at the first run on 13+; the service runs without it). The pause above stays the answer wherever the run is not kept: on iOS and the desktops (no keep-alive), when Android refuses the start (its background-start restriction), and when Android takes it back — 15's cap on `dataSync`, about six hours a day in the background, ends the service within seconds of `onTimeout`, and the head pauses the run then. Swiping the app away from recents destroys its engine and the head's side of the run with it, so the service stops with the activity rather than keep a run nobody can see or steer; the far end's heartbeat deadline, or the next dial's session claim, ends the session there. `WorkManager`'s `setForeground` was rejected: the run is the Rust hub's, in the app process, not a `Worker`'s.

What "continues" means here is a second run of the same request — a fresh dial, scan and reconcile — not a protocol-level resume, and it is a continuation because of §7.3 rather than because anything is remembered: every action reported before the pause is committed on both sides, so the new plan holds what is left. The re-scan costs a walk of both trees and one scan reply, not a rehash, since §5.2's fast path matches everything the previous attempt applied. What it does pay for twice is the hash of a path that was planned but not yet applied, and any conflict the user had not resolved is asked again. Only `paused` triggers this: `inactive` is a notification shade, a permission dialog or an incoming call, and a run torn down for one of those was never in danger. The pause is best-effort by nature — the platform gives a backgrounding app a short window to finish that teardown — and the far end may still hold the session and its locks when the head comes back. The Foreground run does not wait that out: every `peer://` dial presents the session token the far end issued on the last connection (§4.2), which ends that dead session and frees its locks at once; the heartbeat deadline remains the backstop for a far end that never sees the claim.

**A dropped `peer://` link is dialled again, once, inside one bounded window — every head alike.** `ProfileRun` owns it, so the CLI and the app share one rule. When an entry's run fails because its link to a `peer://` side closed, failed at the socket or went silent, the entry is not over: it waits a backoff (1 s, doubling, at most 15 s), then dials, scans, reconciles and runs again — the same "second run of the same request" as above, with the same §7.3 reason it continues rather than restarts, and the token reclaim making its lock free. A re-dial that finds nothing answering, or a link that drops again, is tried again; so is a lock the far side still holds during a re-dial (the dropped session's own, until the reclaim lands). Anything else — a refused or revoked pairing, a withdrawn grant, a certificate, a version mismatch, a folder another run holds — ends the entry with today's outcome at once. The re-dials of one drop share a window of 120 s from the drop: no wait is started that would end past it, and a re-run that gets past its locks opens a fresh window for its next drop. An entry re-dials at most 10 times in all. When the budget runs out the entry fails with the drop itself as its error (not the last dial's), or with the held lock when that is what the last attempt met. Only a *drop* is re-dialled this way: a failure that is not one still waits behind Resume, as above, and `ssh://` and `unix://` sides are not re-dialled at all. A stop or pause while waiting to re-dial ends the entry as a stop while connecting does: not run, with nothing further dialled. The app's run page shows the wait as its own live phase, `Reconnecting`: one line in the stage area, "Connection lost — reconnecting (n)", n being the attempt just made, with Stop active; the entry stays Running, the dropped attempt's rows and failure clear as for any entry start, and the actions it completed still count toward a Stopped or Paused outcome that lands during the backoff. A successful re-dial returns the phase to the ordinary connected course.

**A re-dialled entry is not reviewed again for what has not changed (`run/recalled.rs`).** `ProfileRun` answers all of one entry's attempts through one `Recalled` wrapped around the head's decider, which keeps, per path, the row each answer was given for and the answer: an action approved, reversed or left out; a conflict kept on a side, kept both or left open; and the delete guard's verdict, if one was confirmed. When a re-dial's re-plan reaches the decider, a row *carries* when its path was answered before and the row is the same, field for field; a `CommitOnly` row always carries — it offers no choice, being the trace of an approved copy that landed before the drop — and a path answered before and missing now is done. If every row carries, the earlier answers are the answer and no review opens: a vetoed action stays out and a resolved conflict stays resolved. If any row does not, the head is asked again (`Decider::decide_again`), told row by row which earlier answers still hold and which rows changed or are new (`Recall`); the CLI's prompt then asks the whole plan again from its defaults. The app reopens its review with every carried row's earlier choice already selected — where the row still offers it, else the row's default — and every changed or new row at its default. The changed rows lead the review in a group of their own, "Changed since you approved", conflicts then actions, each marked with what it was when answered ("was: copy to the remote", or "new" for a path the earlier review did not have) and shown in no other section; the review's header line says it: "Reconnected. 3 changed since you approved, shown first; your other 120 choices are kept". The keyboard cursor starts on the first changed row and walks the page in that order. Only where a row is shown moves: each choice stays keyed by the row's plan index, so the answer maps back to the rows it was made for. A first review has no such group, marks or line. When every row carries, the app opens no review, and the rows the run applies show the choices kept (`Decider::carried` is handed the same `Recall`). The delete guard is not asked again while each side it trips deletes no more than a confirmed verdict covered; a side whose count rose, or a newly tripped side, asks again, and a guard never confirmed (`--batch`) is never carried. The record lives for one entry of one profile run: a new entry, a resumed pause or a re-plan in the foreground starts with none.

**The run page's session mirrors `ProfileRun`'s own order (§12).** A run session stays *Live* for as long as `ProfileRun` is still going, whatever any one entry does — an entry being skipped or failing does not make the session Resumable mid-run, since the profile itself has not stopped — and ends `Finished` only when every entry synced, or a new standing, `FinishedWithIssues`, naming the skipped, failed and never-run entries, when at least one did not. `FinishedWithIssues` is **Resumable**, the same standing a failed lone run already had: a retry re-runs the entries that already synced as quick no-ops and only has real work left where the profile actually stopped. Resume — and the app's own Pause/Foreground cycle above — always restarts the **whole profile from entry 1**, never from wherever it left off, which is the simplest rule and matches what a bare retry already did before entries existed (resuming from the entry it paused in is deferred). The run page's header, its missing-root wording and its entry list all come from the same session snapshot, current entry included, rather than from any one entry's own state read in isolation.

**The `app` head asks §10's delete guard on the run page, in the review bar's place.** When the run's view says the guard is waiting (`RunPhaseView::ConfirmingDeletes`, answered by the `AnswerDeletes` intent), the page says how many files of how many would be deleted, on which side ("this device" or "the remote") and in which folder, and offers *Don't delete* and *Delete N files*; Stop stays where it is. It is a step of the run rather than a dialog, like the review before it. Declining ends the *current entry* as a failure worded as the user's choice — nothing on that entry was changed — and the profile carries on to its next entry exactly as any other declined or skipped entry does (§12); Resume runs the whole profile again, which asks again wherever it still has something to ask.

**The `app` head's run page refreshes at most once a second, and nothing on it animates while it waits.** The hub keeps the run's state as every event arrives — so a stop or a pause still reports the latest count — and sends the page a new view of it at most once a second while only progress and the scan's facts change (`REFRESH_INTERVAL`, `native/hub/src/run.rs`); a run with nothing to report sends nothing, so the page schedules no frames at all. A phase change (applied, stopped, paused, failed), a question (the review, §10's guard) and the answer to a tap go out at once, final numbers included. Waiting is a static stage strip — Connect · Scan · Review · Apply · Done, each marked done, current or pending — with one line on the current stage and a fixed "Started HH:MM", never a spinner, an indeterminate bar or an elapsed-time ticker: those repaint at frame rate for as long as a scan lasts to say only "still going". The one moving part is a determinate apply bar, which repaints only when its value changes.

### 11.5 Exit codes
```
0    all planned actions applied, no conflicts
1    completed, but some paths were skipped (including paths the scan could
     not read, §5, or that collided on a case-insensitive filesystem, §5.1)
     or are unresolved conflicts
2    completed, but some actions failed
3    fatal: bad arguments, cannot reach a replica, lock held, archive unreadable,
     protocol version mismatch, deletions §10's guard stopped for not confirmed
130  interrupted by SIGINT (128 + 2)
143  interrupted by SIGTERM (128 + 15)
```
**A conflict the user resolves is not a conflict for this purpose.** `RunSummary::of` (`dsync-domain`) counts a conflict only if it is not among the actions the decider kept — one resolved by picking a direction becomes a kept action, reported as applied or failed like any other, so a run whose only conflicts were all resolved interactively exits 0, not 1. This is the same rule §11.3 already implies ("the user accepts, skips, or picks a direction per item") stated as what it does to the exit code, because a run that stops to ask, gets an answer for everything it asked, and applies the result is a run that completed cleanly.

**Unconfirmed deletions are 3, not 1.** §10's refusal applies nothing, the same outcome as §4.5's missing root that it complements, and a scheduled `--batch` run must not report it as the ordinary "some paths skipped" that a pending conflict produces every day: the run needs a person before it can do anything, which is what 3 already says. An interactive "no" exits 3 for the same reason.

**A profile's exit code is the worst of its entries' (§12).** Each entry is scored by the table above from its own run — a missing root, a wrong-kind root, a refused hello, a held lock, unconfirmed deletions, or an entry never started because an earlier one stopped the profile, are all "no summary", so all of them are 3, exactly as a lone run with no summary is; a synced entry's code is its own summary's. The profile's code is the maximum over every entry, so one skipped entry among three that applied cleanly still exits 3, not 0 — a scheduled job checking the exit code learns that *something* in the profile needs a person, without needing to parse which entry. A stop signal wins over every entry's code, exactly as it wins over one run's own, above.

When both 1 and 2 apply, 2 wins. 130/143 are deliberately outside the 0-3
scheme: they say what the user did, not what the run did, so they win over
any of 0-3 rather than being ranked against them — folding an interrupt into
3 would have retry logic retrying a run the user asked to stop.

A `sync`/`status` run traps both signals the same way: the first one stops
the run gracefully — nothing further starts, the actions in flight finish
and both sides commit their archive entries (§7.3), the run marker is
cleared (§7.6), and the summary is printed — and a second one, of either kind, exits at once. Whichever arrived first picks the
code. SIGTERM is trapped, rather than left to the kernel's default (which
also reports 143), because for a scheduled run — a systemd stop, a
`timeout`, a supervisor's kill — it is the *normal* stop signal, and an
untrapped one lands wherever the process happens to be, mid-copy included:
the data is safe either way, but one side's archive can end a commit behind
with nothing reported. On Windows, where there is no SIGTERM to trap, only
SIGINT is watched.

**Every stop is bounded (task e6be5d).** One owner (`StopSequence`,
`native/cli/src/stop.rs`) holds the whole exit path for every
long-running command: the first signal asks, a second one of either kind
exits at once, and a deadline of **10 seconds**, armed by the first signal,
exits with that signal's code whether or not the shutdown finished. Every
await on the way out — a scan in flight, §4.3's archive flush, a half-open
peer socket, a remote agent that stopped answering — is otherwise a chance
for a stop signal to produce a process that never exits, and a supervisor's
SIGKILL is the one exit path that releases nothing. The deadline is the
last-resort bound, not the normal path: an ordinary stop completes §4.3's
flush-before-release well inside it. Ten seconds leaves headroom over the
ssh transport's own exit grace — up to 2 s waiting out a wedged remote
`ssh` process after the connection closes (`EXIT_GRACE`,
`native/core/src/ssh_transport.rs`) — *on top of* that flush; a
supervisor's kill timeout belongs above 10 s, not below it.

`dsync agent --listen` reports 130/143 too, although a signal is its
*ordinary* way out rather than an interruption: there is no input to close
and no run to have got partway through, and 128 + signal is what a shell
reports for a program that does not trap them at all. Trapping them buys the
socket being unlinked (§4.2), not a different code.

## 12. Profile file

**One store, owned by the core, shared by both heads (plan D7).** Before the Rust port the CLI had TOML profiles and the Flutter head had its own JSON store, `sync-profiles.json` — two stores for one concept. `dsync-core` now owns profiles in TOML under the config directory (`native/core/src/profile_store.rs`), and the head edits them through CoreLink commands (`listProfiles`/`saveProfile`/`renameProfile`/`deleteProfile`) rather than keeping a store of its own. On desktop the head and the CLI resolve the same config dir (§3, §8.3), so after the switch a profile saved from the app is runnable as `dsync sync <name>` and vice versa; that is intended, not a coincidence of the storage layer.

TOML, parsed with the `toml` crate. Location: `<config>/profiles/<name>.toml` — the file's name *is* the profile's name, so a name is validated as file-safe and unique the moment it is chosen, by the core, for whichever head is choosing it. The config directory is resolved per platform the same way the state directory is (§8.3, `dsync_domain::app_dirs`):
- Linux: `$XDG_CONFIG_HOME/dsync/` (default `~/.config/dsync/`); Termux CLI head unchanged.
- macOS: `~/Library/Application Support/dsync/` — the same directory as §8.3's state; macOS has no config/state split.
- Windows: `%APPDATA%\dsync\` — the roaming profile, distinct from §8.3's `%LOCALAPPDATA%` state.
- Android (Flutter head) and iOS: the app's own config dir, handed in resolved by the app head at `Init`, as §8.3 does for state.

**A profile is a named, ordered list of entries (task ceba30): a folder on each side, or one file on each side, each with its own archive, locks, run marker and delete guard (§4.3, §7.6, §8, §10).** Where a profile used to be one `[replicas]` pair, it is now one or more `[[entries]]` tables sharing the rest of the profile — `rules`, `options` and `ssh.*` apply to every entry alike, because they describe *how* dsync talks to each side, not any one pair:

```toml
version = "1.0"

[devices]
b = "a1b2:c3d4:e5f6:0718:293a:4b5c:6d7e:8f90:1a2b:3c4d:5e6f:7081:92a3:b4c5:d6e7:f809"

[[entries]]
a = "~/Documents"
b = "peer://phone:/storage/emulated/0/Documents"

[[entries]]
kind = "file"
a = "~/notes.md"
b = "peer://phone:/storage/emulated/0/Notes/notes.md"

[rules]
ignore = ["**/.git", "*.tmp", "**/node_modules"]
follow = ["shared"]

[options]
warn_size_bytes = 500_000_000
jobs = 4

[ssh.b]
options = ["-i", "~/.ssh/id_phone"]
command = "/data/data/com.termux/files/usr/bin/dsync"
```
(kept consistent with `native/domain/src/profile/tests.rs`'s `TWO_ENTRIES` — the test's copy of this text is the source of truth for the syntax, and this example is written to match it, not the reverse.) `version` is the profile's format (§8.4); the store always writes it, and a profile without one — written by hand — is 1.0. Allowed keys are `version`, `devices.{a,b}`, `entries[].{kind,a,b}`, `rules.*`, `options.*` and `ssh.*`; `[replicas]` and `a_device_id`/`b_device_id` are gone, with no compatibility read for either — this project has no users yet to migrate. A profile of another major is refused naming both versions; one of a later minor loads with the keys and tables that minor added ignored. Every other unknown key is an error rather than ignored, since a misspelled key silently dropped is how a profile quietly stops ignoring `**/.git`.

Each `[[entries]]` table is one pair: `a` and `b` are locations (§2), and `kind` is `"folder"` — the default, and so left out of a written folder entry — or `"file"` (§6.2). A profile needs at least one entry; one missing its `a` or `b` is refused. A `kind = "file"` entry additionally needs a file name on each side — `/`, `peer://p:/` or a path ending in a separator are refused, since the name is what the file syncs under.

**Every entry's side A is on one endpoint, and every entry's side B is on one.** The same host, socket or peer device across every entry of a profile — refused at parse (`MixedEndpoints`) otherwise — because a profile is "a place on this side and a place on the other", plural on the places, singular on the sides. `[ssh.a]`/`[ssh.b]` and `[devices]` follow from that: they are keyed by side, not by entry, and apply to every entry whose that side is remote (ssh) or a peer. They are ignored for a side that runs in-process — a profile may carry one for a side that is local on this machine and remote from the other end of every entry's pair.

§10's delete guard has no key here, on purpose: its thresholds are fixed, and `--allow-mass-delete` is a per-run flag only.

Command-line flags override profile options. `ignore` is additive, and so is `--ssh-option`, for the same reason: a profile's `-i` is what makes the connection work at all, and a `--ssh-option` typed once to debug a run must not silently drop it. Where the same ssh option is given twice, ssh's own precedence decides. `jobs` and `warn_size_bytes` are range-checked on load (`Profile::parse`, `dsync-domain`) — a check the Dart loader lacked.

**A `peer://` side is keyed by device id, not by name, in one `[devices]` table shared by every entry (union schema, plan D7).** A `peer://` replica (§2, §4.4) names a device, and that name is local to this host — a renamed peer must not break a profile that was working a moment before. So a `peer://` side is not resolved by the name alone: `[devices]`'s `a` and `b` keys carry the device id `dsync pair` pinned at pairing time for whichever side is a peer — required when that side is a peer, refused otherwise — and that id, not the name in the location string, is what a run actually dials (§4.4's device-id-not-name rule). It sits at the top level, one table for the whole profile, rather than inside each entry, because every entry's side is on one endpoint (above): a profile has at most one peer device per side however many entries it holds, so there is exactly one id to record per side, not one repeated in every entry. The name in a `peer://` location is a display convenience, refreshed to the device's *current* name whenever the profile is next saved; the id is the truth the connection is dialled by. **A peer path in an entry must be absolute, never `~`-prefixed:** the peer stores its own grants already expanded (§4.4), so a leading `~` and its expansion would be two spellings of one grant that the overlap check below could not tell apart. A profile copied verbatim to a second machine is still portable in name only, exactly as before this schema existed: the id names a specific device's key, and a machine that has never paired with it has nothing to resolve that id against, `dsync pair` has to run there first, and no amount of copying the profile substitutes for it. There is nothing in `[ssh.a]`/`[ssh.b]`'s shape for a `peer://` side to configure — no options to pass to a spawned process, no far-side command to name, because the connection is already authenticated by the pairing and the far side is already running (§4.4) — so `peer://` gets no `[peer.*]` table alongside them. The port is left out of the profile for the same reason: it is carried in the paired-device store's cached address (§4.4), because a profile is the wrong place for anything that already rots on its own.

**`EntryId`: one derivation, for an entry, a head profile's entry and an ad-hoc run alike (was `ProfileId`, before an entry — not a whole profile — was the thing with an id; the wire, the hub's own views/signals and the CLI's `--json` all now say `entryId`/`entry_id` too, name for name).** A 32-character lowercase-hex id, SHA-256 over the canonical replica pair — each side's canonical form, a `peer://` side contributing its *device id* rather than its display name, so a renamed peer keeps the same id and a same-pair entry and ad-hoc run agree on which archive they own (§8.1) — with one addition: **a file entry also hashes the tag `file`** after the pair, so declaring an entry a file where it was a folder, or the reverse, is a new entry with a first sync, never a folder's archive read as a file's. A folder entry's id is therefore byte-for-byte the id the pre-entries format would have derived over the same pair, which is what lets an existing profile's archive survive the switch to entries untouched. This is what an entry and the head's own saved runs share with each other: an entry's archive is keyed by this id, not by the profile's file name or the entry's position in the list, so renaming a profile or reordering its entries orphans nothing, and two differently-named profiles that happen to share one entry share its archive.

**A profile has no id of its own; a head list is keyed by name, and each row shows its entries.** The app head's own profiles are this same store's rows — `ProfileRow` carries the file name (the key a head list is sorted and edited by) and each entry's `EntryId` (its own archive key), kept apart on purpose, since one is a human label shared by the whole row and the other is a derived fact about one pair. A profile whose peer has been revoked, or whose local root no longer passes the §3 filesystem probe, renders on the head's home list as broken and unrunnable rather than disappearing — the row is the only place that run still exists, and it names the first broken entry rather than every one it has (a stated simplification, not a defect). A profile shaped for the CLI in a way the head does not render (an ssh side, say) is simply not offered as one of the head's rows; it is still a profile the CLI runs.

**Overlap: none of a profile's `2N` sides — two per entry — may be, contain, or lie inside another (decision 2, `Profile::options`).** Nested roots would sync one file twice, through two archives that each believe they own it, so this is refused rather than merely surprising: an entry's own `a` against its `b`, entry 1's `a` against entry 2's `b`, two entries' `a`s against each other — every pair of the `2N` sides is checked, on canonicalized paths (`~`/`$VAR` expanded, resolved against the working directory, one trailing separator dropped; a `peer://` side by its device id and path, never its display name; then compared component by component, `/`-only and case-sensitive, except under `Platform::Windows` facts, which also split on `\` and fold case — `dsync-domain`'s `path_nesting.rs`). The first clash found is named in the refusal, by its two 0-based `entries[i].a`/`.b` positions. This runs wherever a profile's options are computed — `dsync sync`/`status` on every run, the hub's `save_profile` before writing — not only once at save time, so a hand-edited profile is caught too. An ad-hoc run's two locations get the same a-vs-b check, with no entries to check across.

**`ProfileRun` (`native/core/src/profile_run.rs`) is the one owner of a profile's entry order.** It syncs a profile's entries **sequentially** — never more than one connection to each device at a time — giving each its own connect and its own `Run` (§4–§10, unchanged per entry: its own hello, locks, scan, reconcile, apply, delete guard and archive commit), closed before the next entry's connect begins. Before any entry, it re-resolves every side that is a plain local path (`Location::Local`; an unschemed `host:path` that happens to name this machine stays a lexical-only check, like any other remote form) through the same canonicalization the folder lock uses (§4.3) and re-runs the overlap check above on the *resolved* paths — a symlink or a move since the profile was last checked can hide a nesting the text does not show — refusing the whole profile before any entry starts if two now nest. A far side reached over ssh or a `unix://` socket gets no such re-check: it is that host's own filesystem to resolve, and neither transport carries grants for this host to check against (a known limit). A `peer://` far side is covered instead: every far path must equal a grant, grants themselves can never nest (§4.4), and that is checked again at that entry's own `hello` — the far-side half of decision 2's "re-check at run start".

One entry's own trouble does not by itself stop the rest: a missing or wrong-kind root, a refused hello (`NOT_GRANTED`/`GRANTS_NEST` included), a held lock, declined deletions, or a failed apply action are that entry's problem alone, and `ProfileRun` moves on to the next entry regardless — the profile ends having synced what it could, skipped or failed the rest, exit code the worst entry's (§11.5). Only a **user stop**, or a **connect failure that means the device or transport itself is unreachable** (a socket that will not open, a peer that cannot be dialled, no identity to dial with — as opposed to a root that merely does not exist yet, or an archive that cannot be opened, which are that one entry's problem), ends the profile early: every entry after the one that hit it is reported never run, rather than each independently waiting out the same timeout.

**Choosing a file entry, in the app.** The app offers no free-text file path and no `FilePicker.pickFiles` — its Android implementation hands back a cache copy with no real filesystem path (§3), useless as a replica root. A file entry's path is instead chosen by picking its folder with the ordinary folder picker and then a name from that folder's own listing (`ListFilterFolder`, sent with an **empty** ignore list, so a file the profile's own rules would otherwise skip is still offered to pick), or typed by hand. Filter preview (§9's Filters page) stays folder-only and is not offered for a file entry (§6.2), and the run setup page's Filters tool binds to the profile's first entry's folder only, whichever kind of entry that is — an accepted simplification, not a bug, since the profile's `ignore` rules are shared across every entry (above) and a file entry offers no filter preview to begin with.

**Concurrency.** The head and a CLI on one desktop can both write profiles and pairings. Each write is temp + fsync + rename + directory fsync of one whole file (§8.2's helper), so a concurrent writer can lose an update but never corrupt a file — the same guarantee §8.2's archive and §4.4's paired-device store already give their own whole-file writes. Two runs of the same profile started at once are not excluded by anything here either — §4.3 covers what happens: each entry's own locks are what one run's second attempt on that entry meets, while the rest of that run's entries still sync.

## 13. Project layout

The engine and the CLI are a **Rust cargo workspace** under `native/` (`native/Cargo.toml`, `native/Cargo.lock`); the Flutter head lives where it always has, at `lib/app/`, and talks to the workspace through one seam.

```
native/
  domain/   dsync-domain — pure rules and values: parsing, reconcile, plan,
            spread, bucket digests, exit policy, profiles, tuning
  core/     dsync-core — I/O: stores (archive, identity, paired devices,
            profiles, lock), the Replica trait and its two implementations,
            the protocol, transports, pairing, Run/Applier
  cli/      dsync-cli — the `dsync` binary: sync, status, agent, pair, archive
  hub/      the rinf bridge: intent-named commands in, one reply per command,
            and each session (run, serve, pairing window) out as
            snapshots, over dsync-core
lib/app/
  core_link/   CoreChannel (the one interface: rinf's signals), CoreLink
               (concrete: correlation, decoding) and the models
  (everything else: pages, ChangeNotifier view state, controllers, scopes —
   unchanged in shape by the Rust port; only the seam to the engine moved)
```

**The dependency rule, enforced by CI (plan D1).** `dsync-domain` depends on nothing but `base64`, `serde`, `sha2`, `thiserror`, `time`, `toml` and `similar` (the review's text diff: pure, no I/O, accepted on purpose as the domain's one algorithmic dependency) — no `tokio`, no filesystem I/O, no network. "Deciding never fetches; fetching never decides" (CLAUDE.md) is not just a style preference here: every reconcile, plan, spread and exit-code rule is a plain function over values, testable with no mock, no temp directory and no `await`, and the `cargo` CI job runs `cargo tree -p dsync-domain -e normal` and refuses the build if `tokio` shows up in it. `dsync-core` depends on `dsync-domain` and owns everything that domain cannot: stores, the `Replica` trait (`LocalReplica` and `RemoteReplica`, the two real implementations that earn it its place as this project's one border abstraction, CLAUDE.md), the protocol (§4.2), transports, pairing (§4.4) and `Run` — the one class that owns the cross-module order of a sync (hello, lock, scan, reconcile, decide, apply, commit, unlock, in that order, on every path). `dsync-cli` is a thin binary over `dsync-core`: argument parsing, the human and JSON renderers, the interactive decider, signal handling. `hub` is the only crate that imports `rinf`, and it is thin by the same rule CLAUDE.md gives an I/O boundary: it decodes a signal, calls a `dsync-core` flow, encodes the result, with no business rule of its own.

**The head's seam: the rinf channel, and nothing upstream of it.** Every call the Flutter head used to make into a Dart `dsync_core` now goes through `lib/app/core_link/core_link.dart`'s `CoreLink`, one concrete class, over `CoreChannel` (`core_channel.dart`): send a `CoreRequest`, receive `CoreReply`s and each session's snapshots, all as the generated binding types. The channel is the one interface, and it earns its place the same way `Replica` earns its on the Rust side: `RinfCoreChannel` cannot run inside `flutter test`, because only a platform build runs Cargokit and links `libhub` — the real implementation cannot run in a test, which is exactly CLAUDE.md's border test. It is already abstract, so it is what a test fakes (CLAUDE.md: "if a dependency is already abstract, fake that"); `CoreLink`'s correlation and decoding are the code the app runs, in the app and in every test. Pure, display-only values (formatted device ids, expiry notes, address text) are computed once in the core's reply and carried across as plain fields, not recomputed per build on the Dart side and not a second round trip. Each command carries a `u64` correlation id and gets one `Reply{id, result}` back — rinf's own signals are one-way, so this id is what turns them into something a Dart `Future` can await; a command that opens a session (a run, a serve, a pairing window) uses its own request id as the session id, and the session's snapshots are a second, ongoing signal keyed by that id.

**Rust owns session state; the head renders it and sends intents.** A run, serving and a pairing window are each a state in the hub (`native/hub/src/run/state.rs`, `serve.rs`, `pairing.rs`) — the phase, the plan and the review's choices, the delete guard's question, the outcome, the connection log, the offered payload — and after every change the hub sends a snapshot of it: `RunSnapshot { session, view: RunView, last }`, `ServeSnapshot`, `PairingSnapshot`, each marking whether it is its session's `last`, on which the head closes the session's stream. The view carries every verdict the head shows — whether a run is live or can be resumed, whether it is a first sync, the scan's and the plan's totals — so the head derives none of them. A serve or pairing snapshot is whole. A run's is whole but for the plan, which can run to tens of thousands of rows: it is sent whole once — the first view the head receives after the hub takes it — and thereafter each view says either *the same plan, and these rows changed since the view you last received* (each changed row carrying its whole current choice and outcome), or *no plan*, or *a new plan, whole*. "Last received" is exact because a session's snapshots are delivered in order and none that is sent is lost (the hub's outbox is unbounded and forwarded in order; the head buffers a session's stream from the moment it opens), and because the hub diffs against what it actually handed to the outbox, never against a snapshot it coalesced away unsent. So the head's one piece of order is folding a run's plan rows into the plan it holds; beyond that its controllers render the latest view (wording, dates, layout) and forward what the user does as intents — `SteerRun { session, intent }` (a row's or a conflict's choice by index, confirm, accept all, answer the delete guard, stop, pause, resume, foreground, close), `ConfirmPairing`, `CancelPairing`, `StopServe` — which the hub weighs where the session stands and ignores or refuses when it cannot take them. Nothing on the Dart side decides a phase, an order or a choice's validity, so there is nothing there that has to agree with Rust. A run session outlives an attempt: a resume runs the same target again in the same session, resolving it afresh, so a target that will not resolve is the session's failed phase rather than a refused command.

**rinf is confined to two directories.** `native/hub` is the only crate that depends on it; `lib/app/core_link/` (plus `lib/main.dart`, which starts it, and the generated bindings under `lib/app/rust/bindings/`) is the only Dart that imports it. Nothing else in `lib/app/` or `native/` knows rinf exists. That confinement is what would make a later swap — to `flutter_rust_bridge`, or raw FFI — a change to two directories rather than a search-and-replace across the head.

**Build integration: Cargokit, and a vendored, patched copy of rinf.** rinf is a Flutter FFI plugin, not a Dart build hook, so its platform code runs Cargokit against `native/hub` with the workspace path hard-coded to `<app>/native/hub`; Cargokit in turn finds `native/Cargo.toml` and `native/Cargo.lock` above it on its own, even though rinf's own template assumes the workspace sits at the Flutter project's root — it does not here, so the tree stays one self-contained `native/` directory rather than spreading Rust files through the repo root. `third_party/rinf` (see `PATCHED.md` there) is rinf vendored and patched, picked up through a `dependency_overrides` entry: Cargokit's Gradle task calls `project.exec`, which Gradle 9 removed, and this project's Android toolchain is on Gradle 9; the patch injects `ExecOperations` and changes nothing else. Regenerating the Dart bindings after editing `hub/src/signals.rs` runs the rinf CLI from a checkout of rinf 8.10.1 (not a global install): `cargo run --manifest-path <rinf-checkout>/rust_crate_cli/Cargo.toml -- gen`, which writes `lib/app/rust/bindings/` (declared in `pubspec.yaml`'s `rinf:` section); the output is committed, so `flutter analyze` and a fresh checkout work without anyone having a rinf checkout of their own. Building the app needs nothing extra beyond that: `flutter build linux`/`apk`/etc. drives Cargokit as part of the ordinary Flutter build. Three build-time gotchas worth knowing before chasing them as bugs: a hot restart does not reload the Rust side, so any change under `native/` needs a full rebuild; Cargokit runs `rustup target add` from inside Gradle whenever an Android target is missing, which changes the machine's Rust toolchain as a side effect of building the app; and `rinf gen`'s output turns a Rust `u64` into a Dart `Uint64` wrapper class rather than a plain `int`, which `lib/app/core_link/wire_models.dart` converts away from at the boundary rather than leaving it to spread through the head's own models.

## 14. Testing

**Gates (`native/`, run from the repo root):** `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo build --workspace --all-targets`, `cargo test --workspace`, plus the `cargo tree -p dsync-domain -e normal` check (§13) that fails the build if `dsync-domain` ever gains a `tokio` dependency. **Gates (the head):** `dart analyze` and `flutter test`, unchanged in shape from before the port.

- Core logic (`dsync-core`) is tested against real temporary directories created per test (`tempfile`), the same principle the Dart core's tests followed.
- Reconciliation is additionally tested as a pure function, in `dsync-domain`, on hand-built status lists covering every cell of the table in §6 — no temp directory, no `await`, because deciding is pure (§13). §6.1's exchange is tested the same way, against the plan the two whole listings produce, since the exchange is a wire optimization and a difference between the two is a bug by definition.
- The protocol is tested by running a `LocalReplica` behind an in-memory `Transport` (`tokio::io::duplex`), exercising the same `RemoteReplica`/`ReplicaServer` code path a real stdio, unix or `peer://` connection does, without a socket or a process — `native/core/tests/it/replica/`.
- A killed write (§7.2, §7.6) is tested in-process (`native/core/tests/it/replica/killed_write.rs`): the write of one path is stopped at every step it has — the body failing part-way, a real process killed mid-body, the commit batch lost, killed before its commits flushed — on an ordinary pull and on a first sync. The old file must be left whole (or no file, on a first sync), a failed write must remove its temp and a killed one's must be swept at the next lock, and the next run must converge by itself with no conflict; nothing is ever copied back over the source.
- Crash-safety of §7.3 is tested in-process (`native/core/tests/it/replica/crash.rs`): one side's archive commit is made to fail after the other side's has landed, which is the exact state a crash between the two commits leaves behind, and a fresh, uninterrupted re-run must converge without moving bytes again. Real process kills are covered separately, through the compiled binary (`native/cli/tests/cli/signals.rs`, `stop_deadline.rs`): a real SIGINT/SIGTERM to a running `dsync sync` proves the trap (§11.5), and the `peer://` e2e tests (`native/cli/tests/cli/pairing.rs`, `peer.rs`) pair two temp state directories through the real `pair` commands and run a whole sync against a real `dsync agent --serve` child, stopped the same way.
- **Every async or process-spawning test runs under its own deadline**, sized to the test and never raised to make one pass: async tests go through a shared `with_deadline` helper (`tokio::time::timeout`) or paused time (`#[tokio::test(start_paused = true)]`) where the test is about a timer (the heartbeat, the handshake deadline, §4.2, §4.4); a test that spawns a process kills it on a deadline (`assert_cmd`'s `.timeout(..)`) and on drop, so a hung child cannot hang the suite behind it.
- **The head is tested over a fake channel** (`test/app/support/fake_hub.dart`): a `CoreChannel` that answers each `CoreRequest` with a generated `CoreReply`, feeds the generated snapshots a test hands it, and records the intents sent — the real `CoreLink` runs on top, its correlation and decoding included. No `flutter test` run loads `libhub` (§13's border test). A widget test is "given this view, the screen shows X" or "tapping Y sends intent Z"; what the view should be is not the head's to know. What `flutter test` cannot exercise, `cargo test` on `native/hub` does instead: each hub command handler is tested against a real `dsync-core` flow on a temp state dir — decode a signal, call the flow, check the reply and the snapshot sequence of real runs, serving and pairing — with the session states' rules unit-tested as plain values.
- **One Linux `flutter drive` test crosses the seam for real**: `integration_test/head_pairs_and_syncs_with_cli_test.dart` builds the real `dsync-cli` binary, starts the app against temporary `XDG_STATE_HOME`/`XDG_CONFIG_HOME` directories, shows a pairing code on the app, redeems it with `dsync pair accept`, serves a granted folder with `dsync agent --serve`, and syncs to it from the Run page — an actual `RinfCoreChannel`, `libhub`, and a real CLI process on the other end of `peer://`, checked once so the seam itself is proven and not only each side of it in isolation.
- **The release check on an Android phone crosses it on the platform the desktop test cannot reach** (task 83c7d4): `integration_test/phone_release_check.sh`, run on the desktop, builds the CLI, seeds the trees and runs `integration_test/phone_release_check_test.dart` on the device through `flutter test -d <serial>` twice — phase `main`, then phase `recover` after it has force-stopped the app. It proves (a) the All-files grant (§3): with the `MANAGE_EXTERNAL_STORAGE` app-op at `default` the core refuses the test folder and Run setup's pick flow refuses it and asks for the grant, and at `allow` the same process, by pid, takes it; (b) Run setup taking the picked folder's path; (c) a sync the app starts against `dsync agent --serve`, and one the desktop CLI starts against the app's Serve page, both over `peer://` (§4.4); and (d) the app killed mid-apply, relaunched, §7.6's run marker seen and the run recovered — each ending in a sha256 comparison of every file on both sides. It is a manual step before a release, on a test device, not a CI job: it needs a phone, and it uninstalls and reinstalls the app, which takes the archives, the identity, the pairings and the All-files grant with it. It is hands-free by design and automates no system screen: state is flipped from the desktop over adb (`appops set` for the grant, `am force-stop` for the kill), and the test calls the app's own code where a person would open the chooser or Settings — the Settings intents are only checked to resolve, never launched — because taps on a system screen are flaky and a check that waits on a person is not a check. Every wait polls the wall clock rather than `tester.pump`, since an app behind another screen draws no frames and a pump waiting for one stalls. What it does not cover is exactly what that leaves out: a person granting access on the Settings screen, and the chooser's `content://` tree URI → path conversion, which runs only inside `file_picker`'s activity-result callback (task 8c71a9 proposes a `treeUriToPath` channel as the seam to test it through). How to run it is in `README.md` ("Release check on a phone").
- **CI runs on Linux, macOS and Windows** (`.github/workflows/test.yml`): a `flutter-test` job (`dart analyze`, `flutter test`) and a `cargo` job (the gates above) on all three, so what §3 says about a macOS or Windows replica — mode bits, case folding, path spelling — is exercised there and not only reasoned about. There is no `dart test` job: the Dart core and CLI it used to run are deleted (§13), and their coverage lives in the `cargo` job now.

### 14.1 Measuring on a device without an app

**The Rust CLI cross-compiles straight to Android, which changes what this section is for.** Before the port, the Dart core could not produce an Android binary of itself at all — `dart compile exe --target-os android` is rejected by the SDK, and a `linux_arm64` Dart binary will not load under bionic's linker — so measuring the actual engine on a phone meant either a hand-rolled C probe standing in for it, or driving it through the whole Flutter app via `integration_test`. `cargo build --target aarch64-linux-android -p dsync-cli` has neither problem in principle: it is the same `dsync` binary the desktop runs, cross-compiled (`cargo check --target aarch64-linux-android -p dsync-cli` passes), and `adb push` plus `adb shell` would run it directly against a real replica on the phone — no APK, no install, no engine-shaped hole to route around — though that path has not itself been exercised on a device yet. Phase 16's phone-acceptance numbers (task 538b18) were taken a different way: through the release APK's **Answer paired devices** (Serve) page running on the phone, synced against with the desktop's release `dsync sync`, driven by `benchmark/interleaved_pairs.dart` — 25×4 MiB fresh: 27-30 MiB/s; 1,500 fresh: 4.5 ms/file; 1,500 overwrite apply: 0.94/1.18 ms/file; phone CPU ≤22 ms/MiB, sampled from `/proc`. What is below is what still needs something other than the plain CLI.

**`dsync-scan-probe`, for what a scan costs (§5.3).** Built for `aarch64-linux-android` the same way as the CLI and run over `adb shell` against a tree in shared storage; `native/scan_probe/README.md` has the commands.

**A static aarch64 binary over `adb shell`, for anything below even that.** `benchmark/device/storage_probe.c` is built with `aarch64-linux-gnu-gcc -static`, and a statically linked ELF needs no interpreter, so it runs on bionic with no APK, no install, nothing touched on the device, and its output in the terminal — see `benchmark/device/run_storage_probe.sh`, which builds, pushes, sweeps and cleans up in one command. This is the right instrument for a question about the *storage itself*, below any userspace runtime's cost, which is where §7.2 shows the phone's write cost mostly lives. It is unaffected by the Dart→Rust switch, having never linked against either core.

**`integration_test` driven by `flutter test -d <id>`, for what has to cross the head's own seam on the phone** — the release check in §14, `integration_test/phone_release_check.sh` — rather than for engine performance, which the plain cross-compiled CLI above now answers directly. It compiles, installs, runs and streams stdout back with no taps, and costs an install, so it is for a test device rather than one holding a real replica — an install can take the app's data and its All-files grant with it.

**Where a probe writes.** `$HOME/.cache/dsync/scratch/<name>` on a host, under XDG's cache root so it is disposable by convention, with `scratch` saying so outright — not the OS temp directory, which is tmpfs on most machines and would measure RAM rather than a disk, and not a name this project already uses for something else (the atomic-write helper's own temp files, §8.2).

**A ladder is only as good as its control.** Every ladder in `benchmark/` carries one: `storage_probe.c` seeds its tree untimed so that no rung is the one paying to create it, without which its first rung reads several times its true cost, and the pure Dart-VM probes kept from before the port (`gc_ladder.dart`, `stat_allocation_probe.dart`, `dir_stat_probe.dart` — none of which ever imported the deleted `dsync_core`, so none needed deleting with it) carry their own for the same reason. A rung ladder with no rung that already knows its own answer is not a measurement.

**A `peer://` comparison is an interleaved pair with the radio beside every run** (task 84fc92). The phone ↔ desktop link drifts between runs by ~13% on a phase total — more than most changes this project measures — and two eras of runs once differed 1.7× with nothing recorded to tell them apart but the bare round trip, which points at the phone's association. So a before/after is not two sittings: `benchmark/interleaved_pairs.dart` runs the two arms alternated in one (`--order abab`, or `abba`, which also cancels a linear drift and switches half as often), and reads `adb shell cmd wifi status` and `dumpsys wifi` at the start and end of every run — band, channel, width, standard, negotiated rates, RSSI, an AP fingerprint and the tx retry share. Each run is the desktop's `dsync sync <profile> --batch --timings` against the phone serving. The driver owns one folder inside the profile's desktop root and leaves it empty: a `fresh` pass pulls a new `synthetic_tree.dart` tree each run and syncs its deletion away untimed afterwards, an `overwrite` pass seeds one tree and rewrites every file before each run. Before the first run and after every arm switch it syncs one file into the phone and away again, untimed, and any sync whose summary shows a failed action stops the session — a phone without its All-files grant otherwise times 3,000 failed writes as a fast run. Its summary gives each pair's ratio, each arm's own spread, and flags what 9d2158 §9.0 says must be re-run before anything is reasoned from it: a run more than 15% either side of its arm's median, named slow or fast with each phase's move against that phase's median, largest first; a run that applied a different action count from the session's others (warned as it happens too); a run whose association moved while it ran; and a run that started on a different association from the first. The session folder is printed at the start and the end. The parsing and the verdicts are plain functions under `benchmark/pairs/`, tested in `test/benchmark/`; the channel width is the one field `WifiInfo` does not carry, so it is looked for in three places, printed as `?` when none has it, and every raw capture is kept beside the run to check it against.

An arm is a command, so where it lives decides what switching costs. **An arm on the desktop** — anything in the initiator, such as the `Applier`'s ordering — is a second `cargo build --release -p dsync-cli` from the other commit, and the session alternates binaries with nothing touched on the phone. **An arm on the phone** — anything in the serving side, such as the write path's mode step (§7.4) — is either a second cross-compiled `dsync` binary pushed over `adb push` (now that one exists, §14.1's opening paragraph), or, where the app itself is what is being compared, a second APK, given with `--switch <arm>='adb install -r <apk> && adb shell am start -n io.github.lumpsoid.dsync/.MainActivity'`; the driver runs it whenever the session moves to that arm and waits for Enter while Serve is started by hand. `adb install -r`, not `flutter install`, which uninstalls first and takes the pairing, the archive and the All-files grant with it. Nothing in `native/` or `lib/` carries a benchmark toggle for this: the "before" of a change is the build without it.

## 15. Defaults chosen where you were undecided

Override any of these before code starts:
1. **Symlinks**: skipped unless matched by a `follow` rule; hardlinks treated as plain files.
2. **Archive format**: JSON Lines append log with compaction, a concrete type rather than behind an interface (§8.2). Alternative: SQLite (a native dependency on both hosts, e.g. `rusqlite`).
3. **Protocol encoding (Rust): postcard, uniformly, for every control payload (§4.2, plan D5).** The Dart protocol split JSON control messages from a hand-rolled binary encoding reserved for `scan`'s replies, because JSON's per-entry overhead was measured as the one payload large enough to be worth a second format. That split does not exist in the Rust protocol: postcard is compact and cheap to decode for every message, `scan`'s replies included, so there is one control encoding rather than two, and no separate binary layout to hand-maintain. The historical measurement that motivated the Dart split, and the memory analysis of what a decoded listing holds resident against the Dart VM's garbage collector, are cut rather than carried forward — they were about `dart:io`'s JSON decoder and the Dart VM's object graph, neither of which the Rust core has.
4. **Exit codes**: as in §11.5, mirroring Unison's four-level scheme.
5. **Profile format**: TOML.
6. **mtime comparison**: exact equality of microsecond values. If a target filesystem turns out to round mtimes, the archive stores the rounded value it reads back, so the next run's fast path still matches.
7. **Pairing handshake**: mutual TLS 1.3 with a self-signed certificate, not Noise (§4.4). The failure-mode argument that settled it is unchanged by the Rust port: a broken certificate encoder cannot ship, because the TLS stack either completes a handshake with what it produced or refuses to load it, while a wrong Noise implementation still handshakes with itself and fails silently. The certificate is EC P-256 / ECDSA-SHA-256, generated with `rcgen` on `ring`. What a pairing pins is the certificate's public key, not its bytes (HPKP's and Syncthing's model), so `dsync pair renew` can re-issue it under the same key inside its ten-year validity without a single peer re-pairing; renewal is manual, because a credential other machines pin should not rotate unseen.

## 16. Deferred

- A borrowed ssh client library as the transport underneath the mobile head. Considered and rejected: it is the hot path on a phone, and a borrowed implementation puts the read loop, the buffering and the framing inside a library this project cannot tune — `peer://` over TLS (§4.4) is this project's own, on `rustls`, end to end.
- Serving a replica from the head *in the background*. The head now serves: `ServeController` (`lib/app/features/serve/`) starts the same `PeerListener::serve` `dsync agent --serve` starts, over this device's own identity and paired-device store, so a desktop can initiate a run against a phone and two phones can sync with each other. What is deferred is doing it unattended — Android's foreground service (§11.4) keeps only a live run, and there is no iOS background mode, so the listener lives and dies with the Serve page in the foreground, exactly as §4.4's enrolment endpoint lives and dies with the pairing window. Nothing on the serving side writes to the paired-device store, so it adds no writer to the lost-update hazard below. Also still deferred: telling devices already paired that the serve port changed (each side learns the other's port once, at pairing — from the payload one way, from the enrolment request the other — and a later change is re-entered by hand on the other device), and any cross-device interlock for two heads that start a run against each other at the same moment — each holds its own local lock and asks for a different profile id, so nothing deadlocks and nothing is corrupted, but two syncs of the same content run concurrently and the result is whatever reconciliation makes of it.
- A desktop head that dials a local `dsync agent --listen` instead of taking the replica itself — the same boundary as the entry above, seen from the other side. The case is one workstation running both the Flutter head and a long-lived agent, which is a minority configuration: the machine that stays up is usually the headless one, with no head to collide with, and the cheap answer to a collision is a legible refusal when the replica lock is already held. If it does turn up, the shape is already built: `--listen <socket>` is a unix-socket transport speaking the same protocol a remote peer speaks (§11.1, §4.2), so a head that finds a socket and dials it stays the *replica client* the entry above commits it to being — a client on the existing code path, not an IPC surface of its own — and exactly one process then touches the replica, the archive and the paired-device store. The last of those matters beyond the lock: `PairedDeviceStore` is whole-document load, mutate, atomic rename with no lock at all (§4.4), and every successful dial rewrites it through `recordConnection`, so two processes dialling from one machine can silently drop each other's entry. What this would *not* be is a management protocol — start, stop, status, schedule — which buys a second wire format, version skew between a head and a daemon that update independently, and an auth story for the local socket. Starting and stopping belong to the service supervisor (the entry below), and a read-only status view answers the question a user actually has. The head keeps its in-process local path for when no socket is there, so "open the app, sync, close it" sees no change.
- Storage Access Framework *content-URI* trees as a local replica on Android. The scanner and `LocalReplica` are plain `std::fs`, and what the Storage Access Framework grants is a `content://` tree URI, not a path `std::fs` can open; reaching such a tree needs a scan/replica implementation over it, which is `dsync-core` work, not a head concern. What the head does instead is take the *path* the directory chooser converts that URI to and prove it with a `dart:io` probe on the head's own side (list, write one entry, remove it, §3) — which on targetSdk 30+ requires All-files access (`MANAGE_EXTERNAL_STORAGE`, §3), asked for when the probe fails and refused with a message when it still does. So a folder outside the app's own container is reachable today, under a permission the user grants on a Settings screen; a folder that has no filesystem path at all (the Downloads provider, a cloud document provider) is what stays out of v1.
- mDNS discovery, to replace manual re-entry when a paired peer's last-known address (§4.4) has gone stale. Not taken for v0: it is a dependency, a multicast socket, an Android multicast lock, an iOS entitlement, and it does not work across subnets — exactly the desktop-to-server case a phone's address changing is most likely to hit. The last-known-address cache plus manual re-entry (§4.4) covers the common case for the price of one field and a write on every successful connect; mDNS is worth its cost only once that stops being true.
- **Readiness notification to a service supervisor (`sd_notify`), and socket activation.** Both are named here so neither is mistaken for an oversight; the process contract dsync does commit to is in `README.md` ("Running the agent under a service supervisor") and `contrib/`. `sd_notify` is systemd-only and linking `libsystemd` is exactly the coupling this section is suspicious of — `Type=simple` works today, and if readiness is ever actually wanted the protocol is one datagram to `$NOTIFY_SOCKET`, plain enough to send from `std::net::UdpSocket` with no library. Socket activation is the more interesting one, because a single `--listen-fd N` — serve a descriptor the supervisor already opened and bound, rather than binding one — would cover systemd, launchd and s6 at once. It is not built: nobody has asked, and until someone has, the flag would be a transport (§11.1 has three) maintained on speculation.
- **A true resume of a dropped `peer://` session on the same token** (step 2 of §11.3's re-dial). Today a re-dial is a second run: it reclaims the dead session only to end it, then scans and reconciles again. Picking the same session up where it stopped — its locks, its scan, its plan and the actions in flight — would save that walk and, when the plan changed, the re-asked review, at the price of a far side that keeps a dead session's state alive for a while and a protocol to resume it.
- Watch mode.
- Delta transfer (librsync via FFI, or a Rust implementation).
- Negated ignore patterns.
- Ownership / xattr preservation.
- Case-insensitivity is decided for v1, not fully closed by it (task a1d635; SPEC §3, §5.1). Detected per replica at scan time as a property of the filesystem actually mounted there — not assumed from the OS, since a case-sensitive-formatted APFS volume or a case-insensitive mount on Linux would otherwise get the wrong behavior. On a replica whose filesystem folds case, two live paths — or a live path and an archived one — that fold to the same key are reported and excluded the way §5.1 already excludes an unreadable path, rather than one silently overwriting the other. Refusing the whole run over one colliding pair was considered and rejected, for the same reason §5's per-path tolerance exists at all: one bad path should not cost the tree. This deferral used to cost nothing, because it applied only to Linux and Android, where it is either moot or, on Android's external storage, already a named exception (§3); it is not affordable now that APFS and NTFS are v1 targets (§3), which is why it is no longer a blanket deferral. What stays deferred: a same-run plan proposing two creates that differ only in case onto a replica where neither path exists yet — that replica's own scan finds nothing on disk or in its archive to collide with, so catching this needs the reconciler or apply phase to fold-check a plan's own paths against a destination known to be case-insensitive before either write lands, and that is not built. Unicode normalization (NFC/NFD converging to one file on a normalizing filesystem) is the same shape of problem for a different reason and gets the same treatment: deferred with the plan-level gap above, not separately, because whichever mechanism closes one closes both.
- **Not a deferral but the commitment that bounds this list: dsync runs no service, and depends on none it would have to run.** No account, no hosted discovery, no hosted relay, no phone-home. The project has to be able to outlive any infrastructure that ever appears around it — a user whose every helper service has vanished still has a working sync between two machines that can reach each other. What follows from that, written down so it is not re-argued each time reachability comes up: any future rendezvous or relay is a *protocol plus an optional binary somebody else hosts*, never a service this project operates, and dsync must work fully with none configured — degrading to exactly today's behaviour (§4.4's last-known address plus manual re-entry), not to broken. The reachability answers this project endorses are, in order: a direct route (IPv6, a LAN, a port the operator forwarded), then the user's own overlay network (WireGuard, Tailscale, Nebula), which costs this project no code and is the user's dependency rather than dsync's. Phone-to-phone across two carrier NATs is the one case that genuinely cannot be served without a third party in the middle; declining to serve it is a legitimate answer and is stated here as scope, not left as an apparent gap. Bulk transfer over Tor or a similar volunteer network is not the way around that: throughput is unusable for file sync, and the burden falls on a network donated for other purposes. This generalizes the instinct the mDNS entry above already acts on. There, a dependency is weighed and found too expensive for what it buys; here the same reasoning is taken to its end — a dependency the project could not survive losing is not on the table at any price.
- **A relay that knows nothing, hosted by whoever wants to.** Not for v1 — a placeholder, so the shape is settled before anyone needs it and so the constraint it has to satisfy is written down. It sits under the commitment above: a relay is a protocol plus a small binary anybody can host, never a service this project operates, and dsync works fully with none configured. **Why it can be trustless at all.** Authentication is already end to end — mutual TLS pinned to device public keys, verified at both ends against the paired-device store (§4.4). A relay that forwards bytes cannot read them, cannot impersonate either side, and cannot be made to; the worst a hostile relay achieves is refusing to forward. Nothing in the security model has to change to add one, and that is the whole reason this is worth doing rather than a compromise to be argued about. **What it would be.** Both peers dial *out* to the relay, so neither needs an inbound port — that is the entire point, and what distinguishes it from a rendezvous service, which only helps when one side is already reachable. The relay matches two connections and pipes ciphertext between them. **"Knows nothing" has to be designed, not asserted**: the payload is already opaque to it, the metadata is not.
  - **Blinded rendezvous keys.** If peers meet under raw device ids, the relay learns the identity graph — who syncs with whom — and can enumerate it. A key derived from the pairing instead — a hash of the device ids under a per-pairing salt both sides already share, rotated per session — gives the relay an opaque token to match on and nothing to correlate across sessions.
  - **No accounts, no registration, no persistent state.** A relay is a process with a port, not a database.
  - **Volume and timing are unavoidable**, and saying so is better than implying otherwise. A relay sees how much moved and when. That is the same traffic-analysis leak an on-path observer already gets, concentrated at one point.
  - **Abuse bounds are the host's problem, and have to be possible**: a connection cap, a bandwidth cap, an optional allowlist of rendezvous keys — so somebody can run one for their friends without running one for the internet. Separately, §4.4's own bounds on an unauthenticated connection — the hello and handshake deadlines and the caps on concurrent unauthenticated connections, in all and per address, counted from accept — apply to a relay-obtained socket exactly as they do to an accepted one; it is the same pre-authentication phase, arriving by a different route.
  - **What it would cost this project**, plainly: a second protocol with its own spec, wire format and tests, plus a binary to maintain. Not money and not uptime, but not nothing either.
  - **The existing code is already close**, which is why this is cheap to leave deferred. `PeerListener`'s accept path takes an already-connected TCP stream and upgrades it as the TLS server under §4.4's bounds; it does not care how that socket arrived, so a relay-obtained one feeds straight in. The client side would need a `PeerDialer::dial` variant taking a connected stream instead of host and port, with the `PeerPin` pinning unchanged. And `peer://<name>` already resolves through the paired-device store rather than DNS (§2, §4.4), so "reachable via relay R" is a new kind of cached address — not a new location syntax, and not a change to anyone's profile.

## 17. Run measurement

The tool measures its own runs, and both heads can show the measurements. This is instrumentation only: nothing in the engine reads these numbers or changes what it does because of them.

**Why it exists.** On a tree of many small files, a run's cost is dominated by *per-path round trips and fsyncs*, not by bytes. A copy costs one `Write` request per side, pipelined behind a bounded window (§4.2) and batched sixty-four to one archive commit (§7.3, §8.2) rather than one commit per path. Nothing else the tool reports can tell a run that was slow because the link was slow from one that was slow because it was chatty: §11.4's summary counts outcomes and §5.2's tally counts scan branches, and both are identical between the two cases.

**What D11 kept, and what it dropped (plan D11).** The Dart core's `--timings` report carried, beside the figures below, a set of diagnostics that existed to see *inside the Dart event loop*: event-loop lag on both ends, served read cadence, and a further split of the wire figures into `queue`/`wire`/`far`/`link`/`starved`/`held`/`settle`, plus a byte-banded breakdown of the transport's own send-coalescing and the `MeteredAgent`/`MeteredChannel` decorator pair that produced them. None of that survives the port. It was built to answer "is the isolate, the socket's own send queue, or the far side's disk the bottleneck" for a runtime — the Dart VM's single-threaded event loop — the Rust core does not have: `tokio`'s executor and the core's blocking writer threads (§7.1, §13) do not share the one failure mode, an event loop starved by other work on the same thread, that whole diagnostic apparatus existed to see through. What is kept is the product-facing half: the report a user, or this project debugging a real run, reads to answer "where did the time go" without needing a theory of the runtime underneath it.

**What is measured** (`native/domain/src/run_metrics.rs`; `RunMetrics`, rendered by `RunMetrics::render`):
- **Phases**, as §13's `Run` already divides them: `connect`, `lock`, `scan`, `reconcile`, `present`, `apply`, `compact`, `unlock`, `disconnect`. A phase a run never reached is absent (printed `—`) rather than zero, so "0 ms" always means "ran and was instant". `present` is the decider's turn — however long a user took to answer an interactive prompt or a conflict sheet — and is therefore the one phase outside the run's total: the total is the sum of every other phase, which keeps it comparable between runs while `present` stays visible in its own row.
- **Per replica, per replica operation** (§4.2's operations: `hello`, `lock`, `unlock`, `createRoot`, `scan`, `read`, `write`, `delete`, `removeEmptyDirs`, `commit`, `compact`, `close`): call count, total, mean and max wall time, plus the file content that replica's operations moved. All three of `scan`'s phases (§6.1) are one row, since they are one thing to a reader — what learning that replica's state cost — not three. Measured at the `Replica` boundary (§13's one border abstraction), the seam every unit of per-path work crosses on a local *and* a remote replica alike, so the initiating side's own archive-commit cost is counted exactly as a remote side's is.
- **The served write-stage summary**, carried once, on the last exchange of a session (`unlock`'s reply): the writer pool's own per-stage totals — `mkdir`, `probe`, `create`, `open`, `wait`, `write`, `mtime`, `mode`, `close`, `rename`, `stat` (§7.2, §7.4) — each a count, a total and a mean, for whichever replica served the writes, local or remote. Absent, not zeroed, when nothing was written or a run ends before `unlock`, so a report never reads a partial writer-pool summary as a complete one.
- **Bytes moved**, and **process CPU**: this process's user-plus-system CPU time over the whole run, from `/proc/self/stat` on Linux and Android and the platform's equivalent elsewhere, printed with **CPU time per MiB moved** — the one figure D11 added beyond what the Dart report carried, because it is the figure a language change is actually judged by (§16's task 538b18 phone-acceptance numbers).

**Measured, not modelled.** Every figure above is a counter or a clock read at the moment the thing happened, summed by the type that already holds it (`RunMetrics`, `ReplicaMetrics`, `OpStats`, `WriteStats`) rather than derived by arithmetic over other printed figures elsewhere. This is the same discipline the Dart report was built on and it survives the trim: a number this report prints is read off a clock, not computed from two other numbers that might individually be wrong in ways that happen to cancel.

**Where it surfaces.** `dsync sync --timings` prints the report to stderr after the summary — after, so it never comes between a reader and the outcome, and on stderr so `--json`'s stdout stays a clean JSON Lines stream (§11.4). The report's head — the `run:`/`cpu:` lines and the phase table — is pinned by `native/cli/tests/cli/timings.rs`, which `benchmark/pairs/run_timings.dart` also parses, so a layout change breaks a test before it breaks a bench session. It prints for a failed or interrupted run too. The Flutter head shows the same report behind a Timings action on the Run page once the run ends, with a copy button that yields the identical text `--timings` prints — the live, mid-run figures the Dart head used to show there are gone with the diagnostics that fed them; a phone is still the device whose cost profile exists nowhere else, and the realistic path from a number on it to whoever is fixing the protocol is still a paste into a message, taken after the run rather than watched during it.

### 17.1 Current numbers

Desktop → phone over `peer://`, measured 2026-09-25 on trunk 976275d: release CLI on the desktop, release APK serving from its Serve page on a OnePlus 6, both on Wi-Fi (5 GHz ch36). Each pass is six runs through `benchmark/interleaved_pairs.dart` with the same binary on both arms. The ranges cover all six runs. Task 538b18 holds the targets and the first acceptance run (09-24).

| Pass | Median (range) | Target |
|---|---|---|
| Fresh pull, 25 × 4 MiB (81.5 MiB) | apply 3.23 s = **25.2 MiB/s** (22.8–29.9) | ≥ 22 MiB/s |
| Fresh pull, 1,500 files (19.4 MiB) | total 7.57 s = **5.0 ms/file** (4.8–5.6) | ≤ 5.5 ms/file |
| Overwrite, 1,500 files | total 1.71 s = 1.14 ms/file; apply 1.18 s = **0.79 ms/file** (0.75–1.25); phone rehash scan 0.33–0.45 s | apply ≤ 1 ms/file |

The fresh small-file pass is ~10% slower than on 09-24, inside the link's ~13% drift between sittings. The overwrite apply went from borderline (0.94–1.18 ms/file) to under target with 32 writes in flight (§7.1): the phone's writers are ~9.2 of 16 busy, up from ~6. Opening a file costs ~2.2 ms per file on the phone, setting its mtime ~1.9 ms and closing it ~1.1 ms. These three still dominate the phone's per-file cost.

**CPU.** The desktop CLI's figures come from its own `--timings` report: 2.1–2.3 ms per MiB on large files, 0.52–0.63 s per 1,500-file fresh pull (~0.4 ms/file) and 0.33–0.35 s per 1,500-file overwrite. The phone app's figures are read from `/proc/<pid>/stat` (user + system) across a whole pass. They include each pass's untimed setup and cleanup syncs, so they are upper bounds: **≤ 22 ms/MiB** on large files (the Dart core took 84–133), ≤ 5.6 s per fresh 1,500-file pull and ≤ 2.5 s per overwrite.

**Memory.** The desktop CLI's peak RSS is 23.5–28.8 MiB per sync, and ~14 MiB for a sync with nothing to do. The phone figure is for the whole Flutter app process, not the core alone: RSS 182–206 MiB, with peak RSS (`VmHWM`) going from 212 to 222 MiB over the three passes.
