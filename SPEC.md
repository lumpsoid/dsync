# Bidirectional File Sync — v0 Specification

Working name: `dsync` (placeholder, rename freely).

## 1. Goals and non-goals

**Goals**
- Bidirectional synchronization of regular files between two replicas.
- No data loss: nothing is overwritten or deleted unless the reconciliation rules say it is safe or the user explicitly confirmed it.
- Minimal resource use: skip work whenever the stored state allows it.
- Same core engine drives a CLI and, later, a Flutter app.

**Non-goals for v0**
- Continuous / watch mode.
- Delta (partial-file) transfer.
- Ownership, ACLs, extended attributes.
- More than two replicas per run.
- A transport this project does not own the read loop of. In-process, ssh, and dsync's own socket transport in its two forms — unix-domain (§4.2) and paired TLS over the network (§4.4) — are what v0 speaks.

## 2. Concepts

- **Replica** — a directory tree at a location. A location is a local path, `user@host:path`, `ssh://[user@]destination:path`, `unix://<socket-path>:<replica-path>`, or `peer://<device-name>:<replica-path>`.
  - The first two are told apart by ssh's and rsync's own rule: a colon separates a host from a path only when it comes before the first `/`. That keeps `./log:old` a local path, and it is why `notes` is a relative path rather than a host.
  - That rule can only describe a destination shaped like a hostname, and `ssh` reaches plenty that are not: a `~/.ssh/config` `Host` alias, a `.host` name, `unix/run/ssh-unix-local/socket` for a socket-activated sshd. `ssh://` means "this one is for ssh, hands off": everything between the scheme and the first `:` is handed to `ssh` as its destination, verbatim, slashes included — which is why the colon separates it from the path and a `/` cannot.
  - `unix://` is the same shape for the transport that needs no `ssh` at all: everything between the scheme and the first `:` is the filesystem path of a socket a `dsync agent --listen` is already bound to (§4.2). Both halves are full of slashes, so only a colon could separate them. No `user@` is split off — there is no user to name, because what decides whether the connection is made is whether the process can open the socket, which is the filesystem's answer. A socket path containing a `:` is not addressable, the same limit an `ssh://` destination has.
  - `peer://` is the same shape once more, for a device reached over dsync's own authenticated network transport (§4.4) rather than ssh or a local socket. `peer://`, not `dsync://`: what follows the scheme here is not a transport, it is the name of a peer — the thing being addressed, not the means of addressing it. Everything between the scheme and the first `:` is the name this host gave that device when it was paired, not a host and not an address; it resolves through the paired-device store (§4.4), never through DNS or the network. No `user@` is split off, for the same reason `unix://` splits none: there is no user to name, because what decides whether the connection is made is whether the store still trusts the certificate that name currently resolves to, which is the store's answer and not a credential anyone types. A device name containing a `:` is not addressable, the same limit `ssh://` and `unix://` already carry.


- **Root** — the top directory of a replica. All paths are relative to the root.
- **Profile** — a named pair of replicas plus options (ignore rules, thresholds). Lives in a TOML file.
- **Agent** — the component that has direct filesystem access to one replica. Every replica is accessed through an agent, whether local or remote.
- **Archive** — per-replica record of the state of every synced file as of the last successful propagation for that path.
- **Run** — one invocation: connect to both agents, scan, reconcile, present, apply, exit.

## 3. Platforms and heads

- Targets: Linux, macOS, Windows, Android, iOS. All five are v1 (task a1d635) — not aspirational, and not free: each bullet below names the cost and whether it is paid now or named as a deferral, so nothing here becomes true by omission.
- Heads: `cli` (Linux, macOS, Windows; Android via Termux) and `app` (Flutter; Android, iOS). Both depend on `core`; `core` has no Flutter dependency. iOS has no `cli` head and cannot get one: the platform grants no arbitrary process execution outside an app bundle, so `app` is the only way onto it.
- Pinned Dart SDK version in `pubspec.yaml` of every package, on every target alike.
- **Linux, macOS and Windows run the whole test suite in CI** (`.github/workflows/test.yml`: `dart analyze` and `flutter test` on all three, plus `dart test` on Linux, on the pinned toolchain). A test that needs a unix socket, a POSIX signal, a `/bin/sh` stand-in for `ssh` or a POSIX far end declares `!windows` and runs on the other two; the real-ssh test additionally skips, naming the reason, on a runner with no sshd. Everything else runs on all three — including the real-filesystem writes `LocalAgent` makes in `ad_hoc_sync_e2e_test.dart` and the case-folding probe, which asserts folding on macOS and Windows and none on Linux — so what the bullets below say about a macOS or Windows replica is exercised there, not only reasoned about.
- The crypto §4.4 is built on is already portable, and costs nothing here: `pointycastle` is pure Dart, depending on nothing beyond `collection` and `convert`, and the pinned SDK above is 3.13.3 everywhere. What follows is our own code, not the dependency graph.
- **State directory is not XDG-only.** `resolveStateDir` (`lib/dsync_core/state_dir.dart`) switches on a `StateDirPlatform` value: `$XDG_STATE_HOME`, else `$HOME/.local/state`, on Linux; `~/Library/Application Support` on macOS; `%LOCALAPPDATA%` on Windows; and a host-supplied base directory for the Flutter heads, which resolve it through the platform's own API and hand it down (§8.3). The platform is passed in, not read from `dart:io` inside the function, so every branch is a unit test with a hand-built environment map; a missing variable throws rather than resolving to a path spelled `null`. This is v1 and non-negotiable: §4.4's device identity, the paired-device store, the archive and its lock all live under it (§8.3), so nothing else works on a platform whose branch is wrong.
- **Root-relative paths stay `/`-normalized on the wire and in the archive, on every platform** — git does the same, and it is what keeps one archive portable between a Windows and a Linux replica. The conversion this requires happens at each filesystem boundary, in both directions, through a `package:path` `Style` the CLI edge resolves once (`HostPlatform.pathStyle`) and threads in as a plain value — never a `Platform.isWindows` read inside `core`, so a test can hand either side a Windows-spelled tree without a Windows host. The read side is `scan/scanner.dart`: a child's own name comes from a `Context` in that `Style`, so a Windows agent's `Directory.list()` handing back paths spelled with `\` still yields `/`-joined root-relative paths for the scan result, the wire and the archive. The write side is converted too (task 0b8e3c): `resolveWithinRoot` runs its escape checks on the `/`-normalized form and then joins the segments onto `rootPath` through a `package:path` `Context` in the same injected `Style`, so a Windows host emits `\`-joined native paths from its own code rather than relying on Win32's tolerance for `/` mixed with a native root — a tolerance the extended-length `\\?\` prefix does not extend. `_parentOf` is unaffected: `removeEmptyDirs` walks up on the root-relative form and rejoins each ancestor, so no native path is ever split there.
- **Mode bits (§7.4) do not exist on Windows.** `_applyMode` (`lib/dsync_core/agent/local_agent.dart`) calls `chmod(2)` through `dart:ffi` (`agent/posix_chmod.dart`); Windows has no `chmod` to call — its C runtime spells a different thing `_chmod` — and its model, ACLs, is not a stricter or laxer version of POSIX bits, so v1 does not attempt to translate one into the other. `mode` is simply absent there: `_applyMode` recognizes a Windows replica ahead of time — `LocalAgent` takes `isWindowsReplica`, resolved once at the CLI edge (`HostPlatform.isWindowsReplica`) alongside the path `Style` above, and starts `_chmodUnavailable` latched — rather than discovering it empirically by a call guaranteed to fail. The empirical latch still exists for every other host: a `ChmodUnavailable` raised for any other reason latches the same flag once, not once per file. A `chmod` that *runs* and is refused by the filesystem (Android's external storage, below) does not latch it and is not an error — §7.4's "archive what actually landed" already covers that case. The archive records whatever `FileStat.mode` actually reports on Windows, which §7.4's existing rule ("record the actual post-write state … rather than the intended one") already states in general terms — Windows is that rule's second occasion, not an exception to it. That write runs on a real Windows host in CI (above), so the call is exercised; what the value it records *means* there is the Windows claim no test asserts. The Dart SDK's own Windows `dart:io` derives a pseudo-mode from the read-only attribute rather than reading a permission set, so the archived `mode` is expected to be one of a few values keyed to that one bit — documented behavior, not a verified one, and nothing acts on it beyond recording it (`LocalAgent.writeFile`'s own comment says the same).
- **Case-insensitive filesystems are a correctness issue, not cosmetic, once macOS and Windows are targets.** APFS and NTFS are case-insensitive by default, as Android's external storage already is (below). §16 states the v1 policy and what it does not catch.
- **Symlinks cost nothing here.** A `follow` rule (§5.1, §9) resolves an existing link and syncs its target's *content* as a plain file at the link's path; dsync does not create a symlink at the destination, on any platform — there is no symlink-creation call anywhere in `lib/`, only `Link(...).resolveSymbolicLinks()`, and only to read. Windows' privilege requirement for creating a symbolic link (Developer Mode or `SeCreateSymbolicLinkPrivilege`) gates an operation this project never performs, so it is not a v1 cost and not a deferral either — there is nothing here to defer.
- **iOS is a target within its sandbox, not a general-purpose one.** A replica root is confined to the app's own container (`Documents/`, `Library/`, the rest of what the sandbox grants by default) plus whatever directories the user has separately granted through `UIDocumentPickerViewController` and kept reachable via a security-scoped bookmark. It cannot sync another app's data or an arbitrary path the way the other four targets can; that is a stated platform limitation, not a defect. The `app` head's location picker is built against that constraint: it offers folders under the app's own documents directory, and folders the user chooses through the platform's own chooser — never a free-text path it cannot actually resolve. A chosen folder is proved usable by a `dart:io` probe (list, write one entry, remove it) before it is offered as a replica root, because only the filesystem can answer that question: on iOS the picker's grant lasts the session but not a relaunch until a security-scoped bookmark is persisted (task c3f70e), and on Android the grant that makes a chosen *path* openable is All-files access, not the picker's own tree-URI grant (§16).
- Android note: Android's shared ("external") storage does not preserve POSIX permission bits and is case-insensitive. The engine must not fail when a metadata write is rejected (see §7.4), and must record the *actual* post-write state in the archive rather than the intended one. Whether mtime can be set on a given Android path is verified on the device early in development; the archive rule above keeps the engine correct either way.

## 4. Replica access

### 4.1 Location resolution
A location `user@host:path` is resolved before the run. If `host` is `localhost`, an address of this machine, or absent, the agent runs **in-process**. Otherwise the agent runs as a **remote process**. Both cases use the same `Agent` interface; the caller does not know which one it got.

A location written with a scheme — `ssh://`, `unix://`, or `peer://` (§2) — is **remote by declaration**, and no address is consulted for it. Inference is what the form opts out of: a config alias can point anywhere, including back at this machine, and a unix socket, a `.host` name, or a device name has no address to compare at all — there is nothing honest to guess with. Asking `ssh -G <destination>` what ssh itself resolved was the alternative considered; it was rejected as a process spawn and a second parser per remote side that still could not answer for the shapes that motivated the form. It also follows that reaching *this* machine through its own `ssh` is a thing a user can ask for, rather than something quietly turned back into an in-process run.

### 4.2 Remote agent
The channel is a bidirectional byte stream behind a `Channel` interface, and the same protocol runs over every transport. Two exist.

**Over ssh.**
- The same binary is installed on the remote host and started as `dsync agent --stdio` over `ssh`, by spawning the system `ssh` executable. That session serves exactly one replica and ends when its input closes.
- The destination is handed to `ssh` exactly as the location gave it and is never resolved, rewritten, or probed here. Whatever `ssh` accepts as its destination argument, dsync addresses.

**Over a socket.** `dsync agent --listen <socket path>` binds a unix socket and serves it, reached by a `unix://` location (§2). It is dsync's own transport: no system binary, which is what a head that cannot rely on one needs (§3, §16), and the read loop and buffering are this project's to tune rather than a borrowed library's.
- A listener outlives a session. It stays up, accepting until the process is signalled, and serves connections concurrently — one `AgentServer` per connection, which holds no state between them. Two sessions against the *same* replica are already handled by §4.3's lock; two against different replicas have nothing to contend over. A session that fails is reported and closed; it does not take the listener down, unlike `--stdio`, where the process *is* the session.
- The socket file is unlinked when the listener closes. One left behind by an agent that was killed outright is cleared on the next start, after connecting to it proves nothing is listening there.
- **It authenticates nobody, and neither does ssh, and neither needs to (task 83800f).** `hello` names the root path and the agent is rooted wherever it says. Over ssh that is harmless because the connection was already authenticated as that user before this protocol ever saw a byte. Over this socket it is harmless because the only gate is the filesystem: on Linux, a connect is refused if the process cannot open the socket, which is why this transport is unix-domain and local by construction. Neither transport requires the pairing §4.4 defines, and that is a decision, not an accident of which code path got touched first: ssh already vouches for the peer, so a second authentication step under `hello` would be authenticating a connection that is already authenticated; and this socket is local by construction, where the filesystem is a real gate, so requiring pairing on top of it would be friction against no threat and would make `dsync agent --listen` useless for a same-machine sync — the plain case the pairing umbrella (589b90) leaves alone. Pairing is what stands in for both of those once a socket leaves the machine, where the connection is no longer already-authenticated the way ssh's is and there is no filesystem to gate it the way this one's is. §4.4 now gives that replacement — authentication and the encryption TLS carries with it — a full design: a self-signed certificate pinned per device, checked at the transport handshake, plus what a paired device may reach once it is on the wire. That transport is `dsync agent --serve` (§11.1), reached by a `peer://` location (§2).
- Two things about a remote replica are configurable **per replica**, since SPEC §4.1 allows a pair of two remotes and two hosts need not agree on either: the **options** passed to `ssh` before the destination (`-p`, `-i`, `-o …`), and the **command** that starts the agent on the far side, which defaults to the bare word `dsync` resolved on the remote *non-interactive* PATH. Both come from the profile (§12) and the command line (§11.2). `~/.ssh/config` already answers port, identity, user and proxy command per destination and remains the better place for them; the options exist for what it cannot say, and for a one-off.
- Protocol: framed messages over the stream. Frame = 1 byte type + 4 byte big-endian request id + 4 byte big-endian length + payload. Type `0` = UTF-8 JSON control message, type `1` = raw file bytes, type `2` = a successful `scan` reply in the binary encoding of §15.3, type `3` = a heartbeat: empty payload, never answered, carrying nothing but the fact that the sender is still there. A *failed* `scan` is a type `0` error like any other operation's, so the type byte is what distinguishes them. First exchange is a version handshake; mismatched protocol versions abort the run. The protocol version is **3**; version 2 committed one path per exchange (`archiveCommitUpsert`/`archiveCommitDelete`) where this one batches them behind a single `archiveCommit`, and version 1 had no request id and a 5-byte header.
- **Requests are pipelined behind the request id (task 0f7dfc).** The initiator allocates an id per operation and every frame of that operation — request, reply, and each `fileBytes` chunk in either direction — carries it, so a reply is matched by id rather than by arrival order and two operations' frames may interleave. Id `0` belongs to no request: it is what the two version frames and every heartbeat carry.
  - **Why it is worth a wire change.** Measured phone-to-desktop over `peer://` (§17), a one-request-one-reply operation cost 8.5 bare round trips. That is 802.11 power save: once the phone transmits its request and falls silent, the chip powers its receiver down and the desktop's reply waits at the access point for the next beacon. It is a receive-side latency, it does not scale with bytes, and it lands on every one of the ~28,000 strictly sequential requests a 14k-file tree costs. Holding several operations open means replies arrive while later requests are still going out, so the radio never gets a doze window — the same effect a 50 ms heartbeat produced artificially in the diagnostic run, but as a consequence of doing real work rather than of burning battery.
  - **A bounded window, and what may enter it.** At most 32 operations are outstanding on one connection — twice what §7.1 runs at once, since an action's operations against one replica are sequential. The per-path operations enter the window — `readFile`, `writeFile`, `delete` and `archiveCommit` — and two operations on the same path never overlap and keep the order they were issued in, since `writeFile` then the commit carrying that path is what §7.3 rests on. `archiveCommit` is about many paths at once, so it enters behind the last operation issued on *every* path in its batch and becomes the tail of all of them; in an apply that costs nothing, since a path's record is only handed over once its own `writeFile` or `delete` has returned. Every other operation is a barrier: `hello`, `lock`, `unlock`, `scan`, `compact` and `removeEmptyDirs` wait for the window to drain and hold everything else until they finish. The first five are barriers because each changes what the whole replica means to the session. `removeEmptyDirs` is the one that is a barrier on its own merits: it reaches *ancestors* of the path it is given (§7.5), so it can remove a directory a concurrent `writeFile` on an unrelated path is about to write into. §7.5 keeps it out of the apply loop entirely, so that barrier finds an empty window.
  - **Failure is per operation; a transport failure is everyone's.** A failed operation's reply comes back under its own id, so it fails that caller alone and the rest of the window carries on and reports its own outcomes — which is what §7.6 already asks of a run. A failure of the *connection* — the channel closing, or bytes that do not decode — fails every outstanding operation and every later one, because nothing can be matched to anything any more; that is fatal for the run (§11.5 exit 3) however many operations it took down.
  - **The far end keeps no window of its own.** It answers each request under the id it arrived on and dispatches concurrently. The initiator already bounds how many are outstanding, and it cannot send a barrier until every earlier reply is in hand; a second, smaller bound on the far end would deadlock a peer waiting on replies that side is refusing to start.
  - **`Channel.send` must tolerate overlapping calls**, since several operations are sending. Whole frames only: a frame split down the middle by another's is decodable by nobody.
- **Nagle is off, deliberately (task fd83ac).** Every TCP socket this protocol runs over — dialed or accepted — sets `TCP_NODELAY`. The protocol is request-then-wait-for-reply and an idle sender flushes each frame on its own, so every write is small with nothing queued behind it: exactly the shape Nagle plus the peer's delayed ACK punishes, holding each frame back until the previous one is acknowledged tens of milliseconds later. Measured over a real `peer://` run (§17), a one-request-one-reply archive commit averaged 84.7 ms against a 10.0 ms bare round trip. Nothing observable on the wire changes — the same bytes in the same order, sooner — which is why it is written down: it is invisible when it is working. A unix socket is left alone, since `TCP_NODELAY` is a TCP option and `setOption` fails outright on one rather than ignoring it.
- **Frames queued behind a write in flight leave together (task 9d2158).** A sender that is not waiting still writes one frame per `add`-and-`flush`, so the bullet above holds unchanged; but while a write is in flight, later frames queue, and when it finishes everything queued goes out as one `add` and one awaited `flush`. There is no timer and no linger — the batching is a consequence of backpressure, not a policy on top of it, so an idle connection is byte-identical to one-frame-per-write and under load a batch forms exactly as large as the sink is behind. It was built because measured phone-to-desktop over `peer://` (§17), a small-file action cost 3.13 sends averaging 4.1 KiB and — on a model since discarded — 82% of its time looked like fixed per-send cost. **It does not buy throughput, and that is measured rather than assumed.** Re-running the commit that introduced it, both sides, against the same tree and pair, gives an apply of 61.4 s where the code before it gave 62.4 and the code after it gives 62.5 — every per-operation column inside 1.5%, `link` included. The 1.63× it was first credited with was one run, and six runs since sit between 56.6 and 63.1 s. It is kept because it is correct and costs nothing: the sink's flushes are strictly serial and total 13.1 s of a 62.5 s apply, ~7% of an action, so there was never 1.63× in it to win. Do not cite it as a throughput win, and do not build on the assumption that the send path is the constraint. `Channel.send`'s contract is untouched: it still returns once that caller's bytes have been flushed. Two consequences are not free. A failed write fails **every** caller in its batch, where before it failed only its own — consistent with "a transport failure is everyone's" above, and the writes queued behind a failed batch still go out. And the queue is bounded twice over: each sender awaits its own `send` before issuing another, so it holds at most one frame per concurrent sender — 32, by the window above — and one write is capped at 1 MiB, which joins fewer frames but never splits one.
- **A bounded silence, on the transport that needs one (task 40812e).** A type `3` heartbeat is sent by either end once it has sent nothing for a few seconds, and a connection whose peer sends nothing at all — not even one of those — for a multiple of that interval, while this side is waiting to read, is failed with an error naming the device (§11.5 exit 3). It applies to the `peer://` transport of §4.4 and to nothing else: a `unix://` peer is a process on this machine, so a dead one has its socket closed by the kernel and the reader gets EOF, and `ssh://` runs under the system `ssh`, which watches the connection itself and is configured out of band (`ServerAliveInterval`) by whoever runs it. Only `peer://` is dsync on both ends of a raw socket with nobody else looking, where the OS default keepalive is two hours and a slept laptop or an expired NAT mapping otherwise leaves a run waiting forever. The heartbeat is what lets the deadline be short: a `scan` of a large cold tree sends nothing between the request and its reply, so without ticks the bound would have to exceed the worst-case scan; and both ends send them, since a client sitting at an interactive conflict prompt (§11.3) is legitimately silent for as long as the user takes to answer. Every reader skips a heartbeat rather than treating it as the next frame it was waiting for.
- Agent operations: `hello`, `lock`, `unlock`, `scan`, `readFile` (streamed), `writeFile` (streamed, temp + rename, set mtime/mode), `delete`, `removeEmptyDirs`, `archiveCommit`. A heartbeat is not among them and never will be: it has no `op`, no reply, and no agent behind it — it is a property of the connection, not a request on the replica.
- `hello` carries the replica this connection should serve (root path — unexpanded — profile id, side, job count) and replies with that replica's archive last-commit time (or `null`), since the initiator cannot `stat` an archive on the remote host.

### 4.3 Locking
Each agent takes a lock file in its state directory for the replica before scanning and releases it at exit. A held lock aborts the run with a fatal error. This is what makes a listener (§4.2) safe to serve concurrently: two sessions reaching for the same replica meet the same lock a second `dsync` process would.

### 4.4 Pairing and the authenticated transport
Extends §4.2's socket transport past the local machine (task 4ec17f, under the pairing umbrella 589b90). §4.2's unix socket gets its access control from the filesystem for free; a socket that leaves the machine has to build its own, and the requirement is the same one stated there — an unpaired peer must not reach the version handshake, `hello`, or any frame parser, not be turned away by one.

**TLS with a self-signed certificate, via `dart:io`, not Noise.** `SecureServerSocket.bind(requireClientCertificate: true)` and `SecureSocket.connect(onBadCertificate:)` are the pinning hooks; the handshake itself runs in BoringSSL, inside the Dart VM, on every target platform (§3). The alternative was Noise (XX or KK, on `cryptography`'s X25519 keys and the Cacophony test vectors) — a genuine second option, not a formality, since `cryptography` ships X25519 where `pointycastle` only carries its OID, so taking route A did not mean dodging a hand-written elliptic curve. It was not taken because the two failure modes are not symmetric. A broken certificate encoder is loud: BoringSSL either completes a mutually-authenticated handshake with the bytes this project generated or refuses to load them, so a wrong `TBSCertificate` assembly cannot ship — it cannot connect to anything, including a second copy of itself. A subtly wrong Noise handshake state machine has no equivalent gate: two copies of the same bug still complete a handshake with each other, and the failure is silent and security-relevant rather than a thrown `HandshakeException`. Put the security protocol in BoringSSL, which the world already attacks; keep a data-format problem — the certificate encoder — for this project to own.

**The identity certificate.** `generateDeviceIdentity` (`lib/dsync_core/identity/self_signed_certificate.dart`) is what every peer generates once and keeps: an EC P-256 keypair (`ECCurve_prime256v1`), assembled into a version-3 X.509 certificate, self-signed with ECDSA-SHA-256 (issuer and subject are the same `RDNSequence`: a `commonName`, which is cosmetic since pairing pins the certificate's public key rather than its subject, and a `serialNumber` attribute holding the first eight hex characters of the key's own SHA-256 — the same digest the device id below is made from, so it is unique per identity and unchanged by renewal). **The subject has to differ between devices, and that is the `serialNumber`'s whole job**: a peer is trusted by having its certificate installed as a trust anchor (below), BoringSSL's trust store looks an issuer up by subject name, and two anchors with byte-identical subjects collide there — the store answers with whichever was added first, and every other device sharing that subject is refused with `CERTIFICATE_VERIFY_FAILED: self signed certificate`, an error naming nothing that leads to the cause. The Flutter head names every identity it generates `dsync-app`, so this is what a desktop paired with two phones would hit. The distinguisher is in `serialNumber` rather than appended to the common name because the common name is what a pairing screen offers as the device's label. Validity defaults to 3650 days and is backdated an hour from the moment of generation, so two clocks that disagree by a few minutes don't read a brand-new certificate as not-yet-valid. It is renewed, never automatically, by `dsync pair renew` (`renewDeviceIdentity`): the same private key, the same common name, a fresh serial and validity window with the same backdating, so the device id below is unchanged and no peer has to pair again. `dsync pair list` and the run header warn `certificate for <device> expires in N days` inside a thirty-day window, for this host's own certificate and each paired peer's; a handshake refused because a certificate has expired is reported as that, naming the side to renew, distinct from the "no pairing" and "unreachable" errors below. Two extensions, both marked critical: `basicConstraints` with `cA: TRUE`, and `keyUsage` with `digitalSignature | keyAgreement | keyCertSign`. The private key leaves the generator as PKCS#8, the spelling `SecurityContext.usePrivateKeyBytes` reads — SEC1's `EC PRIVATE KEY` is not accepted. None of this is negotiated per connection: there is exactly one shape, and the encoder that produces it — about 170 lines of code on `pointycastle` primitives, measured and spiked before being written for real — cannot produce any other.

**Why `cA: TRUE`.** This is the one requirement that isn't obvious from the TLS APIs alone. `SecureServerSocket`, unlike `SecureSocket.connect`, has no `onBadCertificate` hook — BoringSSL's own verification runs before any application code sees the connection, and a failure there kills the handshake before a paired peer could be recognized. Pinning a peer therefore has to happen by installing its certificate as a trust anchor, through `setTrustedCertificatesBytes` and `setClientAuthoritiesBytes`, and a self-signed *leaf* — `cA: FALSE` — cannot be its own issuer; BoringSSL refuses it with "unable to get local issuer certificate" before any pin is ever consulted. Making the identity certificate its own CA is what lets it stand in as a trust anchor at all. Key pinning — `onBadCertificate` comparing the presented certificate's device id (its `SubjectPublicKeyInfo` hash) against the pinned one, and `_resolvePeer` resolving `peerCertificate`'s device id against the store on the server side — layers on top of that verification, never instead of it: a connection needs both a BoringSSL-valid chain (satisfied because the peer's certificate is its own trusted issuer) and the key a pairing recorded. A same-CN, different-key impostor certificate fails the second check even though it would pass the first. Pinning the key rather than the certificate's bytes is what makes renewal possible without re-pairing — the same reason the device id hashes only the key — but BoringSSL's layer is not so forgiving: verified empirically (`agent_listener_secure_test`), a self-signed leaf passes only when the trust store holds those exact bytes, and a renewed certificate is not chained to its predecessor by name and key. So a client that pinned the old certificate accepts a renewed server at once, through `onBadCertificate`, and stores the bytes it saw; a server anchored on a client's old bytes refuses that client's renewed certificate at the handshake until it has learned the new bytes — which it does the first time it dials that peer itself. After `dsync pair renew`, therefore, each peer picks the change up on its next connection *to* the renewed host, and until it has, syncs started from the renewed host toward it are refused; the command says so.

**Device id: SHA-256 of the certificate's `SubjectPublicKeyInfo`, hex, grouped.** Syncthing's shape is a hash of the device certificate, rendered for humans; the deliberate choice here is *what* gets hashed. Hashing the whole certificate DER ties the id to the serial number and the validity window, both freshly generated if a certificate is ever renewed under the same key — which would silently change a device's id out from under an otherwise-unchanged pairing. Hashing only the `SubjectPublicKeyInfo` ties the id to the one thing that cannot change without it actually being a different device. It is rendered as lowercase hex in 4-character groups (`a1b2:c3d4:…`, sixteen groups from the 32-byte hash) — long enough to print in a paired-device list and in `dsync pair`'s output (task bc68c7), and grouped for the reason a hardware key fingerprint is: a human reading two of them side by side, or aloud, gets fixed points to check against instead of one 64-character run.

**The enrolment token, and what photographing the QR gets an attacker.** The QR carries three things: the desktop's certificate (or its DER — the trust anchor itself, and public by nature; there is nothing to protect by keeping it secret), an address hint, and a single-use, time-bounded enrolment token. The phone scans it, connects once, presents the token as proof it saw the QR, and registers its own certificate as a paired device; the token is burned on that first successful use, regardless of whose connection redeemed it. An attacker who photographs the QR — over a shoulder, from a recording — gets exactly the three things a legitimate phone would, and *can* complete enrolment in the phone's place, provided they get there first and inside the token's window. What bounds that: the window is short, the token is single-use (so the real phone and an attacker cannot both succeed — whichever arrives second fails, which is at least a visible signal rather than a silent compromise), and the desktop's enrolment endpoint is off by default and open only for the duration of one pairing operation — a photograph used outside that window, or reused after the token inside it is burned, gets nothing. This is a real cost against two-scan pairing, where the phone's identity also travels out of band and there is no token to steal at all; it is accepted because the same mechanism is what lets `dsync pair` (task bc68c7) work by exchanging text between two machines that both lack a camera, which two-scan pairing cannot do.

**The head reads that QR, and the declarations stop where the scan does (task 57da0f).** The `app` head takes the payload either way: typed or pasted in as the `dsync-pair:v1:` line, or scanned off the symbol `dsync pair show` renders on stderr. Both end in one place — `PairController.submitPayload`, which decodes the payload, checks the version, and maps every failure of the exchange to its own rendered line — with the camera entering through `PairController.onPayloadScanned`: that same path, plus the one guard a source that keeps firing needs. `MobileScanner` reports every frame the code stays in view, and the token inside that code is single-use, burned by the desktop on its first successful redemption, so an unguarded repeat would be *refused* by the far end and the user would be shown "the desktop refused this pairing" over a pairing that had in fact just succeeded. A scan is therefore dropped while an exchange is in flight and once one has succeeded, which is a read of the page's own sealed outcome ("submitting" and "succeeded" are two of its cases) rather than a second flag kept in step with it; a *failed* attempt is not dropped, since a fresh `dsync pair show` code after a refusal is exactly the retry the refusal's own wording asks for. The reader is `mobile_scanner` — the *decoder*, against the `qr` pin that *encodes* the symbol the CLI prints; neither replaces the other, and the CLI links neither. The permissions declared are exactly what that scan uses and nothing more: `CAMERA` in `android/app/src/main/AndroidManifest.xml` and `NSCameraUsageDescription` in `ios/Runner/Info.plist`. A scan of an address the user showed the camera is an outbound TCP connection to a literal host and port, so neither `NSLocalNetworkUsageDescription` nor a `_dsync._tcp` Bonjour entry is declared: iOS asks for local-network access to *discover* and *advertise* peers, not to connect to one it was told about, and a speculative entry is a prompt the user is asked for nothing. The Android release manifest also declares `INTERNET`: Flutter gives it only to the `debug` and `profile` source sets, so until the main manifest had it, every network connect the head made worked in development and failed in a release build. It also declares `MANAGE_EXTERNAL_STORAGE`, for a replica root the user picks outside the app's own container: the directory picker's grant covers the `content://` tree URI it hands back, not the path that URI converts to, and `Scanner` and `LocalAgent` are plain `dart:io` — they open paths — so on targetSdk 30+ All-files access is what makes such a folder readable and writable at all. It is the one permission here granted on a Settings screen rather than a dialog, so it is asked for explicitly and a refusal is not fatal: the app-private documents directory remains a replica root that needs no grant.

**Revocation is local, not a network operation.** `dsync pair revoke` removes a device's certificate from the paired-device store (§8.3's state directory) on whichever side it is run on; that side stops installing the removed certificate as a trusted client authority or trust anchor, so the next connection attempt from it fails the same BoringSSL verification a stranger's would. No message is sent to the revoked device — sending one would mean trusting a channel to a peer this side has just decided not to trust, the same contradiction §4.2 and the pairing umbrella rule out for an unpaired peer generally. A device unpaired while it was offline therefore learns nothing at the moment of revocation; it finds out the next time it tries to connect, when the handshake fails exactly as it would for a device that was never paired — no distinct "you have been removed" error, because producing one needs the trust the revocation just withdrew. Unpairing is consequently one-sided by construction: running it on the desktop stops the desktop from trusting the phone, but the phone's own store still trusts the desktop until the phone — or someone with access to it — removes that entry too. A user who wants both directions severed runs it on both ends; nothing here does it for them.

**A pairing binds to agreed replicas, not the account (task 83800f).** Trusting a device's certificate, above, answers *who*; it says nothing about *what*. Over §4.2's unix socket, `hello` naming any root is contained by filesystem permissions — the agent can only ever be rooted somewhere its own user could already reach, so there is nothing further to decide. That containment is gone once a peer is reached over the network transport this section extends to: "paired" taken literally would mean a paired phone can read, write and delete anywhere the agent's user can reach, not the one folder anyone meant to sync. So pairing a device's identity and authorizing it for a replica are two different acts, not one. The agreed set — the resolved, expanded root paths (the same form `Location.expandedPath` already produces in `_buildAgent`, `lib/cli/commands/agent_command.dart:229`) a given device id may serve — is recorded per device in the paired-device store, alongside the certificate pin this section already keeps there (§8.3's state directory). Granting it is a local operation on this host, by the same hand and for the same reason `dsync pair revoke` is one: nothing a peer sends over the wire can add to its own entry, because a device that could grant itself access to a new path by merely asking for it would make the allowlist decorative. Pairing a device and authorizing it for a path are consequently always two steps, two commands: `dsync pair accept` (or `show`) records the identity, `dsync pair grant` (`lib/cli/commands/pair_grant_command.dart`) adds a root to that device's agreed set, and both write the same paired-device store (`lib/dsync_core/identity/paired_device_store.dart`). The app head has the first step and, deliberately, not the second: its Pair page is `dsync pair accept` with the payload pasted or scanned, and there is no `pair grant` in it, nor planned — granting is local to the host that serves the replica, for exactly the reason above, so a phone that could grant itself a desktop's path would be the decorative allowlist this paragraph rules out. The head asks; the desktop's `dsync pair grant` is what answers.

**The refusal does not confirm what it refused.** A `hello` naming a root outside the calling device's agreed set gets an `AgentFailure`, the same reply shape every other rejected operation already gets (`AgentServer._dispatch`). Its wording has to do one thing carefully: not let the caller distinguish "that path does not exist," "this agent could not read it," and "it exists and is readable but is simply not on your list" — three different facts that, told apart, would let a paired-but-curious device map the host's filesystem one refusal at a time. All three collapse to the one answer a peer with no business asking gets.

**`hello` stays client-named; the allowlist is a property of the session, not the protocol.** The alternative — a pairing names the replica, and `hello` selects it by id instead of by path — was considered and rejected. It removes this class of question by construction, but ssh and the unix socket have no pairing at all (§4.2), so there would be no id for either of them to select by: `hello` would need two modes, or the agent would need a replica registry that exists independently of pairing, either of which is a much larger change than a genuine wire change costs today. What one costs today is nothing: `protocolVersion` is still 1 and every wire change so far has left it there, including task 40812e's new heartbeat frame type (§4.2), because a version number guards a peer running older code and there is no such peer — no release, no packaged build, no installed users, and both ends of every run come from the same checkout. It moves the first time a change ships against something already installed, which is the one job it has and the one that would be spent by bumping it before there is a pair to disagree (`lib/dsync_core/protocol/version_handshake.dart`). `hello` keeps naming a root path, exactly as it does today, on every transport.

What changes is where the check happens. `AgentServer.serve` takes `buildAgent` as `Agent Function(ReplicaSpec spec)`, and that signature does not change: `Channel`, `ReplicaSpec`, `AgentServer` and everything else under `dsync_core/protocol/` stay exactly as they are — the same property task `d0e960` is built to preserve — because none of them is where a peer's identity is known. The transport is. Giving `buildAgent` itself a `peer` parameter was the other shape considered, and it was rejected for teaching that concept to code that should not need it: `AgentServer`, and the plain `buildAgent` that `--stdio` and `--listen` already supply, would all have to carry a parameter that means nothing on those two transports, for the sake of the one transport where it does. Instead, the secure listener (`AgentListener.bindSecure`, `lib/dsync_core/agent/agent_listener.dart`, task `d0e960`) performs the TLS accept and reads `peerCertificate` before `AgentServer.serve` is ever called for that connection — the same moment `AgentListener._serveSession` calls `AgentServer().serve(channel, _buildAgent)`, unwrapped, for the unix socket. It performs that accept itself, per connection, rather than delegating it to a `SecureServerSocket` bound once: it binds a plain `ServerSocket` and, for each socket accepted, reads the paired-device store as it is at that moment, builds a `SecurityContext` from it, and upgrades the socket with `SecureSocket.secureServer`. The trust anchors are therefore never older than the connection they gate — a device paired, granted or revoked while the agent is serving is honoured on its next attempt, with no restart and no rebinding; a session already in flight holds its own upgraded socket and is untouched — for the price of one store read and one context build per accept, which at this transport's connection rate is negligible. A handshake that fails is that one connection dropped and reported, never the listener. An empty store still refuses each connection at the handshake, as a stranger is refused, but the agent reports it with a message naming the fix rather than BoringSSL's opaque verification failure. The secure listener then wraps `buildAgent`: it resolves the pinned certificate to a device id, looks up that device's agreed roots in the paired-device store (`e1101d`), and hands `AgentServer.serve` a connection-scoped closure that checks a `ReplicaSpec`'s expanded root against that set before delegating to the head's own `buildAgent` for the roots it permits. `--stdio` and `--listen` keep calling the head's `buildAgent` exactly as they do today, unwrapped — there is nothing to check because §4.2 already decided there is nothing paired to check against.

One consequence, built to by `d0e960` and `e1101d`: before this task nothing in `AgentServer.serve` caught a `buildAgent` failure, because nothing could make `buildAgent` fail — the call sat between the version handshake and `_dispatch`'s per-operation `try`/`catch`, unguarded. A rejected root can fail it, so `serve` wraps that one call and turns the rejection into the `AgentFailure` reply above rather than letting it propagate as an uncaught error ending the session with no explanation sent — the same in-band treatment `_dispatch` already gives every other failed operation, one call earlier.

**Addressing a paired peer: a name, not a host (task b1ab09).** A `peer://` location (§2) names a device, not an address — resolved through the paired-device store (§8.3), the same store that already holds the certificate pin and the agreed roots, above. The alternative was a location self-contained the way `ssh://` and `unix://` are — `peer://host:port/replica-path` or similar — and it was rejected because the thing it would bake into a profile is exactly the thing pairing already has to track and that changes on its own: a phone's address differs between one sync and the next far more often than its identity does, so writing it into a profile (§12) means writing down something that rots before the profile is read a second time, while a device's *name* is stable for as long as the pairing is. The cost is real and is not hidden by the convenience: a `peer://` location is no longer self-contained the way the other three forms are. The same profile, unchanged, does not work on a machine that has not paired with the named device — and unlike `ssh://`, where `~/.ssh/config` is at least a separate, portable, human-editable file that can be copied alongside the profile to make it work, there is no file to copy here; the paired-device store is this host's own record of a mutual trust exchange, and trust is not something a `cp` can extend to a machine that was never party to it. A run that meets a `peer://` name with no entry in the store fails before it opens a socket, with an error that names the device and points at `dsync pair` (`bc68c7`) — the same "caught while still harmless" property §11.4 already gives a mistyped location, not a hang or a generic connection failure.

**Where the name comes from, and what constrains it.** The name is local: this host's own label for that peer, chosen at pairing time, the way a `~/.ssh/config` `Host` alias is chosen by whoever writes the file rather than agreed with the far end. The two sides of a pairing need not call each other the same thing, and nothing here makes them try. It must be unique within this host's paired set — the store enforces it, the same way it already has to enforce that one device id maps to one entry — and a pairing that would collide with an existing name is rejected at pairing time, not silently disambiguated with a suffix: the operator picks a different name and pairs again. A device name is a handle for humans and for locations; the device id (above) is the cryptographic truth and what actually gets pinned. A location resolves a name to whatever certificate the store currently holds for it, which is the entire point of the indirection: a device re-paired under a new certificate — a phone wiped and set up again, say — keeps the same name, and the same locations keep working once the operator has re-paired it, without editing a single profile.

**Discovery: a last-known-address cache, refreshed on every connection.** The QR (above) carries an address hint, so the first connection needs no discovery at all. The second is answered by a field in the paired-device store: the address a connection to that device last succeeded at, overwritten on every successful connection and read back as the address to try next time. mDNS was considered and set aside (§16) rather than taken: it is not a small addition to reach for — a dependency, a multicast socket, an Android multicast lock, an iOS entitlement — and it does not cross subnets, which is precisely the desktop-to-server shape this product's other pairing case needs. The cache costs one field and a write on every successful connect, and it covers the case that actually dominates: a desktop's address is close to static, and even a phone's is often stable for the length of a sync session on one wifi network. When the cached address is wrong, the escape hatch is manual re-entry — the operator supplies an address the same way the QR supplied one the first time — not a background scan for the device. A connection attempt against a stale cached address does not hang waiting for a socket that will never answer: it is bounded, fails, and reports failure against the address it actually tried and the device name it was trying to reach — distinct in the error text from the "no such pairing" case above. "No pairing for `<device name>`" means dsync never had a certificate to trust in the first place; "could not reach `<device name>` at its last known address `<address>`" means the store trusts it and the address it holds did not work this time, which is the signal that a manual re-entry is what is needed next.

**The port: 28771, fixed, configurable on the listener.** A `peer://` location carries no port of its own — the store's cached address does, alongside the host, since a client never assumes one. The listener's own port defaults to a single fixed value, configurable the way `--listen <socket path>` already takes its socket path as an argument, so the common case of one dsync agent per host needs no configuration at all, and two agents sharing a host stay expressible by giving the second a different port. Negotiation was not considered seriously: there is nothing to negotiate a port over before a connection exists to negotiate on. 28771 is unprivileged — Linux's privileged range ends at 1024, and a listener should not need root — and sits in the registered/user range rather than the ephemeral one (49152–65535) the OS hands out to outgoing connections, which a fixed listening default has no business colliding with. It is also not a port dsync is likely to share with anything else already running on the same host: not ssh's 22, not a dev server's 8080/3000/8000, not Syncthing's 22000/21027/8384 — prior art this design already leans on (above) and that may well be installed alongside it.

## 5. Scan and change detection

Each agent scans its own replica and compares against **its own archive**. It returns a list of entries with a status relative to the archive, so the initiator never needs the full archive of the other side.

A path the scan cannot read — permission denied, or the entry vanished between the directory listing and the read — is **recorded and skipped, and the scan continues with the rest of the tree**, mirroring the per-path tolerance §7.6 gives the apply phase. One locked file does not cost the run. Such a path produces no status entry, for the same reason a skipped symlink does not (§5.1): a path the scan could not read has no state relative to the archive, so there is no cell of §6's table it belongs in. It is reported alongside skipped symlinks and contributes to the exit code (§11.5).

Archive entries beneath a directory whose listing failed are **not** reported `deleted`. The scan never got to look, so their absence from the walk is not evidence they are gone; reporting them would propagate a deletion the user never made to the other replica.

Silence is not enough on its own, though. An unreadable path is reported to reconciliation as well, and excluded there (§6) — because §6 reads a side's silence about a path as "this side has never seen it", which means *mirror it from the other side*. That is the right reading for a path that is genuinely absent and the wrong one for a path that is present and merely unread: it would overwrite a locally-edited file the scan could not look at, on a run that just said the path was not synced. An unreadable directory covers every path beneath it for this purpose, since the directory is what the scan reports but the files are what it hid.

The replica **root** is the exception: if the root itself cannot be listed, that is fatal (§11.5 exit 3), not a per-path skip. There is no tree left to sync, and reporting an empty one would invite mirroring the entire other replica into a directory this host cannot read.

### 5.1 What is scanned
- Regular files only. Directories are traversed but not tracked as entries.
- Symlinks: skipped and reported, unless the path matches a `follow` rule (§9), in which case the link is resolved and the target is treated as if it were at the link's path. A `follow` link that is broken, whose target is neither a regular file nor a directory, or that points back into a directory the walk is already inside, is also reported as skipped. Reported paths travel alongside the status list and surface as `symlink` lines (§11.4); they are not status entries, since a skipped link has no state relative to the archive to reconcile.
- Every reported path says *which* of those cases it was, not just that it was skipped. All four are one outcome to the tool — report it, plan nothing, leave the exit code alone — but not to the reader: a broken link and a link pointing back up its own tree need different fixes, and the walk is the only thing that ever knew which it saw.
- Unreadable paths: reported the same way, as `unreadable` lines (§11.4), carrying the OS's own reason — "permission denied" and "no such file or directory" are what tell a locked file apart from one that vanished mid-scan, and the latter is not there to inspect afterwards. Unlike a skipped symlink, which is the tool obeying §9's rules and happens identically on every run, an unreadable path is a failure and counts toward exit 1.
- Case-folding collisions (§16): on a replica whose filesystem folds case, two live paths — or a live path and an archived one — that fold to the same key are reported and excluded the same way an unreadable path is, rather than one silently overwriting the other, and count toward exit 1 (§11.5) for the same reason.
- Hardlinks: treated as independent regular files.
- Paths matching an `ignore` rule are not scanned.

### 5.2 Fast path
For each file, with archive entry `E`:
1. If `size` and `mtime` equal `E.size` and `E.mtime` → **unchanged**, no hash computed.
2. Otherwise compute the content hash.
   - Hash equals `E.hash` → **unchanged**; the archive entry's `size`/`mtime` are refreshed at commit.
   - Hash differs → **modified**, new hash reported.
3. File present, no archive entry → **created**, hash computed and reported.
4. Archive entry present, file absent → **deleted**.

Hash: SHA-256, via `package:crypto`. Hashing runs in isolates, parallelism configurable.

**Batched per isolate, not per file.** The candidates are split into at most `jobs` shards, balanced by total bytes — largest first into whichever shard is lightest — and each shard is hashed inside one isolate, reading 64 KiB at a time into one reused buffer so peak memory is a block per isolate rather than a file or a shard. **Inside its own isolate a shard reads with the blocking call**, not with `openRead`: on the phone's tree `ReadProbe` measures blocking reads at 28.4 MiB/s against `openRead`'s 10.9 at the same four-way spread (task 9d2158 §15), and the thing that usually makes that unavailable — needing a thread to block — is already paid for here. A job small enough to run on the caller keeps the asynchronous stream, because blocking there would stall the isolate everything else is waiting on; that is the 69 s shape §5.3 measured. A whole job smaller than 256 KiB skips the isolates and runs on the caller, because spawning costs more than hashing that much. The shape this replaced spawned an isolate only for files *above* a size threshold and hashed everything smaller on the calling isolate, which on a tree of small files is the whole tree: SHA-256 is synchronous CPU work, so `jobs` async workers on one isolate interleave at the reads and then queue for one core. Measured over 14,471 files averaging 12.7 KiB, that inline path plateaus at ~93 MiB/s however high `jobs` goes, while the same bytes across real isolates scale about linearly — 100, 196, 384 and 653 MiB/s at 1, 2, 4 and 8 (task 1a341e). Those figures are a desktop's, and the win is only ever as large as the share of hashing that is CPU: on a phone reading the same tree from emulated storage the change bought 15%, because there the cost is per-file `open`/`read`/`close` and not SHA-256 (§5.3).

`mtime` is stored as microseconds since epoch as returned by `FileStat`. Comparison is exact equality.

### 5.3 What a scan costs, and what of that is irreducible

Measured on a phone (Pixel 9a, Android 17, AOT) over a replica of 14,471 files and 179.5 MiB on `/storage/emulated/0` — the same tree and device a §17 report first showed spending 39% of a run in `scan` (task 1a341e). Passes repeated back to back agree, so the cost is syscalls and CPU, not page cache.

**Read the noise floor first.** A rung of this ladder is a ~10 s walk of the whole tree, and repeated passes of the same rung vary by **up to two seconds** — `scan (empty archive)` has measured 20.1 s and 23.9 s in consecutive passes of identical code, and the same §5.1 step has measured 31 ms, 129 ms, 498 ms, 917 ms and −91 ms. Every figure below a second or so is therefore *not separable from zero on this device*, however precisely it prints. Where a sub-second figure is quoted here it is the desktop's, whose noise floor is a few milliseconds; the phone's are quoted only where they are seconds, or where repeated passes agree on a sign and a rough size.

After task 1a341e's two fixes and task 9d2158's blocking hash read, a first sync's scan is **~16.6 s** and a later one — where §5.2's fast path resolves every file and nothing is hashed — is **10.9–11.5 s**, down from 29.9 s and 14.4 s. (1a341e left them at ~22 s and ~9.9 s. The blocking read took 5.4 s off the first and **cannot** touch the second, which hashes nothing; the ~1 s between 9.9 and ~11 is inside this device's noise floor and is not attributable to anything.) Substantially all of both is Android's emulated storage:

- **The walk's floor, ~9.5 s — now 63–66% of a first sync's scan, and its largest term by far**: `Directory.list` at ~400 µs per entry, plus one `FileStat` per file at ~330 µs, the latter now batched `jobs` deep. `Directory.list` does not report size, mtime or mode, so a scan that needs them (§5.2, §7.4) must look each path up a second time. Two lookups per file is the Dart minimum and nothing in `dart:io` exposes a cheaper one.
- **Reading file content to hash it, ~5.5 s** — 378 µs per file, 32.9 MiB/s, measured at 5.18–5.65 s across four passes, which is the tightest repeated figure this project has on this device. It was **11–13 s** (~800 µs a file) while each shard streamed through `openRead`; reading 64 KiB at a time with the blocking call, inside the isolate that shard already owns, took it **2.2×** (§5.2, task 9d2158 §17). This is *not* SHA-256, and that 2.2× coming off the read without touching the hash is the strongest evidence for it yet: the same bytes hash in 768 ms on a desktop, and the isolate batching §5.2 describes — worth 2.5× there — bought only 15% here, because on this device hashing is bound by per-file I/O and not by CPU. A future change that makes hashing faster will not make this scan faster.
- **Everything this project computes**: §5.1's rule matching, §3's path building, the archive lookup, §16's collision check and building the `ScanResult`. Together **60 ms** across all 14,471 files, measured on the desktop where it is measurable at all; on the phone it is under the noise floor. This is not where a scan's time goes, and an optimization aimed here is aimed at the wrong thing. `RuleSet.ignores` over an empty rule set — what the Flutter head runs, since it carries no §9 rules — costs 6 ms across the whole tree.

**A native walk would not get under that floor, and would likely be worse.** The syscall is a FUSE round trip charged to whoever makes it — Dart, Kotlin or C — so the only thing a platform channel could remove is Dart's own per-call overhead, and that overhead measures *negative*: the same walk through `listSync`/`statSync`, which skips the I/O thread pool and makes each syscall on the calling thread, took **69 s** against the asynchronous walk's 10.5 s. Run on the UI thread it took 77 s, so the isolate-blocking penalty accounts for about a tenth of the gap and the rest is real. Why the synchronous path is six times dearer here is not established — thread scheduling and how each path reaches the FUSE daemon are both candidates and neither was measured — but the consequence does not depend on knowing: Dart's asynchronous file I/O is carrying this walk rather than taxing it, and a native implementation making blocking syscalls in a loop is the shape that measured 69 s. One that reproduced the thread pool would be doing what `dart:io` already does, through a channel that adds a hop per call.

**Concurrency was the one lever left, and it is small.** The walk used to keep exactly one `stat` outstanding at a time; it now issues a directory's stats in batches of `jobs`, which measured 797 ms, 851 ms, 1037 ms and 1187 ms cheaper across four passes — consistent in sign and size, so roughly 1 s, or about 9% of the walk. A batch is flushed before anything that reports — a subdirectory, a symlink — so entries stay in walk order whatever order the stats return in. That the overlap is only 9% at four-way concurrency says the round trips barely overlap on this device, which is itself the argument against expecting more from restructuring the walk further.

The one Dart-level cost that *was* worth removing was a third lookup per entry: `FileSystemEntity.type`, asked for information `Directory.list(followLinks: false)` had already returned. It cost 3.50 s, and dropping it took a later scan from 14.4 s to 10.8 s; batching the stats took it to ~9.9 s. So, for §5.1: **the child's type comes from the listing, never from a second lookup.** What that lookup did buy was the path removed between the listing and the walk reaching it — now caught from the `stat` that had to happen anyway, whose `FileStat` reports `notFound` for *any* failure. Since that sentinel carries no `OSError`, the reason is asked for separately, on the failure path only, so the report can still tell a locked file from a vanished one as §5 requires.

## 6. Reconciliation

Done on the initiating side from the two status lists. Per path, with statuses on replicas A and B:

| A \ B | unchanged | created | modified | deleted |
|---|---|---|---|---|
| **unchanged** | nothing | copy B→A | copy B→A | delete on A |
| **created** | copy A→B | same hash: commit only; else **conflict** | same hash: commit only; else **conflict** | **conflict** |
| **modified** | copy A→B | same hash: commit only; else **conflict** | same hash: commit only; else **conflict** | **conflict** |
| **deleted** | delete on B | **conflict** | **conflict** | commit only |

Additional rules:
- **Same content, no transfer.** Whenever both sides currently hold the same hash, no bytes move; both archives are committed with the current state.
- **A path one side has never seen.** The table assumes both replicas report a status for every path. A replica with neither the file nor an archive entry for it reports nothing at all — the normal state of a fresh replica being set up against an established one, and of any path that is new to this pair. Such a path is mirrored from whichever side has it, whatever status that side gives it — or, when that side reports `deleted`, tombstoned on the side that still records it, so the two archives converge instead of drifting apart forever. Silence is what makes that safe: a replica that still had the file on disk would report `created` even against a wiped archive, so silence from one side plus a `deleted` report from the other means the path is gone everywhere. It is not a conflict: treating it as one would make the first run against an empty directory conflict on every file, and treating a still-pending deletion as one would ask the user to resolve a deletion that has already finished everywhere.
- **A path a scan could not read.** Excluded entirely: no action, no conflict. The table needs a status from both sides, and the unreadable side has none to give — its silence would otherwise be read as the "never seen" rule above and mirror the other side's copy over a file the tool was never able to look at. Not a conflict either: asking the user to choose between one side's content and something that was never read is not a choice they can make. The path is reported (§5.1) and counts toward exit 1 (§11.5); the next run reconciles it normally once it can be read.
- **Type mismatch.** A file at `P` on one side and a directory containing files at `P` on the other is a conflict on `P`.
- **Conflicts are never auto-resolved.** They are presented to the user, who picks a direction or skips.
- **Deletions are actions.** A propagated deletion appears in the plan like any other action and can be vetoed per item in interactive mode.

The output of reconciliation is a **plan**: an ordered list of actions (`copy A→B`, `copy B→A`, `delete on A`, `delete on B`, `commit-only`) plus a list of conflicts.

## 7. Applying the plan

### 7.1 Order
Actions are *started* in plan order, and up to **16** of them run at once (task 0f7dfc). Copies before deletions is not required; the archive rule in §7.3 makes order irrelevant for correctness, and it is per path, so two actions on two paths have nothing to order between them — a plan holds one action per path, so no two in flight can share one. Overlapping actions is what fills the idle gap §4.2's window exists to close: a serial applier keeps one operation outstanding however wide that window is.

**The number is the bandwidth-delay product.** Every agent operation costs one round trip, and an action was two of them — a `writeFile` and an archive commit — so one worker moved one file per two round trips however fat the link is. Throughput is `concurrency × file size ÷ (trips × RTT)` until it meets the link, and nothing in between contends: measured over a unix socket with 10 ms of added latency, apply time halved for every doubling from 4 to 64 concurrent actions with every per-operation mean pinned at one round trip. Sixteen is where that meets a phone on Wi-Fi for a tree of ~12.7 KB files. It costs a same-machine sync nothing — the same sweep at zero latency had 16 marginally ahead of 4.

Since task 9d2158 `trips` is one: §7.3's commit is batched and no longer sits in a worker's path. Sixteen is left where it is until it is re-measured against that, rather than re-derived by arithmetic.

**The apply is three stages, not one loop** (task 9d2158). A read-ahead stage reads each copy's source ahead of the writers (§7.2); a worker does an action's file work and hands the records the two archives are owed to the commit stage, which batches them (§7.3) and reports each action once its batch has landed. The three are different work against different resources — the source's storage or the inbound link, the destination's storage, and a round trip carrying one line of JSON — and a worker that did all three in turn spent a third of the apply on the commit and 53–62% of the serialized budget waiting on the read. Each stage is bounded by the thing that constrains it rather than by one count of actions in flight: bytes buffered on the source, **16** actions on the destination, 64 records per exchange. What it costs is that the run reports later than it acts: an outcome is delivered when its batch lands, so the run may be up to `concurrency` actions in flight plus twice the batch size applied-but-unreported ahead of the last outcome a consumer saw. Every outcome delivered is still durable on both sides when it is delivered.

Outcomes are therefore reported in **completion order, not plan order**, and a consumer that stops mid-apply stops within the bound above rather than exactly one action later — each action past the last one reported is already finished and durable on disk, and nothing beyond them starts.

### 7.2 Copy
1. Source agent streams the file; destination agent writes to a temp file in the same directory as the target (so rename is atomic on the same filesystem).
2. Destination sets mtime to the source mtime and mode bits to the source mode (§7.4).
3. Destination renames temp over target. Parent directories are created as needed.
4. Destination stats the final file and returns the resulting `size`, `mtime`, `mode`.

**The source read starts before the write asks for it** (task 9d2158). Step 1 used to be one expression — the destination was handed the source's stream and the stream is lazy, so the read did not begin until the write subscribed and the destination waited out the whole read before it had a byte to write. Measured phone-to-desktop (§17), the peer's `starved` equalled the source's `readFile` to within 4% on five of five runs and was 53–62% of the serialized budget: the largest single term in the apply. A read-ahead stage therefore starts each copy's read while earlier writes are still going, and hands the writer a stream that already has bytes in it. What a copy does and in what order is unchanged; only when the first byte is available is.

**Bounded in bytes, not in files, and there is no size threshold.** The bound is on bytes *buffered per stream* — one chunk, 64 KiB — with a total budget of **1 MiB** across every read in flight, so a file larger than the whole budget holds one chunk and streams the rest under backpressure exactly as it did before. There is no large-file bypass and so no threshold to choose. A second bound caps how many source reads may be open at once, at **24**: the byte budget alone would admit ~80 concurrent reads of a tree of small files, and a remote source's `readFile` holds one of the connection's 32 window slots (§4.2) for its whole stream, while a read on the device is a message to a bounded native-port pool. A slot is held from the read starting until the writer has taken the last chunk, which is earlier than the write finishing.

**What is in flight on the memory-constrained end.** In the pull direction the phone is the destination and holds 16 streaming writes of one chunk each, ~1 MiB, as it did before. In the push direction it is the *source*, and then two of these buffers are on it at once: the read-ahead's 1 MiB and the transport's 1 MiB write cap (§4.2), since the side reading the files is also the side sending them. §17 reports the read-ahead's peak for exactly that reason — the figure is to be read, not assumed, and no reading of the device's own peak has ever been taken against either bound.

### 7.3 Archive commit per path
After an action succeeds on both sides, **both** agents are owed the record for that path. The record is handed over immediately; it *travels* in batches, and it is made *durable* in batches (§8.2), so a crash loses at most the last unflushed batch. That is the same shape of damage as the crash this section is already about, and the rules below close it the same way — it is simply a few hundred paths rather than one. A crash between the two commits leaves one side's archive stale.

**Records travel in batches of 64 (task 9d2158).** One `archiveCommit` per replica carries the records of up to sixty-four finished actions. Measured phone-to-desktop over `peer://` (§17), a commit carrying one path cost 22.0 ms, of which 21.7 ms was link latency and 0.34 ms was the replica's own work: the exchange is the cost, and one per path was a third of a 14k-file apply. Sixty-four takes that to 0.34 ms an action, under everything else in the action and under what §17 can resolve; the bound on going further is what a batch holds and how late the run reports, not the wire. A batch that fails fails every action in it, because nothing says which of its records landed — pessimistic on purpose, since an action reported failed whose record did land costs the next run nothing, and the reverse would archive a path nothing propagated. This batches the wire; §8.2 batches the fsync; the two are independent bounds on the same crash window.

For a copy, that self-heals: the stale side reports the path as modified with the same hash as the other side, which resolves as commit-only (§6). No work is redone beyond one hash.

For a delete, the same crash does not self-heal the same way — there is no shared hash for the two sides to agree on. The side whose commit landed has no file and no archive entry left, so it reports nothing; the side whose commit was lost still holds its stale pre-delete entry, so it reports `deleted`. §6's "a path one side has never seen" rule is what closes this gap: silence from the landed side plus `deleted` from the stale side tombstones the stale side's entry, so the next run converges on both archives agreeing the path is gone, rather than leaving one side reporting a deletion that already finished everywhere.

### 7.4 Metadata
- `mtime`: always propagated. If setting it fails, the write still succeeds; the actual mtime is what gets archived.
- Mode bits: propagated on a best-effort basis; failure is logged, not fatal. On a platform with no mode concept at all — Windows, per §3 — this degrades from "may fail" to "never attempted"; the archived value there is whatever `FileStat.mode` actually reports, the same "actual state, not the intended one" already true for Android's external storage.
- Mode bits travel with content, never on their own. The fast path (§5.2) keys on size and mtime, so a file whose permissions changed and whose content did not scans as `unchanged` and gets no action. A mode-only difference between the replicas is therefore never detected and never repaired; it is corrected the next time that file's content changes. Detecting it would mean comparing the scanned mode against the archived one and adding a metadata-only action, which v0 does not have.
- Ownership, xattrs: not touched.

### 7.5 Delete
Target file is deleted. Every ancestor directory up to the root that the tool has just emptied is removed. Directories that were already empty before the run are left alone — the tool only removes emptiness it created.

**The pruning is swept once, after every action is applied**, not per delete (task 0f7dfc). `removeEmptyDirs` is the one agent operation that cannot share a connection with anything else, because it reaches ancestors of the path it is given rather than that path alone — it can remove a directory a concurrent `writeFile` on an unrelated path is about to write into — so §4.2 makes it a barrier. Run inside the apply loop it drained the connection's window once per delete, handing back most of what §7.1's overlap buys; run after the loop there is nothing left to drain.

Deferring it is not less correct. The rule above is unchanged and still holds: a directory emptied by a delete and then written into again by a later copy is now simply left alone, where before it would have been removed and recreated. What it gives up is that a failure to prune is no longer attributable to an action — that action has already been reported and recorded as applied — so it is swallowed, the same best-effort §7.4 gives mode bits. Pruning is tidying: §7.3's archive rule does not depend on it, so a directory left behind cannot stop the replicas converging.

### 7.6 Failures
A failed action is recorded, the path is left in whatever state it reached (temp files are cleaned up), and the run continues with the next action. Failed paths are reported at the end and contribute to the exit code.

## 8. Archive

### 8.1 Content
One archive per replica, on the host of that replica, keyed by profile id + replica side. Header: schema version, profile id, root path. Entry: `path`, `size`, `mtime`, `mode`, `hash`.

### 8.2 Format (default chosen, see §15)
Append-only JSON Lines log. Each commit appends one line (an upsert or a tombstone). At the end of a run that reached the apply phase, the log is compacted into a fresh file and swapped in by rename. A run that committed nothing does not compact. On load, the log is replayed; last write per path wins.

**Commits are batched behind one fsync (task 0f7dfc).** Lines are buffered and written together — 256 of them, or one second of them, whichever comes first — and the whole batch is fsynced as a single append. Measured phone-to-desktop on a 14k-file tree, one fsync per path cost 85.4 s of a 133 s apply phase on the initiating replica alone and 143 s on the far one (§17); it is the largest serial cost left in an apply once the requests themselves are pipelined (§4.2), because every commit on one replica queues behind every other commit on it.

What batching gives up is bounded: a crash loses at most the last unflushed batch, which is the state §7.3 already converges on without intervention — the stale side rehashes those paths on the next run and they resolve as commit-only. The cost of being wrong is a rehash, never a wrong answer, and it is capped at a couple of hundred paths.

**Buffered commits are flushed before the replica is given up**, which is the part that is not optional: a clean exit must not lose work. `Agent.unlock` is where that happens, since it is the one operation both a local replica and a served one run on every exit path, and the lock is what says the replica is this session's. `load`, `compact` and `lastCommitTime` flush first too, each because it reads or replaces the log that the buffer belongs to.

Rationale: per-path commits (§7.3) without rewriting the whole file, no native dependency, trivially inspectable. The archive sits behind an `ArchiveStore` interface so a SQLite implementation can replace it if the log approach proves inadequate on large trees.

### 8.3 Location
- Linux: `$XDG_STATE_HOME/dsync/` (default `~/.local/state/dsync/`).
- macOS: `~/Library/Application Support/dsync/` — the platform convention; macOS has no XDG variables to defer to.
- Windows: `%LOCALAPPDATA%\dsync\`.
- Android: the app's private files directory (Flutter head) or Termux's home (CLI head).
- iOS: the app's own `Application Support` directory inside its sandbox (§3) — there is no CLI head to have a second answer.

`resolveStateDir` (`lib/dsync_core/state_dir.dart`) is a pure function of an environment map and a `StateDirPlatform`: `LinuxStateDir`, `MacOsStateDir` and `WindowsStateDir` derive the first three rows from the variables named there, and `HostSuppliedStateDir` carries the last two — a base directory the Flutter head has already resolved through the platform's own API, which `core` (no Flutter dependency, §3) could not call itself. The platform is passed in from the one edge that reads `dart:io`'s `Platform` (`lib/cli/dsync_cli.dart`), the same way the environment map already is, so every branch is exercised from a unit test on any host. A variable a branch needs that is absent or empty throws, naming it — `dart:io` would otherwise happily write into a directory literally named `null`. Every one of §4.4's device identity, the paired-device store, the per-replica archive and its lock lives under this directory.

## 9. Ignore and follow rules

- Syntax: glob, matched against the root-relative path. Supported: `*`, `?`, `**`, character classes. No negation in v0.
- `ignore` rules: matching paths are neither scanned nor deleted.
- `follow` rules: matching symlinks are resolved (§5.1) and their target's content is synced as a plain file at the link's path; dsync never creates a symlink at the destination, on any platform, so Windows' privilege requirement for creating one (`SeCreateSymbolicLinkPrivilege`) never applies to v0's write path (§3).
- Rules come from the profile file; `--ignore` may be repeated on the command line and is additive.

## 10. Size warning
Optional `warn_size_bytes` in the profile (`--warn-size` flag). If the total bytes to transfer in the plan exceed it, the plan display shows a warning. Nothing is blocked.

## 11. CLI

### 11.1 Commands
```
dsync sync <profile> [flags]      # the main one-shot run
dsync sync <locA> <locB> [flags]  # ad-hoc, no profile
dsync agent --stdio               # started by ssh on the remote host
dsync agent --listen <socket>     # bind a unix socket and serve it (§4.2)
dsync agent --serve [--port N]    # serve paired devices over the network (§4.4)
dsync status <profile>            # scan + reconcile + print plan, apply nothing
dsync pair show                   # print this device's pairing payload (QR + text), wait for one redeem (§4.4)
dsync pair accept <payload>       # redeem another device's payload; record it as paired
dsync pair list [--json]          # this host's paired devices
dsync pair revoke <name>          # forget a device, locally (§4.4)
dsync pair grant <name> <root>    # authorize a paired device for a replica root here (§4.4)
dsync pair renew                  # re-issue this host's certificate under its existing key (§4.4)
dsync archive list [--json]       # the archive logs this host keeps, and what they cost on disk (§8)
dsync archive clear <profile>     # delete a profile's archive logs; --all for every one of them (§8)
```
`status` is `sync --dry-run` under a friendlier name. `pair` and `archive` alone, with no subcommand, are usage errors.

`archive` is the maintenance surface over §8.3's state directory, and `clear` is the only destructive thing in it: an archive is per-replica sync history (§2), so deleting one touches no file in either replica and costs the next run over that profile a full rescan and rehash — the work its first run did. Both sides of a profile go together, because an archive kept for side `b` after side `a` is gone records a propagation the other side no longer remembers making. A log in use by a run is refused rather than pulled out from under it: `clear` takes §4.3's replica lock for each log it deletes, and that lock now holds against every holder on the host rather than only against another process. The OS file lock alone could not do it — POSIX advisory locks are owned by the process, so the Flutter head (§13), which runs its sync in the same process as its UI, would have been granted a delete out from under its own run, and the run would have rebuilt a log the next run then refuses as a mismatched header (§8.1). `ReplicaLock` therefore keeps a process-local registry of the paths it holds alongside the file lock, and answers `ReplicaLockHeldException` from whichever side the second holder comes. The lock file itself is left where it is: it is empty by construction, so it is not archive state, and removing it would only race the next acquirer.

`agent` needs exactly one transport, and none is a default: they are not spellings of the same thing — `--stdio` serves one session and ends with its input, `--listen` and `--serve` outlive any number of sessions, and only `--serve` authenticates who connects — so a bare `dsync agent` is a usage error rather than a guess, and naming two is a usage error rather than a silent precedence rule. `--serve` binds every interface on 28771 unless `--port` says otherwise (§4.4), and `--port` without `--serve` is a usage error. `--listen` and `--serve` end on SIGINT or SIGTERM (§11.5's 130 / 143), which is what lets `--listen` unlink its socket on the way out.

### 11.2 Flags
```
--dry-run             show plan, apply nothing
--batch               apply non-conflicting actions without asking;
                      conflicts are listed, not resolved
--json                machine-readable output (JSON Lines) on stdout
--ignore <glob>       additive to profile
--warn-size <bytes>
--jobs <n>            hash parallelism
--ssh-option <arg>    one argv word for ssh itself, before the destination;
                      repeatable, additive to the profile
--remote-dsync <cmd>  the command that starts the agent on the far side
--verbose / --quiet
```
`--ssh-option` and `--remote-dsync` apply to every remote replica of the run *that is reached over ssh*. The value that reaches a replica is per replica (§4.2); a run whose two remotes need *different* values is what a profile's `[ssh.a]`/`[ssh.b]` is for. Neither has anything to say to a `unix://` or `peer://` replica — there is no argv to pass options to, and nothing to start on the far side, because the listener is already running in both cases — so a run that names either is not an error; they simply do not apply there.

### 11.3 Interactivity
Default is interactive: the plan is shown, conflicts first, then each proposed action; the user accepts, skips, or picks a direction per item, or accepts all remaining. `--batch` skips the prompts for non-conflicts. With `--batch`, conflicts are never resolved automatically.

### 11.4 Output
- Human mode: a run header naming both replicas and when the pair last synced, then a plan table, then progress lines during apply, then a summary (applied / skipped / conflicts / failed / unreadable). The header prints before anything moves, so a mistyped location is caught while it is still harmless; when either side has no archive it says so, because that run mirrors rather than propagating deletions (§6). `skipped` counts proposed actions the user declined; `unreadable` counts paths §5 could not read, which were never proposed at all — two different questions, so two different numbers.
- `--json`: one JSON object per line with a `type` field (`replicas`, `plan`, `action`, `conflict`, `symlink`, `unreadable`, `caseFoldCollision`, `scanTally`, `progress`, `result`, `summary`, `error`). `symlink` reports a link the scan skipped (§5.1); `unreadable` reports a path it could not read (§5); `caseFoldCollision` reports a path excluded because another folds to the same key on a case-insensitive replica (§16). All three carry a `detail`: which of §5.1's cases the link was, the OS's own reason for the failed read, or the path it collided with. They are separate types rather than one type with a `reason` field, so a consumer already filtering for `symlink` — a thing that is normal on every run — does not silently start matching failures too. `scanTally` reports, per side, how many scanned paths resolved through each of §5.2's branches — most usefully `metadataMatched` against `hashMatched`, the fast path against the rehash it took to prove an unchanged file's drifted size or mtime meant nothing. `replicas` is the header's data — each side's location, locality, archive path and last-commit time, plus the profile id and `firstSync` — as facts only; the human warning is a rendering of `firstSync`, not a string on the wire. Human text goes to stderr in this mode so stdout stays parseable.

**A locked screen on the `app` head is a pause, not a failure.** The mobile head is the peer that gets backgrounded mid-run, and the platform freezes a backgrounded app: the socket then goes silent and the far end fails the session on its heartbeat deadline (§4.2), mid-copy, holding both replica locks until its own deadline fires. So the head takes both halves of the problem. It holds the screen on for as long as a run is live (`wakelock_plus`), which removes the case nobody asked for — the idle timeout — and costs a plugin and no permission. And it treats a real backgrounding as a *pause*: on `AppLifecycleState.paused` it suspends the run at an action boundary exactly as a user's Stop does, so the generator's cleanup unlocks both sides and disconnects, and the phase the page shows says paused rather than stopped or failed. Coming back to the foreground continues it automatically; a run that ended in failure instead waits behind a Resume button, because a stale address or a revoked grant (§4.4) is not something to re-dial every time the user glances at the screen.

What "continues" means here is a second run of the same request — a fresh dial, scan and reconcile — not a protocol-level resume, and it is a continuation because of §7.3 rather than because anything is remembered: every action reported before the pause is committed on both sides, so the new plan holds what is left. The re-scan costs a walk of both trees and one scan reply, not a rehash, since §5.2's fast path matches everything the previous attempt applied. What it does pay for twice is the hash of a path that was planned but not yet applied, and any conflict the user had not resolved is asked again. Only `paused` triggers this: `inactive` is a notification shade, a permission dialog or an incoming call, and a run torn down for one of those was never in danger. The pause is best-effort by nature — the platform gives a backgrounding app a short window to finish that teardown — and the heartbeat deadline remains the backstop when it runs out.

### 11.5 Exit codes
```
0    all planned actions applied, no conflicts
1    completed, but some paths were skipped (including paths the scan could
     not read, §5, or that collided on a case-insensitive filesystem, §5.1)
     or are unresolved conflicts
2    completed, but some actions failed
3    fatal: bad arguments, cannot reach a replica, lock held, archive unreadable,
     protocol version mismatch
130  interrupted by SIGINT (128 + 2)
143  interrupted by SIGTERM (128 + 15)
```
When both 1 and 2 apply, 2 wins. 130/143 are deliberately outside the 0-3
scheme: they say what the user did, not what the run did, so they win over
any of 0-3 rather than being ranked against them — folding an interrupt into
3 would have retry logic retrying a run the user asked to stop.

A `sync`/`status` run traps both signals the same way: the first one stops
the run at the next action boundary — the action in flight finishes, both
sides commit its archive entry (§7.3), and the summary is printed — and a
second one, of either kind, exits at once. Whichever arrived first picks the
code. SIGTERM is trapped, rather than left to the kernel's default (which
also reports 143), because for a scheduled run — a systemd stop, a
`timeout`, a supervisor's kill — it is the *normal* stop signal, and an
untrapped one lands wherever the process happens to be, mid-copy included:
the data is safe either way, but one side's archive can end a commit behind
with nothing reported. On Windows, where there is no SIGTERM to trap, only
SIGINT is watched.

`dsync agent --listen` reports 130/143 too, although a signal is its
*ordinary* way out rather than an interruption: there is no input to close
and no run to have got partway through, and 128 + signal is what a shell
reports for a program that does not trap them at all. Trapping them buys the
socket being unlinked (§4.2), not a different code.

## 12. Profile file

TOML, parsed with `package:toml`. Location: `profiles/<name>.toml` under the config directory, which — like the state directory (§8.3) — is resolved per platform by `resolveConfigDir` (`lib/dsync_core/config_dir.dart`):
- Linux: `$XDG_CONFIG_HOME/dsync/` (default `~/.config/dsync/`); Termux CLI head unchanged.
- macOS: `~/Library/Application Support/dsync/` — the same directory as §8.3's state; macOS has no config/state split.
- Windows: `%APPDATA%\dsync\` — the roaming profile, distinct from §8.3's `%LOCALAPPDATA%` state.
- Android (Flutter head) and iOS: the app's own config dir, handed in resolved by the app head, as §8.3 does for state.

```toml
[replicas]
a = "/home/me/notes"
b = "me@phone:/sdcard/notes"

[rules]
ignore = ["**/.git", "*.tmp", "**/node_modules"]
follow = ["shared"]

[options]
warn_size_bytes = 500_000_000
jobs = 4

[ssh.b]
options = ["-i", "~/.ssh/id_phone"]
command = "/data/data/com.termux/files/usr/bin/dsync"
```
Command-line flags override profile options. `ignore` is additive, and so is `--ssh-option`, for the same reason: a profile's `-i` is what makes the connection work at all, and a `--ssh-option` typed once to debug a run must not silently drop it. Where the same ssh option is given twice, ssh's own precedence decides.

`[ssh.a]` and `[ssh.b]` are keyed by the replica side they configure (§4.2), both optional, as is either key within them. They are ignored for a side that runs in-process — a profile may carry one for a replica that is local on this machine and remote from the other end of the pair.

A `peer://` replica (§2, §4.4) names a device, not an address, and that is deliberate — but it means a profile that names one is portable in name only. The same TOML file, copied verbatim to a second machine, resolves `b = "peer://phone:/sdcard/notes"` against *that* machine's own paired-device store, which is either empty or holds a different `phone`; `dsync pair` (`bc68c7`) has to run there first, and no amount of copying the profile substitutes for it. There is also nothing in `[ssh.a]`/`[ssh.b]`'s shape for a `peer://` replica to configure — no options to pass to a spawned process, no far-side command to name, because the connection is already authenticated by the pairing and the far side is already running (§4.4) — so `peer://` gets no `[peer.*]` table alongside them. The port is left out of the profile for the same reason: it is carried in the paired-device store's cached address (§4.4), because a profile is the wrong place for anything that already rots on its own.

The app head keeps none of this. Its saved runs live in a head-owned store (`lib/app/sync_profile_store.dart`), one JSON document `sync-profiles.json` under the §8.3 state directory beside the paired-device store, and they are deliberately not §12 files: a head profile's local root is a platform grant, not a portable path, so it is not runnable on a desktop and reusing the TOML shape would be legibility to `dsync sync <profile>` the file cannot have. What a head profile saves is a `RunRequest` minus the per-run choices — a name, the local root, the peer's *device id* (not its name, for the reason `ReplicaConnector.profileIdFor` already derives the archive key from the id), the remote root and the job count; the address and the dry-run choice stay per run. The id a new profile is saved under is `profileIdFor` over its triple, so the saved run and its archive line up by construction, and an edit from the setup form saves over the profile's own id rather than beside it. A profile whose peer has been revoked, or whose local root no longer passes the §3 filesystem probe, renders on the head's home list as broken and unrunnable rather than disappearing — the row is the only place that run still exists.

## 13. Project layout

For v0 the code lives in a **single Dart package** for development ergonomics.
The structure is organized so the eventual split into separate packages is a
move, not a rewrite:

```
lib/
  dsync_core/    pure Dart: agent, scan, reconcile, apply, archive, protocol, rules
  cli/           args parsing, TTY prompts, output formatting — everything CLI-specific
  app/           Flutter head: bootstrap gate, routes, one directory per feature
```

`dsync_core/` holds all core code and depends on nothing head-specific.
`cli/` holds everything specific to the CLI experience and depends on
`dsync_core/`. `app/` does the same for the Flutter head, and is the only
place `package:flutter` is imported — `lib/app/dsync_app.dart` is where a
Flutter dependency leaking into the core would surface as a cycle.

The `dsync_core` boundary exposes: `Location`, `Agent` (+ `LocalAgent`,
`RemoteAgent`), `Channel` (+ `AgentListener`, the far end of the socket
transport), `Scanner`, `Reconciler`, `Plan`, `Applier`, `ArchiveStore`, `ArchiveInventory`
(what is stored in §8.3's state directory, what it costs, and deleting it),
`RuleSet`, and a `RunController` that drives a run and emits events the heads
render.

At v1 (or whenever the ergonomics of one package start to hurt), each top-level
folder becomes its own package — `dsync_core`, `dsync_cli`, `dsync_app` — with
the same boundaries already enforced by the folder split.

## 14. Testing

- Core logic is tested against real temporary directories created per test.
- Reconciliation is additionally tested as a pure function on hand-built status lists covering every cell of the table in §6.
- The protocol is tested by running a `LocalAgent` behind an in-memory `Channel`, exercising the same `RemoteAgent` code path as SSH without a network.
- Crash-safety of §7.3 is tested in-process (`test/dsync_core/apply/crash_safety_test.dart`): one side's `Agent` is wrapped so its archive commit throws after the other side's has landed, which is the exact state a crash between the two commits leaves behind, and a fresh, uninterrupted re-run must converge without moving bytes again. Real process kills are covered separately, through the compiled binary: `sigint_e2e_test.dart` sends a real SIGINT/SIGTERM to a running `dsync sync` and asserts the trap (§11.5), and `peer_e2e_test.dart` runs a whole sync against a real `dsync agent --serve` child and stops it the same way.

## 15. Defaults chosen where you were undecided

Override any of these before code starts:
1. **Symlinks**: skipped unless matched by a `follow` rule; hardlinks treated as plain files.
2. **Archive format**: JSON Lines append log with compaction, behind an interface. Alternative: SQLite via `package:sqlite3` (adds a native dependency on both hosts).
3. **Protocol encoding**: length-prefixed JSON frames, *except* a successful `scan` reply, which is a hand-rolled binary payload in its own frame type (§4.2). Settled with measurements rather than left as a default; MessagePack (`package:msgpack_dart`) was the alternative and was not taken.

   Measured on a 100k-entry `scan` result, two-level paths, a unique SHA-256 each:

   | encoding | wire bytes | decode | peak RSS |
   |---|---|---|---|
   | JSON | 17.2 MiB | 162 ms | 320 MiB |
   | binary | 7.2 MiB | 47 ms | 223 MiB |

   `scan` is the only message worth this: it returns the whole replica's listing in one frame, so its size is the size of the tree, while every other operation carries one path or nothing. Those stay JSON — a second encoding for them would be code to maintain in exchange for bytes nobody can measure.

   **Hand-rolled rather than MessagePack** because the win here is the layout, not the syntax. MessagePack would still hand back a boxed map per entry and would still spell the hash as text; it also adds a pinned dependency to every host (§3), which is a real cost for a format this project can write in 200 lines.

   **The hash travels as raw bytes but stays a hex `String` in the model.** Halving its wire size (64 characters → 32 bytes) is where most of the 10 MiB comes from. Holding those bytes in `ScanEntry`/`ArchiveEntry` instead was measured too and rejected: it would take a further ~30 ms off a remote scan while adding ~10 ms to *every* archive load, since §8.2's log stays hex so it stays inspectable. That is ~20 ms net on a 100k-file remote run and a small loss on a local one, in exchange for changing two models, the scanner, the reconciler and the archive store.

   Task 9551c4 recorded a 6× decode win for bytes-in-the-model. It did not reproduce: that measurement's hex-rebuilding decoder grew each hash through a `StringBuffer`, and filling a code-unit list for `String.fromCharCodes` recovers almost all of the difference without touching the model.
4. **Exit codes**: as in §11.5, mirroring Unison's four-level scheme.
5. **Profile format**: TOML.
6. **mtime comparison**: exact equality of microsecond values. If a target filesystem turns out to round mtimes, the archive stores the rounded value it reads back, so the next run's fast path still matches.
7. **Pairing handshake**: TLS with a self-signed certificate, not Noise (§4.4). Both were real options — `cryptography` ships X25519, so Noise would not have meant hand-writing an elliptic curve, which is the assumption that had wrongly ruled it out earlier. Taken on the failure mode instead: a broken certificate encoder cannot ship, because BoringSSL either completes a handshake with what it produced or refuses to load it, while a wrong Noise implementation still handshakes with itself and fails silently. The certificate is EC P-256 / ECDSA-SHA-256, hand-rolled on `pointycastle` rather than generated by `basic_utils` — about 170 lines this project owns, against a dependency that reaches the same PEM through `http`, `json_annotation`, `logging` and `archive` for one function's worth of use. What a pairing pins is the certificate's public key, not its bytes (HPKP's and Syncthing's model), so `dsync pair renew` can re-issue it under the same key inside its ten-year validity without a single peer re-pairing; renewal is manual, because a credential other machines pin should not rotate unseen.

## 16. Deferred

- A Dart SSH client as the transport underneath the mobile head. Considered and rejected: it is the hot path on a phone, and a borrowed implementation puts the read loop, the buffering and the framing inside a library this project cannot tune — `peer://` over TLS (§4.4) is this project's own, on `dart:io`, end to end.
- Serving a replica *from* the mobile head. The head is a client only: it dials `dsync agent --serve` on a desktop and never binds a listener, so a desktop cannot initiate a run against a phone and two phones cannot sync with each other.
- Storage Access Framework *content-URI* trees as a local replica on Android. `Scanner` and `LocalAgent` are plain `dart:io`, and what the Storage Access Framework grants is a `content://` tree URI, not a path `dart:io` can open; reaching such a tree needs a `Scanner`/`Agent` implementation over it, which is `dsync_core` work, not a head concern. What the head does instead is take the *path* the directory chooser converts that URI to and prove it with a `dart:io` probe — which on targetSdk 30+ requires All-files access (`MANAGE_EXTERNAL_STORAGE`, §3), asked for when the probe fails and refused with a message when it still does. So a folder outside the app's own container is reachable today, under a permission the user grants on a Settings screen; a folder that has no filesystem path at all (the Downloads provider, a cloud document provider) is what stays out of v1.
- mDNS discovery, to replace manual re-entry when a paired peer's last-known address (§4.4) has gone stale. Not taken for v0: it is a dependency, a multicast socket, an Android multicast lock, an iOS entitlement, and it does not work across subnets — exactly the desktop-to-server case a phone's address changing is most likely to hit. The last-known-address cache plus manual re-entry (§4.4) covers the common case for the price of one field and a write on every successful connect; mDNS is worth its cost only once that stops being true.
- Watch mode.
- Delta transfer (librsync via FFI or a Dart implementation).
- Negated ignore patterns.
- Ownership / xattr preservation.
- Case-insensitivity is decided for v1, not fully closed by it (task a1d635; SPEC §3, §5.1). Detected per replica at scan time as a property of the filesystem actually mounted there — not assumed from the OS, since a case-sensitive-formatted APFS volume or a case-insensitive mount on Linux would otherwise get the wrong behavior. On a replica whose filesystem folds case, two live paths — or a live path and an archived one — that fold to the same key are reported and excluded the way §5.1 already excludes an unreadable path, rather than one silently overwriting the other. Refusing the whole run over one colliding pair was considered and rejected, for the same reason §5's per-path tolerance exists at all: one bad path should not cost the tree. This deferral used to cost nothing, because it applied only to Linux and Android, where it is either moot or, on Android's external storage, already a named exception (§3); it is not affordable now that APFS and NTFS are v1 targets (§3), which is why it is no longer a blanket deferral. What stays deferred: a same-run plan proposing two creates that differ only in case onto a replica where neither path exists yet — that replica's own scan finds nothing on disk or in its archive to collide with, so catching this needs the reconciler or apply phase to fold-check a plan's own paths against a destination known to be case-insensitive before either write lands, and that is not built. Unicode normalization (NFC/NFD converging to one file on a normalizing filesystem) is the same shape of problem for a different reason and gets the same treatment: deferred with the plan-level gap above, not separately, because whichever mechanism closes one closes both.

## 17. Run measurement

The tool measures its own runs, and both heads can show the measurements. This is instrumentation only: nothing in the engine reads these numbers or changes what it does because of them.

**Why it exists.** On a tree of many small files, a run's cost is dominated by *per-path round trips and fsyncs*, not by bytes. §7.2 and §7.3 made a copy cost one `writeFile` plus one archive commit on each side, so 14,000 files was 28,000 requests carrying 14,000 files' worth of data — strictly sequential until task 0f7dfc, pipelined behind a bounded window since (§4.2), and down to one request per path plus one per batch of them since task 9d2158. Nothing else the tool reports can tell a run that was slow because the link was slow from one that was slow because it was chatty: §11.4's summary counts outcomes and §5.2's tally counts scan branches, and both are identical between the two cases.

**What is measured.**
- **Phases**, as §13's flow already divides them: `connect`, `lock`, `scan`, `reconcile`, `present`, `apply`, `compact`, `unlock`, `disconnect`. A phase a run never reached is absent rather than zero, so "0 ms" always means "ran and was instant" — a `compact` skipped under §8.2 is not a `compact` that took no time. `present` is separated from `apply` because it is the one span that is not the tool's own cost: on an interactive head (§11.3) it is however long the user took to answer.
- **Per replica, per `Agent` operation** (§4.2): call count, total, mean and max wall time, how much of that was spent waiting for a window slot rather than on the wire, and the file content each moved. Measured at the `Agent` boundary, which is the one seam every unit of per-path work crosses on a local *and* a remote replica — instrumenting `RemoteAgent` alone would miss what the initiating side pays for its own commits (§8.2), which on a phone's flash is a real share of the run.
  - **A mean is part queue** (task 3380f4). An operation admitted by the §4.2 window pays its wait *inside* its own span, so `queue` is the wait and `wire` is the exchange. Without the split a mean that rose because the window filled up is indistinguishable from one that rose because the link got dearer, and the two have opposite fixes — the first wants more concurrency or fewer operations, the second wants fewer round trips. The measured example: `writeFile` averaged 41.9 ms on the phone at 16 workers against 25.8 ms at 4, and nothing in the report could say whether the operation had got slower or had started queueing.
  - **Every split is taken on one call, and nothing is subtracted from an aggregate** (task 9d2158). `RemoteAgent` is the only object that sees an operation issued, admitted by the window, and finished, and that decodes what the peer said about that same call; it therefore reports one *exchange record* per call, already split, and the recorder only ever adds those up. What this replaces was arithmetic over totals — `wire` as `total − queue`, `link` as `mean wire − mean far` over a *different* denominator — summed by different collaborators at different instants and clamped at zero at both steps, so two counters that disagreed about which calls they had seen produced a plausible duration rather than a visible disagreement. Each column is now divided by the count of the calls that fed it, which also means **no two columns are each other's difference**: `far` and `link` are averaged over the calls whose peer reported, `queue` and `wire` over every exchange, and subtracting one printed figure from another gives a number with no population behind it.
  - **A mean is part far side** (task 9d2158, phase 0a). On a remote replica `wire` is three things: the request going out, whatever the peer did with it, and the reply coming back. Only the peer can measure the middle term, so it measures it — from the request frame arriving at its dispatch to its reply being handed to the channel — and returns it as an optional field on the reply's existing success control frame, which costs no extra exchange. The report prints it as `far`, and each call's own `wire` less its own `far` as `link`. Without the split, `writeFile`'s 40.9 ms per action on the phone was one figure covering the transfer, the round trip, and the destination's write and fsync — three things with three different fixes. For `writeFile` the peer's span begins when the request frame lands, so it *contains* the inbound transfer; what it excludes is the request out and the reply back, which is the part the split isolates. **Absent is not zero**: a peer that does not report — an older build, or an operation whose reply is not a success control frame, which is `scan` (§15.3) and `readFile` — is printed as `—`, never as 0 ms, because "the destination is free" is exactly the conclusion this figure exists to check rather than assume. Adding it needed no protocol version bump (§4.2): a peer that omits an optional field decodes to the absence it would have had anyway.
  - **`far` is residency, not service time, and the reply says by how much.** The peer dispatches every arriving request concurrently and bounds nothing (§4.2 puts the bound on the initiator), so its span is wall time on an agent that may be serving a dozen others — the same inflation the initiator's own `wire` shows as its worker count rises. The reply therefore carries the peer's **in-flight request count** beside the span, printed as `peers`. Near 1 it says `far` is what the destination cost; near this side's concurrency it says `far` cannot be read as the destination's own cost at all, and a split of it into finer parts would inherit the same problem.
  - **What `far` cannot contain, said outright.** The span stops one line before the reply is handed to the channel, so the wait that reply then serves behind the peer's *other* senders — the peer's own `FlushedSink` queue, which on this side turned out to be two thirds of `link` (§4.2) — falls outside it and lands in `link`. A frame cannot carry the cost of its own flush. What it carries instead is the peer's **cumulative** sink wait up to that reply, so the session total is the last reading and the report prints it against the session's total link time. That is the figure that says whether an apparent link latency is really the peer's send queue.
  - **`far` contains the inbound transfer, so it is split where the frames are consumed.** A `writeFile`'s span begins when the request frame lands and the bytes then arrive at the link's pace, which makes one number mean two opposite things: a destination starved by the radio and a destination busy with its disk report the same `far`, and the fixes are "send fewer, larger" and "write cheaper" respectively. The peer therefore sums the gaps between being ready for the next frame of the request and that frame arriving, and reports it beside the span as `starved`. Near `far` the destination was waiting on the link; near zero the bytes were already there and the write and the fsync are the cost. It is measured at the point of consumption rather than subtracted from anything afterwards, so time spent writing a chunk with the next one already queued costs nothing here — and it is not a round trip, since the initiator streams the file continuously. What made it necessary: cutting the apply concurrency from 16 to 4 collapsed `link` from 42.4 ms to 9.0 ms while apply time rose only 30%, which said `link` had been this side's own queueing all along, and left `far ÷ peers` — 4.35 ms an action at 16 and 4.89 ms at 4, against serialized budgets of 4.29 ms and 5.57 ms — as the one term that did not move.
  - **What is left of `far` after `starved` is nine filesystem round trips, so the destination reports them one by one.** A `writeFile` on the receiving end creates the parent directory, opens a temporary file, writes it, closes it, stamps an mtime, reads a stat and may shell out to `chmod`, renames, and stats again (§7.2, §7.4) — and those have unrelated fixes: the directory create is paid once per *file* where once per *directory* would do, the mode step is a process spawn whenever the temporary file's mode does not already match, and the rename is neither. The destination therefore accumulates a per-step total across the session and reports it with the count of `chmod` processes it actually started, because a spawn per file and a stat per file are different orders of cost that the mode step's total cannot tell apart on its own. **Cumulative, and carried on the `unlock` reply alone** — the last exchange of a run (§4.3), so the totals are complete when they leave and a run that dies earlier reports nothing rather than a partial figure that reads like a whole one. Seven integers on every reply would measurably inflate the byte counts this section exists to explain. The `write` step contains the inbound transfer for the same reason the span does, so it is read against `starved`, never alone. Note what is *not* in there: there is no fsync per file — `IOSink.flush` drains the buffer to the descriptor, and the only fsync in the write path is the archive store's, one per batch (§8.2).
  - **These spans overlap** (task 0f7dfc): §4.2 keeps several operations outstanding and §7.1 runs several actions at once, so a `total` is the sum of wall times that ran concurrently. It does not sum with the other operations' totals to the phase that contained them, and will exceed it. `mean` is what one call cost end to end — which is still the number that says whether the link is slow, and still the one the §4.2 window is judged by — but it is no longer that call's share of the run. Occupancy was the alternative and was rejected: what this report exists to answer is "is an exchange expensive", which is a latency, and a figure that divided one exchange's cost by how many were in flight would hide exactly the regression it was built to catch. Read against the phase duration, the gap is now the overlap, which is itself worth seeing.
  - **A streamed operation's span is part its consumer's, so it is split where the consumer takes over (task 9d2158).** `readFile` is measured from the call to the last chunk being taken, which contains two unrelated things: the replica producing bytes, and the call parked waiting for its consumer to come back for the next one. Once the read-ahead landed (§7.2) that second term became the *send path's* backpressure arriving through the prefetch buffer — `ReadAhead` pauses the source at 64 KiB a stream — so a `readFile` mean that rose because the wire got slower and one that rose because the flash got slower are the same number, with opposite fixes. It is reported as **`held`**, and the span less it as **`own`**. Measured phone-to-desktop, `readFile` read 11.4 ms a call over 14,471 calls, which divided into the apply's serialized budget is essentially all of it — a figure that cannot be the device's storage, and could not be told from one until this split existed. `held` is `starved` seen from the other end of the same pipe: there the destination waiting on our bytes, here our read waiting on the destination's pace. **Absent, not zero** for every operation that hands back no stream, and `own` is printed rather than left to subtraction, only when every counted call reported a hold — netting a total over one population against a total over another is the arithmetic this section exists to refuse. It is taken at the `Agent` boundary rather than inside `ReadAhead` because that is the one object that sees both sides of every handover, and because it is also the only place that covers the unbuffered path, where a copy hands the source stream straight to the write.
  - **`settle` is the one figure on this path that is not an identity.** Per-action `wire` is concurrency divided by throughput by construction, so every split of it — link, far, anything finer — is arguable arithmetic over a quantity that was already determined by the window size and the rate. `settle` is not: it is the span from the reply's bytes arriving at `Channel.input` to that operation's future completing, two readings of one clock in one process, and it contains what nothing else here can — decoding the frame, the route's delivery, the microtask hops, the window slot being released, and any wait behind a subscription paused for backpressure. Everything in it serialises on one isolate's event loop, which is exactly the constraint a concurrency figure hides: a run can be at its throughput ceiling with the link idle and the phone's isolate saturated, and `quiet`, `waiting`, `far` and `link` all look the same in both cases. Read against the *serialized* cost per action — the phase divided by the action count, not the per-action wire — it either accounts for the unexplained remainder or rules the event loop out. **Absent, not zero**, for a `readFile`: it holds its window slot for a whole stream consumed at the caller's pace, with the other replica's `writeFile` inside that span, so there is no instant on it that means "this side had the answer".
- **The apply's read-ahead**, as three counters for the run rather than per replica — it sits between the two agents and belongs to neither (§7.2). How many copies were prefetched, how many had their source read finished before the write was handed the stream, and the most bytes held across every read at once. **Three, because a read-ahead that did not pay off has three explanations and `starved` distinguishes none of them**: it never ran, it ran but not far enough ahead, or its own byte budget was what stopped it running further. The peak is also the only reading this project has taken of an apply-path buffer against the bound §7.2 states for it. Absent rather than zeroed on a run that has not finished applying.
- **Per replica, transport traffic**, for a remote side: bytes with framing included, the number of *sends* — buffers handed to the transport — the number of *writes* those sends actually became, the number of *frames* they carried, the resulting mean frame size, frames per write, and sends per operation. Read against the same side's file-content figure, the byte gap is the protocol's own overhead; read against each other, the counts say how much protocol rides on each flush, which is what a change that coalesces frames is judged by. They are counted rather than derived on purpose: a per-send cost worked out by dividing a byte total by an assumed frame count is a model, and a model that fits one run is not evidence about the next.
  - **Sends and writes are counted on opposite sides of the coalescing** (task 9d2158, phase 3), and that is the point of having both. A *send* is a frame handed to `Channel.send`; a *write* is an `add`-and-`flush` `FlushedSink` actually performed, and §4.2's batching happens between the two, so **no arithmetic over sends can see it** — a run whose frames all left in company reports the same send count as one where none did. `MeteredChannel` therefore reads the channel's own cumulative figures on the way past rather than counting anything itself. **Absent is not zero**: a transport with no sink to flush — an in-memory pair — reports nothing at all and every one of these figures is omitted, because zero writes would read as the one outcome this pair exists to detect.
  - **`frames per write` is a mean and a poor summary of its own subject, so the distribution is reported too.** It moved 1.00 → 1.15 on the run where the effect it exists to detect moved ~2×, because a mean over every write is diluted by the majority that drain with nothing queued. `FlushedSink` therefore counts **how many sends each write carried**, bucketed, plus the largest — the writes that carried a crowd are the ones the batching exists for, and they are invisible in the mean.   - **What the send path costs is two figures, counted on opposite sides of the `add`.** `queue` is per *send*, from being handed over to its write beginning — the wait behind other senders that phase 3 removed, previously *inferred* from a link latency that looked too large. `flush` is per *write*, from `add` to `flush` returning, and it is **the only figure in this section that is wall time**: a sink never has two writes in flight, so those spans are strictly serial and their total is real seconds the connection spent on the transport, readable straight against the phase. One figure over both could not be either — it counted each flush once per sender waiting on it, so it summed past any clock while still being too small to be a queue.
  - **And `flush` is itself a mean over a population of every size, so the writes are banded by bytes.** `flush` × `writes` is the largest serialized term an apply has left — measured phone-to-desktop, 388 µs × 35,378 = 13.7 s of a 24.8 s apply — and whether sending fewer, larger buffers shrinks that total depends entirely on how much of one write is fixed cost (a syscall, a TLS record, a flush) and how much is the bytes going over the link. Those two have opposite consequences for every such change and the mean cannot tell them apart: it averages a 100-byte control frame with a 1 MiB batch. `FlushedSink` therefore keeps, per size band, the writes that landed there, the bytes they carried and their summed flush, so the report prints **what a write of each size cost and the rate it implies**. Flat rates across the bands say the link is the cost and fewer, larger writes buy nothing; rates rising with size say the per-write cost is fixed and they buy the difference. It is measured on the run's own spread rather than on a sweep — a real apply already writes across several orders of size, so the small write and the large one come from the same run, link and radio. The bands sum to `writes` and to the serial total beside them, which is the containment check any new split is read with first, and a band no write landed in prints zeroes because it *was* measured.
  - **A local benchmark cannot judge it, and says so** (task 9d2158). `benchmark/local_sync_throughput.dart` measured 1.13 frames per write at 10 ms / 65 Mbit and 1.02 at 40 ms / 8 Mbit — *less* coalescing on the slower link — because its proxy accepts whatever it is given and rate-limits downstream, so the backpressure the batching is a consequence of stops at the proxy's buffer instead of reaching this side's socket, and a unix-socket `flush` returns in microseconds either way. The benchmark is a regression check on the idle path, not evidence about the gain; only a phone run over `peer://`, where a flush costs TLS and a radio, can produce that.
- **Per replica, per phase, the link not carrying** for a remote side, as **two** figures: `quiet`, time with no send in flight and no operation open on this side, and `waiting`, time with no send in flight and an operation still open. **This is the figure that chooses the next optimization**, and it takes two of them to do it: `quiet` is time more callers would fill, `waiting` is time they would not. A byte count cannot tell those apart, because both move the same bytes.
  - **One figure could not, and was biased rather than merely ambiguous.** It was the gaps between one byte moving and the next — but a send is a *span* and a receive is a *point event*, so inbound traffic contributed no busy time at all and the whole of an arriving transfer read as silence. In the pull direction that is ~100% idle by construction. Both figures are now credited from what this side *has outstanding*, which is a state it knows at every instant, rather than from the spacing of events; a flush still counts as the link carrying something until the transport has taken it, so a link slow enough to apply backpressure shows its transmit time as busy. A phase absent from either is one during which the transport was never measured, not one that was never idle.

**Measured, not modelled.** Every figure above is a counter or a clock read at the moment the thing happened. That is the point of the section, and it is a constraint on what may be concluded from it: a decision about where the next optimization goes is made from a number this report prints, not from arithmetic over several of them. Three claims in the task 0f7dfc sequence were arithmetic — a share of the critical path from multiplying three means together, a per-send cost from an assumed frame count, a link's unused fraction with no account of where it went — and each happened to fit the run it was fitted to. The ones that were wrong were wrong invisibly, which is the failure mode a model has and a counter does not.

**How.** Two decorators — one over `Agent`, one over `Channel` — writing into one recorder, plus phase brackets in `RunController`, `RemoteAgent` reporting one already-split record per exchange, `FrameRouter` stamping each frame it decodes with the arrival instant — on the clock `RemoteAgent` was given, since a span between two clocks is not a span — and `FlushedSink` counting what it did with what it was handed. Each reports what it already holds and none is a new layer: `RemoteAgent` is the only object that sees all four instants of an exchange, the router is the only thing that sees a chunk arrive, the channel is the only thing that sees every byte, and the sink is the only thing that sees a write at all. Both interfaces already exist (§13), so nothing new is abstracted, and a run whose agents are not wrapped records phases and nothing else.

**One assembly object, and one per run *attempt*.** Those pieces were installed by hand at seven call sites, none of which could tell whether it had installed all of them — and a connection wired with a metered channel and an unmetered agent yields a report that looks complete and is not, silently, because every figure it can still compute comes out plausible. `RunInstruments` holds the recorder and hands out all of them, so each site writes one line. It is built per *attempt*, not per controller or per process: every figure a recorder holds accumulates and `elapsed` runs from construction, so a head that can retry — the Flutter one can, from a pause or a failure — would otherwise report two attempts as one run, with a doubled `scan` and an inflated `apply`, and say nothing about having done so.

The recorder is always on: it is a clock read and a map update against operations whose floor is an fsync or a round trip, and a flag would mean the numbers are missing exactly when someone wants them.

**Where it surfaces.** `dsync sync --timings` prints the report to stderr after the summary — after, so it never comes between a reader and the outcome, and on stderr so `--json`'s stdout stays a clean JSON Lines stream (§11.4). It prints for a failed or interrupted run too. The Flutter head has the same report behind a Timings action on the Run page, live while the run is going, with a copy button that yields the identical text `--timings` prints — a phone is the device whose cost profile exists nowhere else, and the realistic path from a number on it to whoever is fixing the protocol is a paste into a message.
